# Composite Pattern — Interview Notes

The Composite Pattern lets you treat **a single object and a group of objects the same way**, so the client never has to care whether it's holding one item or a whole tree.

## 1. First, the scenario (what are we even building?)

You're building the **shopping cart for Amazon**. Two kinds of things can sit in a cart:

**1. A Product** — one single item you can buy.

```
Book "Atomic Habits"  —  ₹499
iPhone 15             —  ₹79,999
Charger               —  ₹1,999
```

**2. A Bundle** — a combo deal. Amazon groups several things together and sells it as **one unit at one price**.

```
iPhone Essentials Combo  —  ₹97,997
   ├── iPhone 15      ₹79,999
   ├── AirPods        ₹15,999
   └── Charger        ₹1,999
```

Here's the important bit: **from the customer's point of view, that bundle is just one thing in their cart.** They see one line, one price, and they can delete it with one click. They don't care that it's internally made of three products.

And bundles can contain **other bundles**:

```
Mega Festival Bundle  —  ₹98,844
   ├── Book "Atomic Habits"       ₹499          ← a product
   ├── iPhone Essentials Combo    ₹97,997       ← a BUNDLE inside a bundle
   │      ├── iPhone 15    ₹79,999
   │      ├── AirPods      ₹15,999
   │      └── Charger      ₹1,999
   └── Back to School Kit         ₹348          ← another bundle
          ├── Notebook     ₹249
          └── Pen Set      ₹99
```

This shape — **things containing things containing things** — is a **tree**. That's the whole setup.

---

## 2. Now the problem (what actually goes wrong)

The naive approach: write two separate classes.

```java
class Product {
    String name;
    double price;
    double getPrice() { return price; }
}

class ProductBundle {
    String bundleName;
    List<Product> products;              // a bundle holds products
    double getPrice() {
        double total = 0;
        for (Product p : products) total += p.getPrice();
        return total;
    }
}
```

Looks fine. Now try to actually use it.

### Problem 1: What type is the cart?

You want to store the cart. So... what do you write?

```java
List<Product> cart;          // ❌ can't hold bundles
List<ProductBundle> cart;    // ❌ can't hold single products
List<???> cart;              // ❌ they share no common type!
```

`Product` and `ProductBundle` are **completely unrelated classes**. Java sees no connection between them. So there is **no single list** that can hold both. You're stuck before you've written any logic.

### Problem 2: You can't write the total

The thing you actually want is this simple loop:

```java
for (item : cart) total += item.getPrice();
```

You can't. There's no common type to loop over. So you end up with two separate lists and manual bookkeeping:

```java
List<Product> looseProducts;
List<ProductBundle> bundles;

for (Product p : looseProducts)      total += p.getPrice();
for (ProductBundle b : bundles)      total += b.getPrice();
```

Now do the same for `display()`. And for `applyDiscount()`. And `checkStock()`. **Every single operation gets written twice.** Add a third type later (a gift card?) and it's written three times.

### Problem 3 (the fatal one): bundles can't nest

Look again:

```java
class ProductBundle {
    List<Product> products;     // ← can ONLY hold Products
}
```

A bundle holds a `List<Product>`. So you **cannot put a bundle inside a bundle**. That Mega Festival Bundle from §1? **Impossible to build.** The structure is permanently stuck at one level deep.

> **The root cause of all three problems is the same:** a single product and a group of products have **nothing in common** in the code — even though in real life they're both just *"a thing in my cart with a price."*

---

## 3. The fix (one idea)

Real life already told us the answer. A customer looks at their cart and sees **"things I'm buying."** A book is one. A combo is one. They behave the same: both have a price, both can be displayed, both can be removed.

So **say that in code** — give them a shared interface:

```java
interface CartItem {
    double getPrice();
    void display(String indent);
}

class Product       implements CartItem { ... }    // a single item IS a CartItem
class ProductBundle implements CartItem { ... }    // a group IS ALSO a CartItem
```

That's it. That's the Composite Pattern. Watch all three problems dissolve:

```java
List<CartItem> cart;                                  // ✅ Problem 1 solved — holds both

for (CartItem item : cart) total += item.getPrice();  // ✅ Problem 2 solved — one loop
```

And for Problem 3 — the bundle changes **one word**:

```java
class ProductBundle implements CartItem {
    List<CartItem> items;        // ✅ was List<Product>. Now holds products AND bundles
}
```

Because `ProductBundle` is itself a `CartItem`, a bundle can now hold bundles. **Nesting to any depth, for free.**

> **Composite Pattern, in one sentence:** make the *group* implement the same interface as the *single item*, so the code can't tell them apart — and nobody has to.

---

## 4. Why the recursion works (this trips people up)

When you call `megaBundle.getPrice()`, how does it know how deep to go?

**It doesn't. And it doesn't need to.** Here's the actual loop inside a bundle:

```java
double getPrice() {
    double total = 0;
    for (CartItem item : items) total += item.getPrice();
    return total;
}
```

The bundle just asks each child *"what's your price?"* It has **no idea** whether that child is a product or another bundle — and it doesn't check:

- If the child is a **Product** → returns its price. **Stops.** (base case)
- If the child is a **Bundle** → runs this same loop on *its* children. **Goes deeper.** (recursive step)

**Each object knows what it is.** So the tree unwinds itself. You never write a type check, never track depth, never write a counter.

```
megaBundle.getPrice()
   ├── book.getPrice()           → 499          (Product: stops)
   ├── iphoneCombo.getPrice()    → asks its 3 children → 97,997   (Bundle: recurses)
   └── schoolKit.getPrice()      → asks its 2 children → 348      (Bundle: recurses)
                                                  ─────────
                                    total = 98,844
```

## 5. The two roles (standard vocabulary)

| Role | Here | Children? | Job |
| --- | --- | --- | --- |
| **Component** | `CartItem` | — | The shared interface. The client only ever sees this |
| **Leaf** | `Product` | ❌ | Does the real work — **the base case** |
| **Composite** | `ProductBundle` | ✅ | Delegates to children, combines results — **the recursive step** |

"**Part-whole hierarchy**" is just the textbook phrase for this: the *parts* (products) and the *whole* (bundle) are treated the same way.

---

## 6. ⭐ The skeleton (be able to write this cold)

```java
// COMPONENT — the shared interface
interface CartItem {
    double getPrice();
    void display(String indent);
}

// LEAF — no children, does its own job
class Product implements CartItem {
    private String name;
    private double price;

    public Product(String name, double price) {
        this.name = name;
        this.price = price;
    }

    public double getPrice() { return price; }              // BASE CASE

    public void display(String indent) {
        System.out.println(indent + "Product: " + name + " - Rs." + price);
    }
}

// COMPOSITE — holds children, delegates to them
class ProductBundle implements CartItem {
    private String bundleName;
    private List<CartItem> items = new ArrayList<>();       // ⭐ THE KEY LINE

    public ProductBundle(String bundleName) { this.bundleName = bundleName; }

    public void addItem(CartItem item) { items.add(item); }

    public double getPrice() {
        double total = 0;
        for (CartItem item : items) total += item.getPrice();   // RECURSIVE STEP
        return total;
    }

    public void display(String indent) {
        System.out.println(indent + "Bundle: " + bundleName);
        for (CartItem item : items) item.display(indent + "   ");
    }
}
```

### If you remember one thing, remember this line

```java
List<CartItem> items;      // ✅ list of the INTERFACE  → nesting works
List<Product>  items;      // ❌ list of the LEAF       → stuck one level deep
```

The composite holds a list of the **interface**, not of the leaf. Get this wrong and everything still compiles — nesting just silently never works. It's the line an interviewer watches you write.

## 7. ⭐ The one real follow-up: where do `add()`/`remove()` go?

| | **Transparency** (`add` in the interface) | **Safety** (`add` only in Composite) ✅ |
| --- | --- | --- |
| Uniform treatment | Perfect — leaf and composite look identical | Client must know the type to add children |
| `product.addItem(x)` | **Compiles**, throws at runtime 💥 | **Won't compile** ✅ |
| Verdict | GoF's original choice | What you should write in Java |

> **Say this:** *"I keep `addItem()` only on the Composite. Putting it on the interface means `product.addItem()` compiles and then throws `UnsupportedOperationException` at runtime — I'd rather the compiler catch that. Classic transparency vs safety trade-off; I pick safety."*

## 8. Where this shows up in LLD rounds

You won't be asked *"explain Composite."* You'll be asked to design something that's **secretly a tree**:

| Problem | Component | Leaf | Composite |
| --- | --- | --- | --- |
| **File system** (most common) | `FileSystemItem` | `File` | `Directory` |
| **Org hierarchy** | `Employee` | Individual contributor | `Manager` |
| **Restaurant menu** | `MenuComponent` | `MenuItem` | `Menu` (sub-menus) |
| **UI / DOM** | `Component` | `Button`, `Text` | `Panel`, `Container` |
| **Cart / pricing** | `CartItem` | `Product` | `ProductBundle` |

> **Keep file system loaded.** `getSize()` on a `File` returns its own size; on a `Directory` it sums its children. Identical skeleton, renamed. A folder containing folders is the exact same shape as a bundle containing bundles.

---

## 9. Pros / Cons

| Pros | Cons |
| --- | --- |
| Client code has **zero type checks** | **Overkill if nothing nests** — don't force it on flat data |
| Nesting to any depth comes **free** | **Over-general interface** — some methods make no sense for a leaf |
| New item types need **no client changes** (OCP) | Can **hide real differences** between types where that matters |
| Each operation written **once**, not per-type | Deep trees → **recursive stack traces are harder to debug** |

---

## 10. Interview Quick Recall

- **Type:** Structural
- **Core idea:** The group implements the same interface as the single item, so the client can't tell them apart
- **Roles:** Component (interface) + Leaf (base case) + Composite (recursive step)
- **Trigger phrase:** *"a X can contain other X"* → tree → Composite
- **Key line:** `List<CartItem> items;` — list of the **interface**, not the leaf
- **When NOT to use:** Data never nests, or leaf and group genuinely need different handling
- **Follow-up 1:** *"Where do add/remove go?"* → Composite only; safety over transparency (§7)
- **Follow-up 2:** *"Composite vs Decorator?"* → Both wrap, both share the component interface. **Decorator wraps exactly ONE** object to add behaviour. **Composite holds MANY** to build a tree
