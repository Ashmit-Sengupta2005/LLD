# Proxy Pattern — Interview Notes

The Proxy Pattern puts a **stand-in object** in front of the real one, so checks, caching or lazy loading can happen before the call is passed through.

## 1. The scenario (plain language)

You're building video downloads for a YouTube-style app. One class does the work:

```java
class RealVideoDownloader {
    String downloadVideo(String url) {
        // hits the network, takes 300ms, uses bandwidth
    }
}
```

Now: **User 1 downloads a video. User 2 asks for the same video.** You download it again. User 3 asks — download again.

Same bytes, fetched three times. Wasted bandwidth, wasted time, and the user waits every time.

> **Analogy:** A CEO's assistant. You don't get to call the CEO directly — you call the assistant. If you ask something they already know, they just answer you (the CEO is never disturbed). If it's genuinely important, *then* they put you through. The assistant **looks like** the way to reach the CEO, but gets to decide what actually reaches them.

---

## 2. The problem

The obvious fix is to add caching inside `RealVideoDownloader`. But then:

- That class now does **two jobs** — downloading *and* cache management (violates SRP)
- Tomorrow you want **permission checks**. And **logging**. All stuffed into the same class
- You **can't turn caching off** for a test or a special case
- If it's a **third-party / legacy class, you can't edit it at all**

And the client is hardwired to the concrete class:

```java
RealVideoDownloader d = new RealVideoDownloader();   // locked in
```

There's no seam — nowhere to slip in extra behaviour without editing the real class or every call site.

---

## 3. The fix: put a stand-in in front

Make an interface, and have **both** the real class and a stand-in implement it:

```java
interface VideoDownloader {
    String downloadVideo(String url);
}

class RealVideoDownloader   implements VideoDownloader { ... }   // does the work
class CachedVideoDownloader implements VideoDownloader { ... }   // the PROXY
```

The proxy holds the real object and decides **whether to even call it**:

```java
class CachedVideoDownloader implements VideoDownloader {
    private RealVideoDownloader realDownloader;
    private Map<String, String> cache = new HashMap<>();

    public String downloadVideo(String url) {
        if (cache.containsKey(url)) {
            return cache.get(url);          // ⭐ real object NEVER called
        }
        if (realDownloader == null) {
            realDownloader = new RealVideoDownloader();   // created only when needed
        }
        String video = realDownloader.downloadVideo(url);
        cache.put(url, video);
        return video;
    }
}
```

Now the client swaps one word and changes nothing else:

```java
VideoDownloader downloader = new CachedVideoDownloader();   // was RealVideoDownloader
downloader.downloadVideo(url);   // identical call — client has no idea a proxy exists
```

> **Proxy in one sentence:** a stand-in that implements the same interface as the real object, so it can **intercept calls and control whether the real object is used at all**.

**That last part is the whole point.** The proxy's job isn't to do the work — it's to decide whether the work needs doing.

---

## 4. ⭐⭐ Proxy vs Decorator (the question you WILL get)

These two are **structurally identical**. Same interface, wraps an object, delegates to it. If you diagram them, you cannot tell them apart. The difference is **what they're for**:

| | **Decorator** | **Proxy** |
| --- | --- | --- |
| **Intent** | **Add** behaviour to the result | **Control access** to the object |
| **Does the real object get called?** | **Always** — it's just enhanced | **Maybe not** — that's the point |
| **Who stacks them?** | **Client** — `new Cheese(new Olives(pizza))` | **Nobody** — the proxy usually creates the real object itself |
| **How many?** | Many, stacked freely | Usually one |
| **Example** | Pizza + cheese + olives | Cache / permission check / lazy load |

> **The one-line test:** *"Does the wrapper always call the wrapped object?"*
> **Always calls it → Decorator.** It can only add to the result.
> **Might skip it → Proxy.** It's gatekeeping.

> **Say this:** *"Structurally they're the same — both implement the subject's interface and hold a reference to it. The difference is intent. A decorator always delegates and adds to the result; a proxy may refuse to delegate at all. A cache proxy returning a hit never touches the real object — a decorator can't do that."*

Also worth knowing: **Proxy and Adapter are not the same either.** An adapter **changes** the interface (because two sides don't match). A proxy **keeps the interface identical** (that's what makes it a drop-in replacement).

---

## 5. The 4 types (just know the names + one example each)

| Type | Controls... | Example |
| --- | --- | --- |
| **Virtual** | *When* the object is created | Don't build the expensive object until first real use — **lazy loading** |
| **Protection** | *Who* can call it | Admin can edit, viewer can only read |
| **Remote** | *Where* the object lives | Object is on another server; proxy hides the network call |
| **Smart** | *What happens around* the call | Caching, logging, counting accesses |

Our example is **Smart** (caching) + **Virtual** (the real downloader isn't created until the first cache miss).

---

## 6. The skeleton

```java
// SUBJECT — both implement this, which is what makes the swap invisible
interface VideoDownloader {
    String downloadVideo(String url);
}

// REAL SUBJECT — does one job, knows nothing about caching or permissions
class RealVideoDownloader implements VideoDownloader {
    public String downloadVideo(String url) {
        System.out.println("Downloading from network: " + url);
        return "Video content from " + url;
    }
}

// PROXY — same interface, decides whether to call the real one
class CachedVideoDownloader implements VideoDownloader {
    private RealVideoDownloader realDownloader;
    private Map<String, String> cache = new HashMap<>();

    public String downloadVideo(String url) {
        if (cache.containsKey(url)) return cache.get(url);     // short-circuit

        if (realDownloader == null)
            realDownloader = new RealVideoDownloader();         // lazy init

        String video = realDownloader.downloadVideo(url);
        cache.put(url, video);
        return video;
    }
}
```

**Two details worth getting right:**

1. **Declare the client variable as the interface** — `VideoDownloader d = new CachedVideoDownloader();` If you write `CachedVideoDownloader d = ...` you've thrown away the swappability that justifies the pattern.
2. **A proxy usually creates the real object itself** (a decorator is handed one). That's what lets it do lazy initialization — you can't delay creating something that was passed to you.

## 7. Where you've already used it

| Real system | What the proxy does |
| --- | --- |
| **Hibernate / JPA lazy loading** | `order.getCustomer()` returns a proxy; the DB query fires only when you actually touch a field |
| **Spring `@Transactional`, `@Cacheable`** | Spring AOP wraps your bean in a proxy that opens/commits the transaction around your method |
| **Java RMI** | Local stub object forwards calls over the network (remote proxy) |
| **`java.lang.reflect.Proxy`** | JDK's built-in dynamic proxy — creates proxies at runtime |
| **Spring Security `@PreAuthorize`** | Protection proxy — checks your role before the method runs |

> Good line to drop: *"Spring's `@Transactional` is a proxy — that's why calling an annotated method from inside the same class doesn't work. The call never leaves the object, so it never passes through the proxy."* This is a classic real-world gotcha and shows you understand it beyond the textbook.

---

## 8. Pros / Cons

| Pros | Cons |
| --- | --- |
| **Real class stays clean** — no caching/auth logic mixed in (SRP) | **Extra layer** — more classes, more indirection |
| Can **add behaviour without touching** the real class (OCP) — works even for third-party code | Proxy must **mirror the whole interface**, even methods it doesn't care about |
| **Lazy initialization** — expensive objects built only if needed | **Adds latency** if the proxy itself does heavy work |
| Swappable — client sees only the interface | **Debugging is confusing** — stack traces show the proxy, not your class |

---

## 9. Interview Quick Recall

- **Type:** Structural
- **Core idea:** A stand-in implementing the same interface, which **controls access** to the real object
- **Roles:** Subject (interface) + RealSubject (the worker) + Proxy (the gatekeeper)
- **Key property:** The proxy may **not call the real object at all** — that's what separates it from Decorator
- **4 types:** Virtual (when), Protection (who), Remote (where), Smart (what around)
- **When NOT to use:** Object is cheap and access needs no control — the layer buys you nothing
- **Follow-up 1:** *"Proxy vs Decorator?"* → Identical structure, different intent. Decorator **always** delegates and adds; proxy **may skip** delegating (§4)
- **Follow-up 2:** *"Proxy vs Adapter?"* → Adapter **changes** the interface (compatibility). Proxy **keeps it identical** (drop-in replacement)
- **Follow-up 3:** *"Real example?"* → Hibernate lazy loading, or Spring `@Transactional` — plus the self-invocation gotcha (§7)
