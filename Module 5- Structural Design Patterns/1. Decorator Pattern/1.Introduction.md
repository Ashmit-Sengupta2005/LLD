# Decorator Pattern — Interview Notes

## 1. The scenario

You sell pizzas. There's a base pizza, and customers add toppings: cheese, olives, stuffed crust.

Each topping changes **two things** — the description and the price:

```
Plain Pizza                              ₹200
Plain Pizza + Cheese                     ₹240
Plain Pizza + Cheese + Stuffings         ₹320
```

The obvious approach: one class per combination.

```java
class PlainPizza {}
class CheesePizza extends PlainPizza {}
class CheeseOlivePizza extends CheesePizza {}
class CheeseOliveStuffedPizza extends CheeseOlivePizza {}
```

---

## 2. The problem: class explosion

Every topping either **is or isn't** on the pizza. So **n toppings → 2ⁿ combinations**:

| Toppings | Classes needed |
| --- | --- |
| 3 | 7 |
| 5 | 31 |
| 10 | **1023** |

And it's worse than just "many classes":

- **Can't change at runtime** — the combination is fixed when you pick the class
- **Logic is duplicated** — "+₹40 for cheese" is rewritten in every class containing cheese
- **One new topping doubles everything** — adding `Paneer` means re-creating every existing class with a paneer version

> **Analogy:** You don't own a separate jacket for every weather combination. You wear a shirt, add a sweater if cold, add a raincoat if wet. **Layers, composed on the spot** — not one garment per situation.

---

## 3. The fix: wrap instead of subclass

Make toppings into **wrappers** that hold a pizza and implement the same interface as a pizza:

```java
Pizza pizza = new PlainPizza();     // ₹200
pizza = new Cheese(pizza);          // wraps it  → ₹240
pizza = new Stuffings(pizza);       // wraps that → ₹320
```

Each wrapper holds the previous object. Because `Cheese` is itself a `Pizza`, it can be wrapped again — any combination, **any order, at runtime, with zero new classes**.

> **Decorator in one sentence:** wrap an object in another object that has **the same interface**, so it can add behaviour while still looking like the original.

---

## 4. ⭐ How the layers actually work

`Cheese` doesn't know the price of a plain pizza. It only knows **"whatever I'm wrapping, plus 40."**

```java
public int getCost() {
    return basePizza.getCost() + 40;   // ask inward, then add my bit
}
```

So the call travels **inward** to the base, then each layer **adds on the way back out**:

```
Stuffings.getCost()
   └── Cheese.getCost()
          └── PlainPizza.getCost()  →  200      ← base case, stops here
          ←  200 + 40 = 240                     ← cheese adds its bit
   ←  240 + 80 = 320                            ← stuffings adds its bit
```

Exactly like a recursive call stack: go all the way down, then accumulate coming back up.

---

## 5. The skeleton

```java
// 1. COMPONENT — common interface for base objects AND wrappers
interface Pizza {
    String getDescription();
    int getCost();
}

// 2. CONCRETE COMPONENT — a real base object (the base case)
class PlainPizza implements Pizza {
    public String getDescription() { return "Plain Pizza"; }
    public int getCost() { return 200; }
}

// 3. ABSTRACT DECORATOR — implements Pizza AND holds a Pizza
abstract class PizzaDecorator implements Pizza {
    protected Pizza basePizza;                    // ⭐ THE KEY LINE
    PizzaDecorator(Pizza pizza) { this.basePizza = pizza; }
}

// 4. CONCRETE DECORATOR — delegate inward, then add your bit
class Cheese extends PizzaDecorator {
    Cheese(Pizza pizza) { super(pizza); }

    public String getDescription() { return basePizza.getDescription() + " + Cheese"; }
    public int getCost()           { return basePizza.getCost() + 40; }
}
```

### The line that makes it work

```java
abstract class PizzaDecorator implements Pizza {   // ← IS a Pizza
    protected Pizza basePizza;                     // ← HAS a Pizza
}
```

A decorator **is** the thing *and* **holds** the thing. That dual nature is the entire pattern — being a `Pizza` is what lets a decorator be wrapped by another decorator.

---

## 6. Where you've already used it — Java I/O

This is the textbook real example, and it's worth recognising:

```java
new BufferedReader(new InputStreamReader(new FileInputStream("file.txt")))
```

Three layers: read the file → decode bytes to characters → add buffering. Each wraps the previous, each adds one capability, all are `Reader`s.

**Others:** text formatting (bold/italic/underline on plain text), notification systems (base alert + SMS + email + Slack wrappers), food delivery add-ons.

---

## 7. Decorator vs Proxy vs Composite (all three wrap — know the difference)

| | **Decorator** | **Proxy** | **Composite** |
| --- | --- | --- | --- |
| **Intent** | **Add** behaviour | **Control access** | Build a **tree** |
| **Wraps** | One object | One object | **Many** children |
| **Calls the wrapped object?** | **Always** | **Maybe not** (cache hit skips it) | Calls all children |
| **Who builds it?** | **Client** stacks them | Proxy makes its own | Client builds the tree |

> **Decorator vs Proxy is the common trap.** Structurally identical. Test: *does the wrapper always call what it wraps?* **Always → Decorator** (it can only add). **Might skip → Proxy** (it's gatekeeping).

---

## 8. Pros / Cons

| Pros | Cons |
| --- | --- |
| **No class explosion** — 1 class per feature, not per combination | **Many small classes** |
| **Runtime composition** — add/remove/reorder on the fly | **Order can matter** (10% discount before or after tax?) — subtle bugs |
| Each decorator is **reusable** with any base | **Debugging is painful** — deep stack traces through every layer |
| **Open/Closed** — new feature = new class, nothing else changes | Client must know to **stack** them correctly |

---

## 9. Interview Quick Recall

- **Type:** Structural
- **Core idea:** Wrap an object in something with the same interface that delegates inward and adds its own bit
- **Roles:** Component (interface) + Concrete Component (base) + Abstract Decorator (is-a + has-a) + Concrete Decorators
- **Solves:** **Class explosion** — 2ⁿ subclasses for n optional features
- **Key line:** `abstract class PizzaDecorator implements Pizza { protected Pizza basePizza; }` — **is-a and has-a together**
- **When NOT to use:** Only one or two fixed variations (just subclass), or when ordering causes subtle bugs
- **Follow-up 1:** *"Decorator vs Inheritance?"* → Inheritance is **static** (compile time, fixed combination). Decorator is **dynamic** (runtime, any combination)
- **Follow-up 2:** *"Decorator vs Proxy?"* → Same structure. Decorator always delegates and adds; proxy may skip the real object entirely
- **Follow-up 3:** *"Real example?"* → Java I/O streams — `new BufferedReader(new InputStreamReader(new FileInputStream(f)))`
