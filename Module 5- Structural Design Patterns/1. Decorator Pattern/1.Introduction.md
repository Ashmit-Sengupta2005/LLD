# Decorator Pattern — Interview Notes

## 1. What is the Decorator Pattern?

The **Decorator Pattern** is a structural design pattern that allows behavior to be **added to individual objects dynamically at runtime**, without affecting the behavior of other objects from the same class.

It wraps an object inside another object that adds new behaviors or responsibilities, keeping the **original object's interface intact**.

> "Don't create a new class for every combination — wrap layers on top of a base."

---

## 2. Real-life Analogy (Coffee Shop)

Think of a coffee shop:

- You order a **simple coffee**
- Then you add **milk**, **sugar**, **whipped cream**, etc.
- You don't need a whole new drink class for every combination

Each addition **wraps** the original and adds something more. The final drink is still a "coffee" — it just has extra layers.

---

## 3. The Problem It Solves (Class Explosion)

Without the Decorator Pattern, adding combinations of features leads to **class explosion**:

```java
class PlainPizza {}
class CheesePizza extends PlainPizza {}
class OlivePizza extends PlainPizza {}
class StuffedPizza extends PlainPizza {}
class CheeseStuffedPizza extends CheesePizza {}
class CheeseOlivePizza extends CheesePizza {}
class CheeseOliveStuffedPizza extends CheeseOlivePizza {}
// ... keeps growing exponentially!
```

With **3 toppings**, you need **7 subclasses**. With **10 toppings**, you'd need **1023 subclasses**. This is unmanageable.

The Decorator Pattern eliminates this by letting you **compose behaviors using wrappers** instead of subclassing:

```java
Pizza myPizza = new MargheritaPizza();
myPizza = new ExtraCheese(myPizza);   // wrap with cheese
myPizza = new Olives(myPizza);        // wrap with olives
myPizza = new StuffedCrust(myPizza);  // wrap with stuffed crust
```

Any combination, **zero new classes needed**.

---

## 4. How does it work? (Key mechanics)

| Component              | Purpose                                                                     |
| ---------------------- | --------------------------------------------------------------------------- |
| **Component Interface**| Common interface for both base objects and decorators (`Pizza`)              |
| **Concrete Component** | Base object that can be decorated (`PlainPizza`, `MargheritaPizza`)         |
| **Abstract Decorator** | Implements the Component, holds a reference to a wrapped Component          |
| **Concrete Decorators**| Each adds one specific behavior (`ExtraCheese`, `Olives`, `StuffedCrust`)   |

### Flow:

1. Start with a **base component** (e.g., `MargheritaPizza`)
2. **Wrap** it with a decorator (e.g., `ExtraCheese`) — the decorator holds a reference to the original
3. Wrap **again** with another decorator (e.g., `Olives`) — it holds a reference to the previous wrapper
4. Each decorator **delegates** to the wrapped object and **adds** its own behavior
5. The client sees the **same interface** (`Pizza`) throughout — it doesn't know about the layers

---

## 5. Without Decorator vs. With Decorator

### Without (Bad Practice — Inheritance for every combination)

```java
class PlainPizza {}
class CheesePizza extends PlainPizza {}
class OlivePizza extends PlainPizza {}
class CheeseOlivePizza extends CheesePizza {}
class CheeseOliveStuffedPizza extends CheeseOlivePizza {}
// exponential growth for every new topping!
```

**Problems:**
- **Class explosion** — every combination needs its own subclass
- **Rigid** — can't add/remove toppings at runtime
- **Violates Open/Closed** — new toppings require modifying the hierarchy
- **Not reusable** — `ExtraCheese` logic is duplicated across multiple subclasses

### With Decorator (Good Practice) ✅

```java
Pizza myPizza = new MargheritaPizza();          // base: ₹200
myPizza = new ExtraCheese(myPizza);             // +₹40
myPizza = new Olives(myPizza);                  // +₹30
myPizza = new StuffedCrust(myPizza);            // +₹50

System.out.println(myPizza.getDescription());   // Margherita, Extra Cheese, Olives, Stuffed Crust
System.out.println(myPizza.getCost());           // ₹320
```

- **No class explosion** — add new decorators independently
- **Runtime composition** — add/remove/reorder toppings dynamically
- **Each decorator is reusable** — works with any `Pizza` base
- **Open/Closed** — extend with new decorators, never modify existing code

## 6. The Code Structure

```java
// 1. COMPONENT INTERFACE — common contract
interface Pizza {
    String getDescription();
    double getCost();
}

// 2. CONCRETE COMPONENT — the base object
class MargheritaPizza implements Pizza {
    public String getDescription() { return "Margherita Pizza"; }
    public double getCost() { return 200.0; }
}

// 3. ABSTRACT DECORATOR — wraps a Pizza, implements Pizza
abstract class PizzaDecorator implements Pizza {
    protected Pizza pizza;              // holds the wrapped object
    public PizzaDecorator(Pizza pizza) {
        this.pizza = pizza;
    }
}

// 4. CONCRETE DECORATOR — adds one specific behavior
class ExtraCheese extends PizzaDecorator {
    public ExtraCheese(Pizza pizza) { super(pizza); }

    public String getDescription() {
        return pizza.getDescription() + ", Extra Cheese";   // delegate + add
    }
    public double getCost() {
        return pizza.getCost() + 40.0;                      // delegate + add
    }
}
```

### Key insight — the call chain:

```
StuffedCrust.getCost()
  → Olives.getCost()
      → ExtraCheese.getCost()
          → MargheritaPizza.getCost()   → returns 200
        → returns 200 + 40 = 240
    → returns 240 + 30 = 270
  → returns 270 + 50 = 320
```

Each decorator **delegates** to the inner object, then **adds** its own contribution. Like a **call stack** — behavior accumulates layer by layer.

---

## 7. Key Takeaways

- **Abstract classes can have constructors** — `PizzaDecorator`'s constructor initializes the wrapped reference. It's called via `super(pizza)` from each concrete decorator
- **Decorator as layers** — each decorator wraps the previous one, like wrapping a gift box with multiple layers of paper
- **Call stack analogy** — behavior accumulates step by step as each decorator delegates inward, then adds its own logic on the way back
- **Loose coupling** — the client only knows the `Pizza` interface. It doesn't care whether it's a base pizza or ten decorators deep

---

## 8. The Interview Explanation

> "Without the Decorator Pattern, if I have a `Pizza` base and 5 possible toppings, I'd need up to 31 subclasses to cover every combination — that's class explosion.
>
> With the Decorator Pattern, I define a `Pizza` interface, base components like `MargheritaPizza`, and an abstract `PizzaDecorator` that wraps any `Pizza`. Each topping is a concrete decorator — `ExtraCheese`, `Olives`, `StuffedCrust` — that wraps the previous object, delegates the call, and adds its own behavior. I can compose any combination at runtime by stacking decorators. Adding a new topping means one new decorator class — nothing else changes."

## 10. When to Use the Decorator Pattern

- **Add responsibilities dynamically** — attach functionality at runtime, not compile time
- **Avoid subclass explosion** — compose behaviors instead of creating classes for every combination
- **Follow Open/Closed Principle** — extend behavior without modifying existing code
- **Reusable, composable behaviors** — decorators can be mixed and matched freely
- **Layered, step-by-step enhancements** — apply decorators one after another in any order

---

## 11. Pros of Decorator Pattern

- **Adheres to Open/Closed Principle** — enhancements without modifying existing code
- **Runtime flexibility** — behaviors added or removed dynamically
- **Avoids subclass explosion** — one decorator per feature, not one subclass per combination
- **Single Responsibility** — each decorator handles exactly one add-on
- **Composable** — stack any number of decorators in any order

---

## 12. Cons of Decorator Pattern

- **Can result in many small classes** — each feature needs its own decorator class
- **Stack trace debugging is difficult** — deeply nested decorators produce complex call chains
- **Overhead of multiple wrapping** — many layers can introduce slight runtime overhead
- **Developers must understand decorator flow** — the chaining logic has a learning curve

---

## 13. Real-World Use Cases

| Use Case                          | Base Object     | Decorators                            |
| --------------------------------- | --------------- | ------------------------------------- |
| **Food delivery (Swiggy/Zomato)** | Base food item  | Extra cheese, sauces, toppings        |
| **Google Docs / Word processors** | Plain text      | Bold, Italic, Underline               |
| **Java I/O Streams**              | `InputStream`   | `BufferedInputStream`, `DataInputStream`, `GZIPInputStream` |
| **Notification systems**          | Base notification | SMS, Email, Push, Slack wrappers     |
| **Logging**                       | Base logger     | Timestamp, File output, Encryption    |

> **Java I/O is the classic Decorator example:** `new BufferedReader(new InputStreamReader(new FileInputStream("file.txt")))` — each class wraps the previous one, adding buffering, character decoding, and file reading in layers.

---

## 14. Interview Quick Recall

- **Pattern type:** Structural
- **Core idea:** Add behavior to objects **dynamically** by wrapping them with decorator objects — same interface, extra functionality
- **Key components:** Component Interface + Concrete Component + Abstract Decorator + Concrete Decorators
- **Key benefit:** Eliminates **class explosion** — compose any combination of features at runtime
- **Solves:** Rigid inheritance hierarchies, hardcoded feature combinations, violation of Open/Closed Principle
- **When to use:** Need runtime-configurable features, many optional add-ons, layered behavior
- **When NOT to use:** Only one or two fixed features (just use inheritance), or when decorator ordering causes subtle bugs
- **Common follow-up:** "How is it different from Inheritance?" → Inheritance is **static** (compile-time, one hierarchy). Decorator is **dynamic** (runtime, composable, any combination)
