# Facade Pattern — Interview Notes

## 1. What is the Facade Pattern?

The **Facade Pattern** is a structural design pattern that provides a **single, simplified entry point** to a complex subsystem of many classes.

The client talks to **one** class instead of **ten**. The facade internally coordinates all the real work.

> "One doorbell instead of ten doors."

---

## 2. Real-life Analogy (Manual vs Automatic Car)

- **Manual car (no facade):** to move, you coordinate clutch + gear + accelerator yourself, in the right order, at the right time. The complexity is exposed to you.
- **Automatic car (facade):** you press **D** and drive. The gearbox still does all that work internally — you just don't have to know about it.

The complexity didn't disappear. It got **moved behind a simple interface**.

---

## 3. The Problem It Solves

Booking a movie ticket (BookMyShow) isn't one action — it's a **workflow** across 5 services:

```
PaymentService  →  SeatReservationService  →  TicketService
                →  LoyaltyPointsService    →  NotificationService
```

If the client does this itself, the client must know:

1. **WHICH** services exist (all 5)
2. In **WHAT ORDER** to call them (pay first, ticket only after seat is reserved)
3. The **BUSINESS RULES** in between (how many loyalty points for this amount?)

That's a lot of knowledge for a client whose only job is *"book me a ticket"*. And every new client — web app, mobile app, admin panel — has to repeat all of it.

---

## 4. ⭐ But isn't this just "a class that calls other classes"?

**Yes — and that's the honest answer.** Structurally, Facade is the simplest pattern in the book. There is no clever mechanism here like Decorator's recursive wrapping or Adapter's interface translation. It is literally one class holding references to several others.

**Facade is a pattern of INTENT, not of STRUCTURE.**

So the real question isn't *"what's the trick?"* — it's **"what do you actually gain?"** Four things:

### (a) The workflow knowledge has to live SOMEWHERE

The order of steps and the business rules are **real logic**. They aren't optional. The only choice is:

- **In every client** → duplicated 5 times, and 5 places to fix when it changes
- **In one facade** → written once

### (b) One place to change

New step added (say, a GST invoice service)? Loyalty rule changes from 10% to 15%? `SeatReservationService` changes its method signature?

- **Without facade:** hunt down every call site across the codebase
- **With facade:** change one class. **No client changes at all.**

### (c) Compile-time coupling drops

The client imports **1 class** instead of **5**. It literally cannot depend on things it doesn't know about.

### (d) The client's code says WHAT, not HOW

```java
bookingFacade.bookMovieTicket("user123", "movie456", "A10", "user@example.com", 500);
```

One line that reads like the business requirement. Compare that to 10 lines of service wiring.

> **Interview line:** *"Facade isn't clever — it's disciplined. It takes orchestration knowledge that would otherwise be scattered across every client and puts it in exactly one place."*

---

## 5. How does it work? (Key mechanics)

| Component     | Purpose                                                                                                   |
| ------------- | --------------------------------------------------------------------------------------------------------- |
| **Client**    | Knows only the facade. Nothing else.                                                                       |
| **Facade**    | Exposes one simple method; holds references to all subsystem classes; owns the **order** and the **rules** |
| **Subsystem** | The real worker classes (`PaymentService`, `TicketService`, …)                                             |

### Important: the arrows go ONE WAY

```
Client  →  Facade  →  Subsystem
```

The subsystem classes **do not know the facade exists**. They stay fully independent and individually testable. The facade is added *on top* — it doesn't change them.

---

## 6. Without Facade vs With Facade

### Without (Bad Practice)

```java
PaymentService paymentService = new PaymentService();
paymentService.makePayment("user123", 500);

SeatReservationService seatService = new SeatReservationService();
seatService.reserveSeat("movie456", "A10");

TicketService ticketService = new TicketService();
ticketService.generateTicket("movie456", "A10");

LoyaltyPointsService loyaltyService = new LoyaltyPointsService();
loyaltyService.addPoints("user123", 50);     // why 50? the rule lives in the client!

NotificationService notificationService = new NotificationService();
notificationService.sendBookingConfirmation("user@example.com");
```

**Problems:**

- Client is **tightly coupled** to all 5 services
- Workflow order and business rules **leak into the client**
- **Duplicated** in every client that books a ticket
- Violates **SRP** — the client knows far too much

### With Facade (Good Practice) ✅

```java
MovieBookingFacade bookingFacade = new MovieBookingFacade();
bookingFacade.bookMovieTicket("user123", "movie456", "A10", "user@example.com", 500);
```

- Client knows **one class, one method**
- Order + rules live in **one place**
- Subsystem can be refactored freely — client never changes

## 7. The Code Structure

```java
// SUBSYSTEM — independent, knows nothing about the facade
class PaymentService {
    public void makePayment(String accountId, double amount) { ... }
}
class SeatReservationService {
    public void reserveSeat(String movieId, String seatNumber) { ... }
}
// ... TicketService, LoyaltyPointsService, NotificationService

// FACADE — holds the services, owns the order and the rules
class MovieBookingFacade {
    private PaymentService paymentService;
    private SeatReservationService seatReservationService;
    private TicketService ticketService;
    private LoyaltyPointsService loyaltyPointsService;
    private NotificationService notificationService;

    public MovieBookingFacade() {
        this.paymentService = new PaymentService();
        this.seatReservationService = new SeatReservationService();
        // ... initialize the rest
    }

    public void bookMovieTicket(String accountId, String movieId, String seatNumber,
                                String userEmail, double amount) {
        paymentService.makePayment(accountId, amount);
        seatReservationService.reserveSeat(movieId, seatNumber);
        ticketService.generateTicket(movieId, seatNumber);

        int points = (int) (amount * 0.10);   // BUSINESS RULE lives here, not in the client
        loyaltyPointsService.addPoints(accountId, points);

        notificationService.sendBookingConfirmation(userEmail);
    }
}
```

---

## 8. Key Takeaways

- **Facade does not block direct access.** A power user who needs something advanced can still call `PaymentService` directly. The facade is a **convenience layer**, not a wall. (This is what separates it from a strict abstraction layer.)
- **Facade adds no new functionality.** It only re-packages existing behaviour. If you're adding real new logic, you may be building a *service layer*, not a facade.
- **Subsystem stays testable.** Each service is still an independent class you can unit test on its own.
- **You can have more than one facade** over the same subsystem — e.g. `MovieBookingFacade` and `RefundFacade`.

---

## 9. The Interview Explanation

> "Booking a movie ticket touches five services — payment, seat reservation, ticket generation, loyalty points, and notification. Without a facade, every client has to know all five classes, the correct call order, and the business rules in between. That knowledge gets duplicated across the web app, the mobile app, and the admin panel.
>
> With the Facade Pattern, I create a `MovieBookingFacade` with a single `bookMovieTicket()` method. It holds the five services and owns the orchestration — the order and the rules. The client makes one call. If a new step is added or a rule changes, I change one class and zero clients.
>
> Structurally it's just a class that delegates — Facade is a pattern of intent, not of mechanism. The value is that orchestration knowledge lives in exactly one place."

## 11. When to Use the Facade Pattern

- **Subsystem is complex** — many classes with many dependencies between them
- **You want a simple API for the outside world** — one entry point instead of many
- **You want to reduce coupling** between client code and subsystem internals
- **You want clean layering** — the facade marks the boundary between layers
- **The same multi-step workflow is repeated** in several places

---

## 12. Pros of Facade Pattern

- **Loose coupling** — client depends on one class, not the whole subsystem
- **Simplifies client code** — one call instead of a wiring sequence
- **Single place to change** — workflow and rules are centralized
- **Flexibility** — subsystem can be refactored without touching clients
- **Promotes layered architecture** — clear boundaries between layers
- **Better testability** — subsystem tested independently, facade tested for orchestration

---

## 13. Cons of Facade Pattern

- **Can become a god object** — if it orchestrates too much it violates SRP. Split into multiple facades
- **Hidden complexity** — the complexity still exists, it's just not visible. Harder for a new developer to see the full flow
- **Harder to debug** — an extra layer of indirection in stack traces
- **Error handling gets murky** — a failure deep in the subsystem is harder to diagnose through the facade
- **Fragile if the facade itself changes often** — then clients break anyway, defeating the purpose

## 15. Facade vs Adapter vs Decorator (common interview trap)

|               | **Facade**                           | **Adapter**                         | **Decorator**             |
| ------------- | ------------------------------------ | ----------------------------------- | ------------------------- |
| **Intent**    | **Simplify** a complex subsystem     | **Convert** one interface to another | **Add behaviour** to an object |
| **Wraps**     | **Many** classes                     | Usually **one** class               | **One** object (stackable) |
| **Interface** | Creates a **brand new, simpler** one | Must **match an existing** expected one | **Keeps the same** interface |
| **Why**       | Convenience                          | Compatibility                       | Extension                 |

> Quick memory hook: **Adapter** = make it *fit*. **Decorator** = make it *more*. **Facade** = make it *simpler*.

---

## 16. Interview Quick Recall

- **Pattern type:** Structural
- **Core idea:** Provide one simplified entry point to a complex subsystem; the facade owns the **order** and the **rules**
- **Key components:** Client + Facade + Subsystem classes
- **Key benefit:** Orchestration knowledge lives in **exactly one place** instead of being duplicated in every client
- **Solves:** Client tightly coupled to many classes, duplicated multi-step workflows, leaked business rules
- **When to use:** Complex subsystem, repeated multi-step workflow, want a clean layer boundary
- **When NOT to use:** Subsystem is already simple (the facade adds a pointless layer), or you'd be adding real new logic (that's a service layer, not a facade)
- **Common follow-up 1:** *"Does the facade block direct access to the subsystem?"* → **No.** Clients can still use subsystem classes directly for advanced needs. It's a convenience layer, not a wall
- **Common follow-up 2:** *"Facade vs Adapter?"* → Adapter changes an interface for **compatibility** (the interface is forced on it). Facade invents a **new simpler** interface for **convenience**
- **Common follow-up 3:** *"Isn't this just a wrapper class?"* → Structurally yes. Facade is defined by **intent**, not mechanism — the point is centralizing orchestration, not a clever structure
