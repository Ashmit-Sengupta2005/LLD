# Facade Pattern — Interview Notes

## 1. What is the Facade Pattern?

A structural pattern that provides a **single, simplified entry point** to a complex subsystem of many classes. The client talks to **one** class instead of ten; the facade coordinates the rest internally.

> **Analogy:** Automatic car. You press **D** and drive — the gearbox still does the clutch/gear work, you just don't deal with it. The complexity didn't vanish, it moved behind a simple interface.

---

## 2. The Problem It Solves

Booking a movie ticket isn't one action, it's a **workflow** across 5 services: payment → seat reservation → ticket → loyalty points → notification.

If the client does this itself, it must know:

1. **WHICH** services exist (all 5)
2. In **WHAT ORDER** to call them
3. The **BUSINESS RULES** in between (how many points for ₹500?)

And every client — web, mobile, admin panel — repeats all of it.

---

## 3. ⭐ "Isn't this just a class that calls other classes?"

**Yes. That's honestly all it is structurally.** There's no clever mechanism like Decorator's wrapping or Adapter's translation.

**Facade is a pattern of INTENT, not of STRUCTURE.** The value:

- **The workflow knowledge has to live somewhere.** The call order and the business rules are real logic. Either they're in **one** facade, or copy-pasted into **every** client.
- **One place to change.** Points rule 10% → 15%? New GST step? Change one class, **zero clients**.
- **Client code says WHAT, not HOW** — one line that reads like the requirement.

> **Interview line:** *"Facade isn't clever, it's disciplined. It puts orchestration knowledge that would otherwise be scattered across every client into exactly one place."*

---

## 4. Without vs With

```java
// WITHOUT — client knows all 5 classes, the order, and the rules
PaymentService ps = new PaymentService();
ps.makePayment("user123", 500);
SeatReservationService ss = new SeatReservationService();
ss.reserveSeat("movie456", "A10");
TicketService ts = new TicketService();
ts.generateTicket("movie456", "A10");
LoyaltyPointsService ls = new LoyaltyPointsService();
ls.addPoints("user123", 50);          // why 50? the rule leaked into the client
NotificationService ns = new NotificationService();
ns.sendBookingConfirmation("user@example.com");

// WITH — client knows one class, one method
MovieBookingFacade facade = new MovieBookingFacade();
facade.bookMovieTicket("user123", "movie456", "A10", "user@example.com", 500);
```

---

## 5. The Code Structure

```java
class MovieBookingFacade {
    private PaymentService paymentService;
    private SeatReservationService seatReservationService;
    private TicketService ticketService;
    private LoyaltyPointsService loyaltyPointsService;
    private NotificationService notificationService;

    public MovieBookingFacade() {
        this.paymentService = new PaymentService();
        // ... initialize the rest
    }

    public void bookMovieTicket(String accountId, String movieId, String seatNumber,
                                String userEmail, double amount) {
        paymentService.makePayment(accountId, amount);
        seatReservationService.reserveSeat(movieId, seatNumber);
        ticketService.generateTicket(movieId, seatNumber);

        int points = (int) (amount * 0.10);   // BUSINESS RULE lives here, not in the client
        loyaltyPointsService.addPoints(accountId, points);

        notificationService.sendBookingConfirmation(userEmail);
    }
}
```

**Arrows go one way:** `Client → Facade → Subsystem`. The subsystem classes don't know the facade exists, so they stay independent and testable.

---

## 6. The Interview Explanation

> "Booking a ticket touches five services. Without a facade, every client knows all five classes, the call order, and the rules in between — duplicated across web, mobile and admin.
>
> With a facade, `MovieBookingFacade.bookMovieTicket()` owns that orchestration. The client makes one call. If a rule changes or a step is added, I change one class and zero clients.
>
> Structurally it's just a class that delegates — Facade is a pattern of intent, not mechanism. The value is that orchestration lives in exactly one place."

---

## 7. Pros / Cons

| Pros | Cons |
| --- | --- |
| Loose coupling — client depends on 1 class, not 5 | Can become a **god object** if it does too much (violates SRP) |
| Workflow + rules centralized in one place | Complexity is hidden, not gone — harder for new devs to see the full flow |
| Subsystem can be refactored without touching clients | Extra indirection makes debugging / stack traces harder |
| Promotes clean layering | If the facade itself changes often, clients break anyway |

**Real examples:** Spring `JdbcTemplate` (hides Connection/Statement/ResultSet/cleanup), SLF4J `LoggerFactory`, e-commerce `OrderFacade`.

---

## 8. Facade vs Adapter vs Decorator

|  | **Facade** | **Adapter** | **Decorator** |
| --- | --- | --- | --- |
| **Intent** | **Simplify** a subsystem | **Convert** one interface to another | **Add behaviour** |
| **Wraps** | **Many** classes | Usually **one** class | **One** object (stackable) |
| **Interface** | Invents a **new simpler** one | Must **match an existing** one | **Keeps the same** one |

> **Memory hook:** Adapter = make it *fit*. Decorator = make it *more*. Facade = make it *simpler*.

---

## 9. Interview Quick Recall

- **Type:** Structural
- **Core idea:** One simplified entry point to a complex subsystem; the facade owns the **order** and the **rules**
- **Components:** Client + Facade + Subsystem
- **Key benefit:** Orchestration lives in **exactly one place** instead of every client
- **When NOT to use:** Subsystem is already simple, or you're adding real new logic (that's a service layer, not a facade)
- **Follow-up 1:** *"Does it block direct access to the subsystem?"* → **No.** Clients can still call `PaymentService` directly. It's a convenience layer, not a wall
- **Follow-up 2:** *"Facade vs Adapter?"* → Adapter changes an interface for **compatibility** (interface is forced on it). Facade invents a new simpler one for **convenience**
