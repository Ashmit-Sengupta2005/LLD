# Adapter Pattern — Interview Notes

## 1. The scenario

Your checkout code pays through a gateway. You started with PayU, and your system calls:

```java
paymentGateway.pay(orderId, amount);
```

Now the business wants **Razorpay** too. You pull in their SDK and find:

```java
razorpayAPI.makePayment(invoiceId, amountInRupees);   // different method name!
```

Same job — charge money — but a **different method name and different parameter names**. Your code says `pay()`, theirs says `makePayment()`.

You **cannot fix this by editing their class.** It's a third-party JAR. You don't own it.

> **Analogy:** Your Indian charger doesn't fit a European socket. You don't rewire the hotel, and you don't buy a new phone. You use a **plug adapter** — it fits the socket on one side and your plug on the other.

---

## 2. The problem

Without a fix, the mismatch leaks into your business logic:

```java
class CheckoutService {
    public void checkout(String orderId, double amount, String provider) {
        if (provider.equals("payu")) {
            new PayUGateway().pay(orderId, amount);
        } else if (provider.equals("razorpay")) {
            new RazorpayAPI().makePayment(orderId, amount);   // different call
        }
        // Stripe next month? another branch. PayPal? another branch.
    }
}
```

- `CheckoutService` now **knows every provider's API** — tightly coupled
- Every new provider means **editing checkout logic** (violates Open/Closed)
- **No polymorphism** — you can't just swap providers, you branch on a string
- Payment plumbing is **tangled with business logic**

---

## 3. The fix: a translator class

Write a small class that **implements the interface your system expects**, and internally **calls the third-party method**:

```java
interface PaymentGateway {                    // what YOUR system expects
    void pay(String orderId, double amount);
}

class RazorpayAdapter implements PaymentGateway {
    private RazorpayAPI razorpayAPI = new RazorpayAPI();

    public void pay(String orderId, double amount) {
        razorpayAPI.makePayment(orderId, amount);   // ⭐ translate: pay() → makePayment()
    }
}
```

That's the whole pattern. `RazorpayAdapter` **looks like** a `PaymentGateway` to your code, but **speaks Razorpay** on the inside.

Now checkout is clean and never changes again:

```java
class CheckoutService {
    private PaymentGateway gateway;
    public CheckoutService(PaymentGateway gateway) { this.gateway = gateway; }
    public void checkout(String orderId, double amount) { gateway.pay(orderId, amount); }
}

new CheckoutService(new PayUGateway());       // already fits
new CheckoutService(new RazorpayAdapter());   // made to fit
```

> **Adapter in one sentence:** a wrapper that **converts one interface into another** so two incompatible classes can work together, without modifying either.

## 4. The skeleton

```java
// TARGET — the interface your system expects
interface Target {
    void doSomething(params);
}

// ADAPTEE — the existing class with the WRONG interface (you can't edit it)
class Adaptee {
    void doSomethingDifferently(otherParams) { ... }
}

// ADAPTER — implements Target, wraps Adaptee, translates between them
class Adapter implements Target {
    private Adaptee adaptee;

    public void doSomething(params) {
        adaptee.doSomethingDifferently(convert(params));   // the translation
    }
}
```

**The skeleton is always this.** What varies per use case is only:

- the **method name** being mapped
- the **parameter mapping** (reorder, rename, convert units — e.g. rupees → paise, `double` → `BigDecimal`)
- the **return value** translation (e.g. their `PaymentResponse` → your `boolean`)

---

## 5. ⭐ The key distinction: Adapter vs Facade vs Decorator

All three wrap something. The difference is **what happens to the interface**:

| | **Adapter** | **Facade** | **Decorator** |
| --- | --- | --- | --- |
| **Interface** | **Changes** it to match what the client expects | **Invents a new simpler** one | **Keeps it identical** |
| **Wraps** | One class | **Many** classes | One object (stackable) |
| **Why** | **Compatibility** — it doesn't fit | **Convenience** — too complicated | **Extension** — add behaviour |
| **Did you have a choice?** | No — the interface was forced on you | Yes — you chose to simplify | Yes — you chose to extend |

> **Memory hook:** Adapter = make it **fit**. Facade = make it **simpler**. Decorator = make it **more**.

---

## 6. Where you've already used it

| System | Adaptee | What the adapter does |
| --- | --- | --- |
| **SLF4J** | Log4j, java.util.logging | One `Logger` interface over every logging framework |
| **JDBC drivers** | MySQL, PostgreSQL, Oracle | One `Connection` API over every database |
| **`Arrays.asList()`** | A Java array | Makes an array look like a `List` |
| **Cloud SDKs** | S3, GCS, Azure Blob | One `StorageService` interface over all three |

> **The giveaway that you need an Adapter:** you're integrating code **you can't modify** — third-party SDK, legacy module, or a team's API you don't own.

---

## 7. Pros / Cons

| Pros | Cons |
| --- | --- |
| **Reuse existing code** without modifying it | **Extra layer** of indirection |
| New provider = **one new adapter**, zero changes elsewhere (OCP) | Too many adapters → **hard to follow** what's really being called |
| Client depends on an **abstraction**, not a vendor (DIP) | Can **mask bad design** — sometimes the right fix is refactoring, not wrapping |
| Makes third-party integration **swappable and testable** | Translation can be **lossy** if the two APIs don't map cleanly |

---

## 8. Interview Quick Recall

- **Type:** Structural
- **Core idea:** Implement the interface the client expects; internally call the incompatible class
- **Roles:** Target (expected interface) + Adaptee (incompatible class) + Adapter (translator) + Client
- **Trigger:** The class has the **right logic but the wrong interface**, and you **can't edit it**
- **Key line:** `class Adapter implements Target { private Adaptee adaptee; }` — implements one side, holds the other
- **When NOT to use:** You control both sides — just make the interfaces match instead of wrapping
- **Follow-up 1:** *"Object Adapter vs Class Adapter?"* → Object Adapter uses **composition** (holds the adaptee as a field) — **the one you use in Java**. Class Adapter uses **multiple inheritance**, which Java doesn't allow (C++ only)
- **Follow-up 2:** *"Adapter vs Facade?"* → Adapter changes an interface for **compatibility** (forced on you). Facade invents a new simpler one for **convenience** (your choice)
- **Follow-up 3:** *"Real example?"* → SLF4J over Log4j, or `Arrays.asList()`
