# Adapter Pattern — Interview Notes

## 1. What is the Adapter Pattern?

The **Adapter Pattern** is a structural design pattern that allows **incompatible interfaces to work together** by acting as a translator or wrapper around an existing class. It converts the interface of a class into another interface that a client expects.

> "Don't modify the plug or the socket — just use an adapter."

---

## 2. Real-life Analogy (Plug Adapter)

Imagine traveling from India to Europe. Your mobile charger doesn't fit into European sockets. Instead of buying a new charger, you use a **plug adapter**. The adapter allows your charger (Indian plug) to fit the European socket — enabling charging **without modifying** either the socket or the charger.

Similarly, the Adapter Pattern allows objects with incompatible interfaces to collaborate by introducing an adapter in between.

---

## 3. When do you need it? (Real use cases)

Use the Adapter Pattern when:

- You need to use an **existing class**, but its interface **doesn't match** what your system expects
- You want to **reuse legacy code** without modifying its internal structure
- You're **integrating third-party APIs** or external services into your application
- You want to **decouple** your client code from specific implementations

**Examples:**

- **Payment gateways** — Razorpay uses `makePayment()`, your system expects `pay()`. An adapter translates between them
- **Logging frameworks** — unify Log4j, SLF4J, java.util.logging behind a common interface
- **Cloud SDKs** — abstract AWS S3, Google Cloud Storage, Azure Blob behind one `StorageService` interface
- **Database drivers** — different databases expose different APIs; JDBC acts as an adapter layer

> Analogy: A translator at a UN conference — the speaker speaks French, the listener understands English. The translator (adapter) converts French → English. Neither the speaker nor the listener needs to change.

---

## 4. How does it work? (Key mechanics)

| Component          | Purpose                                                                    |
| ------------------ | -------------------------------------------------------------------------- |
| **Target**         | The interface the client expects (e.g., `PaymentGateway`)                  |
| **Adaptee**        | The existing class with an incompatible interface (e.g., `RazorpayAPI`)    |
| **Adapter**        | Implements the Target, wraps the Adaptee, translates calls between them    |
| **Client**         | Uses the Target interface — never knows about the Adaptee or the Adapter's internals |

### Flow:

1. Client calls `adapter.pay(orderId, amount)` (Target interface)
2. Adapter internally calls `razorpayAPI.makePayment(orderId, amount)` (Adaptee's method)
3. Client is **completely unaware** that Razorpay's API is different under the hood

---

## 5. Without Adapter vs. With Adapter

### Without (Bad Practice)

```java
class CheckoutService {
    public void checkout(String orderId, double amount, String provider) {
        if (provider.equals("payu")) {
            PayUGateway payu = new PayUGateway();
            payu.pay(orderId, amount);
        } else if (provider.equals("razorpay")) {
            // Can't use RazorpayAPI directly — different method signature!
            RazorpayAPI razorpay = new RazorpayAPI();
            razorpay.makePayment(orderId, amount);  // different method name
        }
    }
}
```

**Problems:**
- `CheckoutService` is **tightly coupled** to every payment provider's specific API
- Adding a new provider → modify `CheckoutService` (violates Open/Closed Principle)
- Business logic **mixed** with provider-specific details
- No polymorphism — can't swap providers cleanly

### With Adapter (Good Practice) ✅

```java
class CheckoutService {
    private PaymentGateway paymentGateway;

    public CheckoutService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }

    public void checkout(String orderId, double amount) {
        paymentGateway.pay(orderId, amount);
    }
}

// Usage:
new CheckoutService(new PayUGateway());        // works directly
new CheckoutService(new RazorpayAdapter());    // adapter makes it work
```

- `CheckoutService` depends **only** on `PaymentGateway` interface — fully decoupled
- Adding a new provider = add one Adapter class — **zero changes** to the service
- Clean polymorphism — swap providers via constructor injection

## 6. The Adapter Template (Structure)

You're right that the Adapter Pattern is **context-dependent** — the exact translation logic varies per API. But the **structural skeleton** is always the same:

```java
// 1. TARGET — the interface your system expects
interface Target {
    void doSomething(params);
}

// 2. ADAPTEE — the existing class with a DIFFERENT interface
class Adaptee {
    void doSomethingDifferently(differentParams) { ... }
}

// 3. ADAPTER — bridges the gap
class Adapter implements Target {
    private Adaptee adaptee;

    Adapter(Adaptee adaptee) {
        this.adaptee = adaptee;
    }

    void doSomething(params) {
        // Translate and delegate
        adaptee.doSomethingDifferently(convertedParams);
    }
}
```

This template is **fixed**. What changes between use cases is:
- The **method names** being translated
- The **parameter mapping** (converting types, reordering args, etc.)
- The **return value translation** (if any)

---

## 7. The Interview Explanation

> "Without the Adapter Pattern, my `CheckoutService` would need to know every payment provider's specific API — `makePayment()` for Razorpay, `pay()` for PayU, `charge()` for Stripe. Adding a new provider means modifying the service, violating Open/Closed Principle.
>
> With the Adapter Pattern, I define a `PaymentGateway` interface with `pay()`. PayU implements it directly. For Razorpay, I create a `RazorpayAdapter` that implements `PaymentGateway` and internally delegates to `razorpayAPI.makePayment()`. The service only knows the interface — it's completely decoupled from provider-specific APIs. Adding a new provider means writing one adapter class. The service never changes."

## 9. Pros of Adapter Pattern

- **Code reusability** — reuse existing classes without changing their implementation
- **Code extensibility** — systems become more flexible and adaptable to change
- **Minimal client changes** — integration without modifying existing client logic
- **Simplifies third-party integration** — makes it easier to incorporate external services and APIs
- **Follows Open/Closed Principle** — extend with new adapters, never modify existing code
- **Follows Dependency Inversion** — client depends on abstraction (Target), not concrete implementations

---

## 10. Cons of Adapter Pattern

- **Adds an extra layer of abstraction** — can introduce unnecessary complexity if not used judiciously
- **Overuse can obscure design** — excessive adapters might make the architecture harder to understand and maintain
- **Slight performance overhead** — an extra indirection layer for every call (negligible in practice)
- **Can mask design issues** — sometimes the right fix is to redesign the interface, not wrap it

## 12. Interview Quick Recall

- **Pattern type:** Structural
- **Core idea:** Wrap an existing class with an incompatible interface to make it conform to the interface the client expects
- **Key components:** Target (expected interface) + Adaptee (existing incompatible class) + Adapter (translator) + Client
- **Key benefit:** Enables integration of **incompatible interfaces** without modifying existing code
- **Solves:** Interface mismatch, tight coupling to third-party APIs, non-reusable legacy code
- **When to use:** Existing class has the right logic but wrong interface, third-party integration, legacy code reuse
- **When NOT to use:** When you control both interfaces and can just make them match directly, or when the design should be refactored rather than wrapped
- **Common follow-up:** "Object Adapter vs Class Adapter?" → Object Adapter uses **composition** (wraps adaptee as a field — preferred in Java). Class Adapter uses **multiple inheritance** (not directly possible in Java, used in C++)
