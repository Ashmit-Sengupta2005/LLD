# Composite Pattern — Interview Notes

## 1. What is the Composite Pattern?

A structural pattern that composes objects into **tree structures** so that clients can treat **a single object and a group of objects identically**.

> **Recognition signal (this is what matters):** the data forms a **tree**, and a *"group"* should behave exactly like a *"single item"*. The moment you see **"a X can contain other X"** — folder in folder, bundle in bundle, menu in menu — it's Composite.

---

## 2. The Problem

Cart holds `Product` and `ProductBundle`. They're unrelated types, so:

- Client **branches on type** everywhere: `if (item is Product) ... else ...`
- Cart **can't hold one type** safely
- `ProductBundle` holds `List<Product>` → **a bundle can never contain another bundle**

---

## 3. Leaf vs Composite (the only two roles)

| Role | Here | Has children? | Does what |
| --- | --- | --- | --- |
| **Component** | `CartItem` | — | The shared interface. The client only ever sees this |
| **Leaf** | `Product` | ❌ | Does the actual work (`return price`) — the **base case** |
| **Composite** | `ProductBundle` | ✅ | **Delegates** to children and combines results — the **recursive step** |

---

## 4. ⭐ The Skeleton (memorize this — you'll be asked to code it)

```java
// COMPONENT — the shared interface
interface CartItem {
    double getPrice();
    void display(String indent);
}

// LEAF — no children, does its own job
class Product implements CartItem {
    private String name;
    private double price;

    public Product(String name, double price) {
        this.name = name;
        this.price = price;
    }

    public double getPrice() { return price; }              // BASE CASE

    public void display(String indent) {
        System.out.println(indent + "Product: " + name + " - Rs." + price);
    }
}

// COMPOSITE — holds children, delegates to them
class ProductBundle implements CartItem {
    private String bundleName;
    private List<CartItem> items = new ArrayList<>();       // ⭐ THE KEY LINE

    public ProductBundle(String bundleName) { this.bundleName = bundleName; }

    public void addItem(CartItem item) { items.add(item); }

    public double getPrice() {
        double total = 0;
        for (CartItem item : items) total += item.getPrice();   // RECURSIVE STEP
        return total;
    }

    public void display(String indent) {
        System.out.println(indent + "Bundle: " + bundleName);
        for (CartItem item : items) item.display(indent + "   ");
    }
}
```

### The one line that matters

```java
List<CartItem> items;      // ✅ recursive — a bundle can hold bundles
List<Product>  items;      // ❌ flat — only one level, pattern is dead
```

**The composite holds a list of the INTERFACE, not of the leaf.** That single choice is what makes nesting work. If you remember nothing else, remember this — it's the line an interviewer watches you write.

### Why the recursion just works

`megaBundle.getPrice()` doesn't know what its children are. It calls `getPrice()` on each, and **each child knows what it is**. A `Product` returns its price (stops). A `Bundle` loops again (recurses). The tree unwinds itself — you never write a type check or a depth counter.

## 5. ⭐ The one real follow-up: where do `add()`/`remove()` go?

This is the actual design discussion for Composite, and the only "theory" question likely to come up.

| | **Transparency** (put `add`/`remove` in the interface) | **Safety** (keep them only in Composite) ✅ |
| --- | --- | --- |
| Client treats leaf & composite | Perfectly uniformly | Must know the type to add children |
| `product.addItem(x)` | **Compiles**, then throws at runtime | **Won't compile** |
| Verdict | GoF's original; favours uniformity | What you should write in Java |

> **Say this:** *"I keep `addItem()` only on the Composite. Putting it on the interface means `Product.addItem()` compiles and then throws `UnsupportedOperationException` at runtime — I'd rather the compiler catch that. It's the classic transparency vs safety trade-off, and I pick safety."*

## 6. Where this actually shows up in LLD rounds

You'll rarely be asked *"explain Composite."* You'll be asked to **design something that is secretly a tree**:

| Problem | Component | Leaf | Composite |
| --- | --- | --- | --- |
| **File system** (most common) | `FileSystemItem` | `File` | `Directory` |
| **Org hierarchy** | `Employee` | Individual contributor | `Manager` |
| **Restaurant menu** | `MenuComponent` | `MenuItem` | `Menu` (sub-menus) |
| **UI / DOM** | `Component` | `Button`, `Text` | `Panel`, `Container` |
| **Cart / pricing** | `CartItem` | `Product` | `ProductBundle` |
| **Arithmetic parser** | `Expression` | `Number` | `AddExpression` |

> **File system is the one to have ready.** `getSize()` on a `File` returns its own size; on a `Directory` it sums its children. Same skeleton, renamed.

---

## 7. Pros / Cons

| Pros | Cons |
| --- | --- |
| Client code has **zero type checks** — polymorphism handles it | **Overkill for flat structures** — if nothing nests, don't use it |
| Nesting to any depth comes **for free** | **Over-general interface** — some methods don't make sense for a leaf |
| New item types need **no client changes** (OCP) | Can **hide real differences** between types where that matters |
| Price/display logic written **once** | Deep trees are **harder to debug** (recursive stack traces) |

---

## 8. Interview Quick Recall

- **Type:** Structural
- **Core idea:** Leaf and Composite share one interface; the Composite holds `List<Component>` and delegates
- **Components:** Component (interface) + Leaf (base case) + Composite (recursive step)
- **Trigger phrase:** *"a X can contain other X"* → part-whole hierarchy → tree
- **Key line:** `List<CartItem> items;` — list of the **interface**, not the leaf
- **When NOT to use:** Structure is flat / never nests, or leaf and group genuinely need different handling
- **Follow-up 1:** *"Where do add/remove go?"* → Composite only (safety over transparency) — see §5
- **Follow-up 2:** *"Composite vs Decorator?"* → Both wrap and both share the component interface. **Decorator wraps exactly ONE** object to add behaviour; **Composite holds MANY** to build a tree
