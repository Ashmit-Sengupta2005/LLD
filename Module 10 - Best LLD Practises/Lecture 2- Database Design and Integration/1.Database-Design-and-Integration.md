# Database Design & Integration in LLD

> **Say this first:** *"Database design in LLD is the path from requirements to running code: first I find the entities and how they relate (ER model), then turn those into tables with keys, then into classes in my application, and finally I put a DAO or Repository in between so my business logic never writes SQL directly."*

**Running example: a Razorpay-style payment system.**

---

## 1. ER Model — entities, attributes, relationships

An **ER (Entity-Relationship) model** is a diagram of your data before any SQL exists.

| Piece | Means | Razorpay example |
| --- | --- | --- |
| **Entity** | A real-world thing you store | `User`, `Merchant`, `Payment`, `Invoice` |
| **Attribute** | A property of that thing | `user_id`, `email`, `kyc_status` |
| **Relationship** | How two entities connect | User **makes** a Payment; Merchant **receives** a Payment |

**Relationship types — know these three:**

| Type | Example | How it's stored |
| --- | --- | --- |
| **One-to-One** | User ↔ KYC details | Foreign key on either side |
| **One-to-Many** | User → many Payments | **FK on the "many" side** (`payments.user_id`) |
| **Many-to-Many** | Students ↔ Courses | A **junction table** holding both FKs |

> **⭐ The rule to remember:** in one-to-many, the foreign key always lives on the **many** side. A payment stores *its* user; a user doesn't store a list of payment IDs.

## 2. Requirements → tables

**The steps:**
1. Pull the **entities** out of the requirement (usually the nouns)
2. List each entity's **attributes**
3. Pick the **primary key**, add **foreign keys** for the relationships
4. **Normalize** (see §3)
5. Add **constraints** (`NOT NULL`, `UNIQUE`) and **indexes**

**Requirement:** *"A user pays a merchant through a payment gateway using a payment method."*

```sql
users(user_id PK, name, email, phone)
merchants(merchant_id PK, name, business_type)
payment_methods(method_id PK, type, provider)
payments(payment_id PK, user_id FK, merchant_id FK, method_id FK, amount, status, created_at)
```

- **Primary key** — uniquely identifies a row (`payment_id`)
- **Foreign key** — points at another table's PK (`payments.user_id` → `users.user_id`)
- **Index** on anything you filter by often (`payments.user_id`), so lookups don't scan the table

---

## 3. ⭐ Normalization — the short version

**The goal: store each fact in exactly one place**, so an update can't leave two rows disagreeing.

**Unnormalized** — merchant name repeated in every payment row:

| payment_id | amount | merchant_name | merchant_city |
| --- | --- | --- | --- |
| 1 | 500 | Swiggy | Bangalore |
| 2 | 300 | Swiggy | Bangalore |

Swiggy changes city → you must update **every payment row**, and if you miss one the data contradicts itself.

**Normalized** — the merchant lives once, payments point at it:

```sql
merchants(merchant_id PK, name, city)
payments(payment_id PK, merchant_id FK, amount)
```

| Form | Rule in one line |
| --- | --- |
| **1NF** | No repeating groups — one value per cell (no `"phone1, phone2"` in a column) |
| **2NF** | 1NF + every non-key column depends on the **whole** primary key |
| **3NF** | 2NF + no non-key column depends on **another non-key** column |

> **Practical answer:** *"I normalize to 3NF by default, then denormalize deliberately if reads become a bottleneck — duplicating data is a performance trade, not an accident."*

## 4. ER → class model

Each entity becomes a class, each attribute a field, each relationship a reference.

```java
class User {
    Long id;
    String name;
    String email;
    List<Payment> payments;     // one-to-many
}

class Payment {
    Long id;
    User user;                  // many-to-one — mirrors payments.user_id
    Merchant merchant;
    Double amount;
    String status;
}
```

> **Note the difference:** the table stores a **foreign key** (`user_id`), the class holds the **object** (`User user`). An ORM like Hibernate is what converts between the two.

## 5. DAO — Data Access Object

**A DAO is a class whose only job is talking to the database.** All queries live there, so your business logic never contains SQL.

```java
public interface PaymentDAO {
    Payment getPaymentById(Long id);
    List<Payment> getPaymentsByUser(Long userId);
    void save(Payment payment);
}
```

**Why bother:**
- **Loose coupling** — swap MySQL for Postgres, or SQL for an API call, and only the DAO changes
- **Testable** — inject a fake `PaymentDAO` in tests instead of connecting to a real DB (this is **Dependency Injection**, Module 08)
- **Separation of concerns** — service classes hold business rules, DAOs hold queries

> **Without a DAO**, SQL strings end up scattered through your service classes, and every schema change means hunting them down.

---

## 6. Repository — and how it differs from DAO

A **Repository** gives you a **collection-like** view of your domain objects — as if the data were just a `List<Payment>` in memory. Frameworks usually generate it for you:

```java
public interface PaymentRepository extends JpaRepository<Payment, Long> {
    List<Payment> findByUserId(Long userId);     // Spring writes the query from the method name
}
```

| **DAO** | **Repository** |
| --- | --- |
| Database-centric — "how do I persist this?" | Domain-centric — "give me the payments for this user" |
| One DAO per **table** | One repository per **aggregate / domain object** |
| You write the SQL | Often **auto-implemented** by the framework |
| A plain persistence pattern | Comes from **Domain-Driven Design** |

> **⭐ If asked to distinguish them:** *"In practice they overlap heavily — both hide data access behind an interface. The intent differs: a DAO mirrors the table and exposes CRUD, while a repository mirrors the domain and hides that a database exists at all."*

That nuance is enough; nobody expects more at this level.

## 7. Real-world practices (one-liners)

- **Read replicas** for heavy reads; **batch inserts** for heavy writes
- **Cache** hot data in Redis so you aren't hitting the DB for the same row repeatedly
- **Audit logs** for anything money-related — payments must be traceable
- **Encrypt sensitive columns**, and use role-based access on the DB itself
- **Schema migrations** via Flyway or Liquibase — never edit production schema by hand
- **Monitor** slow queries (Grafana / Prometheus) before users report them

---

## 8. Quick Recall

- **ER model** = entities + attributes + relationships, drawn before any SQL
- **One-to-many → the FK lives on the many side**; many-to-many needs a **junction table**
- **Requirements → tables:** entities → attributes → PK/FK → normalize → constraints + indexes
- **Normalization** = each fact stored once. **3NF by default**, denormalize only for performance
- **ER → classes:** entity → class, attribute → field, FK → an object reference; the **ORM** bridges them
- **DAO** = all DB access behind an interface — loose coupling, easy to mock in tests
- **Repository** = collection-like, domain-centric; Spring Data auto-implements it from method names
- **DAO vs Repository** = table-centric vs domain-centric; in practice they overlap
