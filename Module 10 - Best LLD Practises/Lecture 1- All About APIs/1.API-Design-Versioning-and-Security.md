# API Design, Versioning & Security

> **Say this first:** *"An API is a contract between two services — it defines what data you can ask for, how you ask for it, and what you get back. Good API design is mostly about being predictable: consistent naming, the right HTTP verb, the right status code, and never breaking existing clients when you change something."*

---

## 1. What makes a good API

| Principle | Means |
| --- | --- |
| **Clarity** | Resource names are nouns, plural: `/users`, `/payments` — not `/getUser` |
| **Consistency** | Same naming style, same error format, same verbs everywhere |
| **Predictability** | Same input → same output. No surprises |
| **Minimalism** | Expose only what the client needs |
| **Statelessness** | No server-side session; **every request carries everything it needs** |

**HTTP verbs — know which does what:**

| Verb | Use | Idempotent? |
| --- | --- | --- |
| `GET` | Read | ✅ |
| `POST` | Create | ❌ |
| `PUT` | Replace the whole resource | ✅ |
| `PATCH` | Update part of it | ❌ (usually) |
| `DELETE` | Remove | ✅ |

> **⭐ Idempotent** = calling it 5 times has the same effect as calling it once. `DELETE /users/7` twice still leaves one deleted user. `POST` creates 5 records — that's why it isn't idempotent, and why payment APIs use **idempotency keys**.

---

## 2. Status codes — the part that always comes up

| Range | Meaning | The ones to know |
| --- | --- | --- |
| **2xx** | Success | `200` OK, `201` Created, `204` No Content |
| **4xx** | **Client's fault** | `400` Bad Request, `401` Unauthorized, `403` Forbidden, `404` Not Found, `409` Conflict, `429` Too Many Requests |
| **5xx** | **Server's fault** | `500` Internal Server Error, `503` Service Unavailable |

> **⭐ `401` vs `403`:** `401` = *"I don't know who you are"* (not logged in / bad token). `403` = *"I know who you are, you're just not allowed."*

**Never return `500` for a client mistake.** That's the most common API-design criticism in an interview.

---

## 3. Error responses — keep one shape everywhere

```json
{
  "timestamp": "2025-07-29T10:23:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Missing required field: email",
  "path": "/api/users"
}
```

One consistent structure across every endpoint, so clients can parse errors generically. The `message` should say **what to fix**, never leak a stack trace or SQL.

## 4. ⭐ DTOs — why not just return the entity?

**Entity** = the class that maps to your database table.
**DTO (Data Transfer Object)** = a separate, plain class holding only what goes over the wire.

**The problem — returning the entity directly:**

```java
class User {                  // maps to the users table
    Long id;
    String email;
    String passwordHash;      // ⚠️ now sent to the browser
    boolean isInternalTestUser;
    Date deletedAt;
}

@GetMapping("/users/{id}")
User getUser(Long id) { return repo.findById(id); }   // ⚠️ leaks all of it
```

Whatever is in the entity **is** your API response. So the client receives `passwordHash` and internal flags, and the day you rename a column, **every client breaks**.

**The fix — a DTO that exposes only what's needed:**

```java
class UserResponse {          // the API's contract
    Long id;
    String email;
}

@GetMapping("/users/{id}")
UserResponse getUser(Long id) {
    User u = repo.findById(id);
    return new UserResponse(u.id, u.email);     // pick the safe fields
}
```

Now the DB and the API can change **independently**: rename `passwordHash` in the entity, and as long as `UserResponse` still has `id` and `email`, no client notices.

**Separate DTOs for in and out**, because they aren't the same shape:

| | Fields |
| --- | --- |
| `CreateUserRequest` | `email`, `password` — **no `id`** (the server makes it) |
| `UserResponse` | `id`, `email` — **no password**, ever |

> **The one-liner:** *"Entities are how I store data, DTOs are how I expose it. Returning entities directly leaks internal fields and ties my API contract to my database schema."*

## 5. ⭐ Versioning

You version because **you can't break existing clients.**

| Strategy | Looks like | Verdict |
| --- | --- | --- |
| **URI versioning** | `/api/v1/users` | **Most common.** Explicit, easy to test in a browser |
| **Header versioning** | `X-API-Version: 1` | Cleaner URLs, harder to debug |
| **Media type** | `Accept: application/vnd.company.v1+json` | Most "correct" REST, rarely used |

**Rules:**
- **Breaking changes go in a new version** — removing a field, renaming it, changing a type
- **Adding** an optional field is **not** breaking, so no new version needed
- Keep the old version alive with a **deprecation timeline**, then remove it

## 6. Filtering, sorting, pagination

**The problem:** `GET /users` on a table with 2 million rows would load all of them into memory, serialise them, and ship megabytes to a client that wanted to show 50. It kills the server, not just the request.

**The fix — the client says exactly what slice it wants**, through query parameters:

```
GET /users?status=active&sort=created_at&order=desc&page=2&limit=50
            └── filter ──┘ └──── sort ─────────────┘ └─ paginate ─┘
```

| Part | Parameter | Does |
| --- | --- | --- |
| **Filtering** | `status=active&type=premium` | Narrows **which** rows (→ SQL `WHERE`) |
| **Sorting** | `sort=created_at&order=desc` | Decides the **order** (→ `ORDER BY`) |
| **Pagination** | `page=2&limit=50` | Returns only that **slice** (→ `LIMIT 50 OFFSET 50`) |

> `page=2&limit=50` means *skip the first 50, give me the next 50.* The database does the slicing — never fetch everything and cut it in Java.

**The response wraps the list with metadata:**

```json
{
  "data": [ ... 50 users ... ],
  "page": 2,
  "limit": 50,
  "totalItems": 320,
  "totalPages": 7
}
```

**Why the metadata matters:** without `totalItems`, the client can't render "Showing 51–100 of 320" or know whether to draw a Next button. It would have to keep requesting pages until one comes back empty.

### ⭐ Is this metadata a DTO?

**Yes — it's a wrapper DTO around the list:**

```java
class PageResponse<T> {
    List<T> data;          // a list of UserResponse DTOs
    int page, limit, totalItems, totalPages;
}

PageResponse<UserResponse> getUsers(...) { ... }
```

**But don't confuse the two meanings of "metadata":**

| Kind | Example | Expose? |
| --- | --- | --- |
| **Pagination metadata** — about the **response** | `page`, `totalItems`, `totalPages` | ✅ Yes — the client needs it to paginate |
| **Entity metadata** — internal DB bookkeeping | `deletedAt`, `rowVersion`, `isInternalTestUser` | ❌ No — this is exactly what §4's DTO filters out |

> **The rule:** expose metadata **about the response**, hide metadata **about your storage**.

## 7. ⭐ Security

| Concern | Answer |
| --- | --- |
| **Authentication** (*who are you?*) | OAuth2, **JWT**, or API keys |
| **Authorization** (*what may you do?*) | Role-based / permission-based access control |
| **Transport** | **HTTPS everywhere** — TLS, no exceptions |
| **Input validation** | Sanitise everything — prevents **SQL injection** and **XSS** |
| **Secrets** | Never in the URL — URLs land in logs and browser history. Use headers or the body |

> **⭐ Authentication vs Authorization** is the most-asked pair here: *"Authentication is proving who you are; authorization is what you're allowed to do once you're in."*

---

## 8. Rate limiting & throttling

- **Rate limiting** — a cap on requests per client per window (e.g. 100/min)
- **Throttling** — slowing down or temporarily blocking a client over the limit
- **Quotas** — longer-term caps (monthly usage per user or app)

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

> **Why:** protects against abuse, scrapers, runaway retry loops, and one noisy client degrading service for everyone.

---

## 9. Quick Recall

- **API = a contract.** Clear nouns, consistent format, **stateless**
- **Verbs:** `GET` read, `POST` create, `PUT` replace, `PATCH` partial, `DELETE` remove
- **Idempotent:** `GET`, `PUT`, `DELETE` ✅ — `POST` ❌
- **`4xx` = client's fault, `5xx` = yours.** `401` = unknown, `403` = known but not allowed
- **DTOs ≠ entities** — don't leak `passwordHash` or tie clients to your schema
- **Versioning:** `/api/v1/...` is the default; **breaking changes only in a new version**, adding a field isn't breaking
- **Always paginate** large lists and return total counts
- **Security:** HTTPS, JWT/OAuth2 for **authn**, roles for **authz**, validate all input, secrets never in the URL
- **`429 Too Many Requests` + `Retry-After`** is the rate-limit response
