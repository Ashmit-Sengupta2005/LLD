# Observer Pattern — Interview Notes

The Observer Pattern lets one object **announce that something changed** and have every interested subscriber notified automatically, without it knowing who they are.

> **Behavioural patterns** are about **how objects talk to each other** — who calls whom, and how control flows. (Creational = how objects are *made*. Structural = how they're *arranged*. Behavioural = how they *interact*.)

---

## 1. The scenario

A YouTube channel uploads a video. **Everyone subscribed must be told** — some by email, some by app notification, some by SMS.

The naive version puts the notifying inside the upload:

```java
class YouTubeChannel {
    public void uploadVideo(String title) {
        System.out.println("Uploading: " + title);

        // channel itself decides WHO gets told and HOW
        sendEmail("rahul@example.com", title);
        sendAppNotification("raj", title);
    }
}
```

> **Analogy:** You don't refresh a channel's page every hour to check for new videos (that's **polling** — wasteful). You hit **Subscribe** once, and *the channel tells you* when something happens. That inversion — *"don't call us, we'll call you"* — is the whole pattern.

---

## 2. The problem

- **Tight coupling** — `YouTubeChannel` knows every subscriber's email and every notification mechanism
- **Can't add a new type** — want SMS? **Edit the channel class** (violates Open/Closed)
- **SRP violation** — the class does two unrelated jobs: uploading *and* notifying
- **Hardcoded subscribers** — nobody can subscribe or unsubscribe while the program runs

The root issue: **the channel knows too much about who's listening.**

---

## 3. The fix: let the channel hold a list of "things that can be notified"

Define what a listener must be able to do, and have the channel keep a list of those:

```java
interface Subscriber {
    void update(String videoTitle);     // "something happened, here it is"
}

class YouTubeChannel {
    private List<Subscriber> subscribers = new ArrayList<>();   // ⭐ THE KEY LINE

    public void uploadVideo(String title) {
        System.out.println("Uploaded: " + title);
        for (Subscriber s : subscribers) s.update(title);       // just broadcast
    }
}
```

The channel now calls `update()` and **that's it**. It has no idea whether a subscriber sends an email, a push, or an SMS — **each subscriber decides that for itself**:

```java
class EmailSubscriber implements Subscriber {
    public void update(String title) { System.out.println("Email: " + title); }
}
class SmsSubscriber implements Subscriber {
    public void update(String title) { System.out.println("SMS: " + title); }
}
```

**Adding SMS = one new class. The channel is never touched.**

> **Observer in one sentence:** a **subject** keeps a list of **observers** and notifies them all when its state changes — without knowing or caring what any of them actually do.

---

## 4. The skeleton

```java
// OBSERVER — what every listener must be able to do
interface Subscriber {
    void update(String videoTitle);
}

// CONCRETE OBSERVERS — each reacts in its own way
class EmailSubscriber implements Subscriber {
    private String email;
    public EmailSubscriber(String email) { this.email = email; }
    public void update(String videoTitle) {
        System.out.println("Email to " + email + ": " + videoTitle);
    }
}

// SUBJECT — what anything observable must support
interface Channel {
    void subscribe(Subscriber s);
    void unsubscribe(Subscriber s);
    void notifySubscribers(String videoTitle);
}

// CONCRETE SUBJECT — holds the list, does the broadcasting
class YouTubeChannel implements Channel {
    private List<Subscriber> subscribers = new ArrayList<>();   // ⭐ list of the INTERFACE

    public void subscribe(Subscriber s)   { subscribers.add(s); }
    public void unsubscribe(Subscriber s) { subscribers.remove(s); }

    public void notifySubscribers(String videoTitle) {
        for (Subscriber s : subscribers) s.update(videoTitle);
    }

    public void uploadVideo(String videoTitle) {     // the business action
        System.out.println("Uploaded: " + videoTitle);
        notifySubscribers(videoTitle);               // then broadcast
    }
}
```

**The direction of knowledge is the whole point:**

```
Subject  →  knows only "List<Subscriber>"      (an interface — nothing concrete)
Observer →  knows nothing about the subject at all
```

Neither side knows the other's real type. That's why both can change independently.

---

## 5. ⭐ The gotcha: unsubscribing *during* a notification

Very common requirement: *"notify me once, then remove me."* So the observer calls `unsubscribe()` inside its own `update()`. You're now **modifying the list while looping over it**. Two things can happen, and which one you get depends on list size:

| Setup | What happens |
| --- | --- |
| 3 subscribers, the 1st removes itself | 💥 `ConcurrentModificationException` |
| 2 subscribers, the 1st removes itself | 😨 **No exception — the 2nd subscriber is silently skipped** |

The second case is **worse**. No crash, no stack trace — a subscriber just never gets notified, and you find out in production.

**Fix — iterate over a copy:**

```java
public void notifySubscribers(String videoTitle) {
    for (Subscriber s : new ArrayList<>(subscribers)) {   // snapshot
        s.update(videoTitle);
    }
}
```

Or use `CopyOnWriteArrayList` for the subscriber list (standard choice for listener lists in Java).

> **Related, same family:** **memory leaks.** The subject holds a strong reference to every observer. An observer that forgets to unsubscribe is **never garbage collected** — the classic Android/Swing listener leak. Always unsubscribe in cleanup/`onDestroy`.

Both of these are genuinely good things to mention unprompted — they show you've actually used it, not just read about it.

## 6. Push vs Pull (how much does the subject send?)

> **Analogy — your phone's notification preview.**
> **Push** = the notification shows the whole message: *"New video: Observer Pattern"*. You already have what you need.
> **Pull** = it just says *"takeUforward posted something"*. You open the app to find out what.

### Push — subject sends the data

```java
interface Subscriber {
    void update(String videoTitle);        // the data comes with the call
}

// subject does:
s.update("Observer Pattern");

// observer does:
public void update(String videoTitle) {
    System.out.println("Email: " + videoTitle);     // already has it
}
```

### Pull — subject sends *itself*, observer fetches what it wants

```java
interface Subscriber {
    void update(Channel channel);          // just "something changed on me"
}

// subject does:
s.update(this);

// observer does:
public void update(Channel channel) {
    String title = channel.getLatestVideo();        // goes and gets it
    int duration = channel.getDuration();           // takes only what IT needs
}
```

### Why pull exists at all

Say the channel later publishes **title + duration + thumbnail + description**, and different observers need different pieces:

- The **email** subscriber wants title + description
- The **app** subscriber wants title + thumbnail
- The **analytics** subscriber wants only duration

With **push**, the signature must carry everything for everyone:

```java
void update(String title, int duration, String thumbnail, String description);
```

Now **every observer is forced to accept all four params** even if it uses one. Worse — add a fifth field tomorrow and you must **edit every single observer class** just to change the signature. The thing the pattern was supposed to prevent.

With **pull**, the signature never changes. Add a new field, add a getter, and only the observers that care touch it.

### The trade-off

| | **Push** | **Pull** |
| --- | --- | --- |
| Signature | `update(videoTitle)` | `update(channel)` |
| Observer knows the subject? | **No** — only gets a `String`. Fully decoupled | **Yes** — must know `Channel` and its getters |
| Adding a new field | Changes the interface → **edits every observer** | Costs nothing — add a getter |
| Data sent | Everything, to everyone | Only what each observer asks for |
| Extra calls | None | Observer calls back into the subject |

> **Rule of thumb:** small, fixed payload that everyone wants → **push** (simpler, keeps observers ignorant of the subject). Rich or growing state where observers need different slices → **pull**.

Our example is **push** — one `String`, everyone wants it. That's the common default, and what you'd write unless asked otherwise.

## 7. ⭐ Observer vs Pub/Sub (the follow-up that separates people)

| | **Observer** | **Pub/Sub (Kafka, RabbitMQ)** |
| --- | --- | --- |
| Who connects them | Subject holds observers **directly** | A **broker** sits in the middle |
| Do they know each other? | Subject holds a reference to each observer | Publisher and subscriber **never meet** |
| Where it runs | **One process**, same memory | **Across machines / services** |
| Timing | **Synchronous** — upload blocks until all are notified | **Asynchronous** — fire and forget |
| If a listener is down | Everything breaks or blocks | Broker queues it for later |

> **Say this:** *"Observer is the in-process version — the subject holds direct references and notifies synchronously. Once you need it across services, with retries and durability, you move to a message broker. Same idea, different scale."*

**This is also the honest answer to "when does Observer break down?"** A celebrity with 10M followers going live cannot be a synchronous `for` loop. Observer is for **tens or hundreds** of observers in one process — beyond that you need an event-driven architecture.

## 8. Where you've already used it

| System | Subject | Observers |
| --- | --- | --- |
| **UI listeners** (`addActionListener`, `onClick`) | Button | Registered handlers |
| **Spring `ApplicationEvent`** | `ApplicationEventPublisher` | `@EventListener` methods |
| **RxJava / Reactive Streams** | `Observable` | `Subscriber` |
| **Stock tickers** | Price feed | Charts, alerts, watchlists |
| **File watchers** (`WatchService`) | Directory | Compilers, sync tools |

> Note: Java's built-in `java.util.Observable` / `Observer` are **deprecated since Java 9** (not an interface, not serializable, no ordering guarantees). Always hand-roll it — which is what interviewers expect anyway.

---

## 9. Pros / Cons

| Pros | Cons |
| --- | --- |
| **Loose coupling** — subject knows only an interface | **Notification order isn't guaranteed** — don't depend on it |
| **Open/Closed** — new observer type = new class only | **Memory leaks** if observers never unsubscribe |
| **Runtime subscribe/unsubscribe** | **Synchronous** — one slow observer blocks the whole broadcast |
| Observers are **reusable** across subjects | **Hard to debug** — indirect calls, no visible call site |

---

## 10. Interview Quick Recall

- **Type:** Behavioural
- **Core idea:** Subject keeps a `List<Observer>` and calls `update()` on all of them when state changes
- **Roles:** Subject (interface) + Concrete Subject (holds the list) + Observer (interface) + Concrete Observers
- **Defines:** a **one-to-many** dependency
- **Key line:** `private List<Subscriber> subscribers;` — list of the **interface**, so the subject stays ignorant of concrete types
- **Trigger phrase:** *"when X happens, notify all the Y's"*
- **When NOT to use:** Millions of observers, or notification timing/ordering must be controlled → use a message broker instead
- **Follow-up 1:** *"Observer vs Pub/Sub?"* → Observer is in-process, direct references, synchronous. Pub/Sub adds a broker, works across services, is async (§7)
- **Follow-up 2:** *"Problems in production?"* → **Memory leaks** (observer never unsubscribes) and **`ConcurrentModificationException`** when an observer unsubscribes during notify — fix by iterating over a copy (§5)
- **Follow-up 3:** *"Push or pull?"* → Push sends the data, pull sends the subject so observers fetch what they need (§6)
