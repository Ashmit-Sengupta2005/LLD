# Strategy Pattern — Interview Notes

## 1. The scenario

Uber matches a rider to a driver. But **"matching" means different things in different situations**:

```
Normal city ride   →  nearest available driver
Airport pickup     →  FIFO queue (first driver in line)
Peak hours         →  surge-zone priority
```

One job, several algorithms, and which one applies is decided **while the app is running**.

The naive version is one method full of branches:

```java
class RideMatchingService {
    public void matchRider(String location, String matchingType) {
        if (matchingType.equals("NEAREST")) {
            // nearest-driver logic
        } else if (matchingType.equals("AIRPORT_QUEUE")) {
            // FIFO queue logic
        } else if (matchingType.equals("SURGE_PRIORITY")) {
            // surge logic
        }
    }
}
```

> **Analogy:** Google Maps. Same request — "get me from A to B" — but **drive**, **walk**, and **cycle** use completely different route algorithms. You pick the mode with a tap; the app doesn't become a different app.

---

## 2. The problem

- **Every new rule means editing this class** — VIP matching? Add another `else if` (violates Open/Closed)
- **The method keeps growing** — 3 branches become 10, all in one place
- **Can't test one algorithm alone** — the logic is trapped inside a method with everything else
- **Can't reuse** — another service wanting "nearest driver" must copy the code
- **Two jobs in one class** — deciding *which* algorithm and *being* every algorithm

---

## 3. The fix: one class per branch, behind a common interface

```java
interface MatchingStrategy {
    void match(String riderLocation);
}

class NearestDriverStrategy  implements MatchingStrategy { ... }
class AirportQueueStrategy   implements MatchingStrategy { ... }
class SurgePriorityStrategy  implements MatchingStrategy { ... }
```

The service now **holds one** of them and just delegates:

```java
class RideMatchingService {
    private MatchingStrategy strategy;          // ⭐ interface type

    public void setStrategy(MatchingStrategy strategy) { this.strategy = strategy; }

    public void matchRider(String location) {
        strategy.match(location);               // no if-else anywhere
    }
}
```

And it can be swapped **on the same object, at runtime**:

```java
service.matchRider("Downtown");                      // nearest driver
service.setStrategy(new SurgePriorityStrategy());    // peak hour hits
service.matchRider("Downtown");                      // now surge priority
```

> **Strategy in one sentence:** pull each branch of an if-else into its own class behind a shared interface, so the behaviour can be **swapped at runtime** without touching the class that uses it.

---

## 4. The skeleton

```java
// STRATEGY — the contract every algorithm satisfies
interface MatchingStrategy {
    void match(String riderLocation);
}

// CONCRETE STRATEGY — one per algorithm (each was an if-else branch)
class NearestDriverStrategy implements MatchingStrategy {
    public void match(String riderLocation) {
        System.out.println("Nearest driver to " + riderLocation);
    }
}

// CONTEXT — holds a strategy, delegates to it, contains no algorithm itself
class RideMatchingService {
    private MatchingStrategy strategy;                      // ⭐ THE KEY LINE

    public RideMatchingService(MatchingStrategy strategy) { // constructor injection
        this.strategy = strategy;
    }

    public void setStrategy(MatchingStrategy strategy) {    // runtime swapping
        this.strategy = strategy;
    }

    public void matchRider(String location) {
        strategy.match(location);
    }
}
```

**Three roles:** Strategy (interface) + Concrete Strategies (the algorithms) + Context (holds one and delegates).

---

## 5. ⭐ "But doesn't the if-else just move somewhere else?"

**Yes — and this is a fair objection worth answering properly.** *Somebody* still has to choose:

```java
if (location.contains("Airport")) service.setStrategy(new AirportQueueStrategy());
else if (isSurgeHour())           service.setStrategy(new SurgePriorityStrategy());
else                              service.setStrategy(new NearestDriverStrategy());
```

The branching didn't vanish. But it **changed character**, and that's the real win:

| Before | After |
| --- | --- |
| if-else **mixed with** the algorithms | if-else **only picks**; algorithms live elsewhere |
| Grows **every time** any algorithm changes | Only grows when a **new** algorithm is added |
| In the middle of business logic | In **one** place — a factory, config, or DI container |
| Algorithms can't be tested alone | Each strategy is **independently testable** |

And it often disappears entirely — a `Map<String, MatchingStrategy>` lookup, a config file, or Spring injecting the right bean.

> **Say this:** *"The selection logic still exists, but it's isolated to one place and only changes when a new strategy is added. The algorithms themselves are now closed for modification."*

---

## 6. ⭐⭐ Strategy vs State (the question you WILL get)

**Structurally identical** — context + interface + implementations. Like Proxy vs Decorator, the difference is intent:

| | **Strategy** | **State** |
| --- | --- | --- |
| **Who picks?** | **The client** — from outside | **The object itself** — from inside |
| **Do implementations know each other?** | **No** — totally independent | **Yes** — each one decides the next state |
| **Changes on its own?** | No — stays until you swap it | **Yes** — transitions as events occur |
| **Models** | *How* to do something | *What stage* something is in |
| **Example** | Payment method, sort algorithm | Order: Placed → Shipped → Delivered |

> **The test:** *Does the object switch its own behaviour, or does someone outside switch it?*
> **Outside picks → Strategy.** **Switches itself → State.**

---

## 7. In modern Java, a strategy is often just a lambda

`MatchingStrategy` has exactly one abstract method, so it's a **functional interface** — no class needed:

```java
service.setStrategy(loc -> System.out.println("Random driver near " + loc));
```

This is why you rarely see the full ceremony in modern code — `Comparator`, `Runnable`, `Predicate` are all strategies you already use as lambdas.

> **Caveat:** use a real class when the strategy has **state, dependencies, or more than a few lines**. Lambdas are for small, stateless logic.

---

## 8. Where you've already used it

| System | Strategy interface | Strategies |
| --- | --- | --- |
| **`Collections.sort(list, comparator)`** | `Comparator` | Any sort order you pass in |
| **Spring Security** | `PasswordEncoder` | BCrypt, Argon2, PBKDF2 |
| **Payment checkout** | `PaymentMethod` | Card, UPI, wallet, COD |
| **Compression tools** | `Compressor` | ZIP, GZIP, RAR |
| **Google Maps** | `RouteStrategy` | Drive, walk, cycle, transit |

> `Comparator` is the cleanest example — `sort()` doesn't know *how* you want things ordered, you hand it the algorithm.

---

## 9. Pros / Cons

| Pros | Cons |
| --- | --- |
| **Kills if-else chains** — each branch becomes a class | **Many small classes** (lambdas help) |
| **Open/Closed** — new algorithm = new class, nothing edited | **Client must know** which strategies exist |
| **Runtime swapping** on the same object | **Overkill for 2 fixed cases** that never change |
| Each algorithm is **testable and reusable** alone | Selection logic still lives **somewhere** (§5) |
| **Composition over inheritance** — swap behaviour, don't subclass | Extra indirection for very simple logic |

---

## 10. Interview Quick Recall

- **Type:** Behavioural
- **Core idea:** Encapsulate each algorithm in its own class behind one interface; the context holds one and delegates
- **Roles:** Strategy (interface) + Concrete Strategies + Context
- **Key line:** `private MatchingStrategy strategy;` — the context holds the **interface**, so it never knows which algorithm it has
- **Trigger phrase:** *"several ways to do the same thing"* / a growing `if-else` or `switch` on a type string
- **When NOT to use:** Only two cases that will never change — an if-else is genuinely simpler
- **Follow-up 1:** *"Strategy vs State?"* → Identical structure. **Client** picks the strategy; the object picks its **own** next state. States know each other, strategies don't (§6)
- **Follow-up 2:** *"Doesn't the if-else just move?"* → Yes, but it only **selects** now — it's isolated and only changes when a new strategy is added (§5)
- **Follow-up 3:** *"Real example?"* → `Comparator` in `Collections.sort()`, or Spring's `PasswordEncoder`
