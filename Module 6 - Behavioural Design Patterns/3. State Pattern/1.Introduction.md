# State Pattern — Interview Notes

The State Pattern gives every state of an object **its own class**, and lets the object **delegate its behaviour to whichever state it's currently in** — so the object's behaviour changes as its state changes, with no `if` and no `switch`.

---

## 1. The scenario

A food delivery app tracks one order through its lifecycle:

```
ORDER_PLACED  →  PREPARING  →  OUT_FOR_DELIVERY  →  DELIVERED
      ↓              ↓
  CANCELLED      CANCELLED            (and nowhere else)
```

The rules differ at every stage: you can cancel a placed order, you **cannot** cancel one that's already on a bike, and a delivered order can do neither.

The obvious way is to keep the state in a field and branch on it:

```java
class Order {
    private String state = "ORDER_PLACED";

    public void cancel() {
        if (state.equals("ORDER_PLACED") || state.equals("PREPARING")) {
            state = "CANCELLED";
            System.out.println("Order has been cancelled.");
        } else {
            System.out.println("Cannot cancel the order now.");
        }
    }

    public void next() {
        switch (state) {
            case "ORDER_PLACED":     state = "PREPARING";        break;
            case "PREPARING":        state = "OUT_FOR_DELIVERY"; break;
            case "OUT_FOR_DELIVERY": state = "DELIVERED";        break;
            default: System.out.println("No next state from: " + state);
        }
    }
}
```

It works. Then the product team says: *"add a `DRIVER_ASSIGNED` stage, plus live tracking, refunds and rating."*

---

## 2. The problem

- **Every new action gets its own copy of the same switch** — `track()`, `requestRefund()`, `rateOrder()`, `contactDriver()` each need to know all five states. That's the real pain, not the one switch you can see
- **Every new state means editing every existing method** — insert `DRIVER_ASSIGNED` and you touch `cancel()`, `next()`, `track()`, … (violates Open/Closed)
- **The rules for one state are scattered** — ask *"what can I do while OUT_FOR_DELIVERY?"* and you must read every method in the class to find out
- **The state is a `String`** — `"PREPARNG"` compiles fine and silently falls to `default`. The compiler can't help you
- **Illegal transitions are prevented only by vigilance** — nothing stops `state = "DELIVERED"` straight from `"ORDER_PLACED"`
- **Three jobs in one class** — `Order` holds the data, performs the actions, **and** owns the entire transition table

> The root cause: **the state is being stored as data when it should be behaviour.** A `String` can't refuse a method call. An object can.

---

## 3. The fix: make each state a class, and delegate to it

```java
interface OrderState {
    void next(OrderContext context);     // ⭐ gets the context, so it can transition it
    void cancel(OrderContext context);
    String getStateName();
}
```

Each state class answers *every* question, but only **for itself**:

```java
class OrderPlacedState implements OrderState {
    public void next(OrderContext ctx)   { ctx.setState(new PreparingState()); }
    public void cancel(OrderContext ctx) { ctx.setState(new CancelledState()); }
    public String getStateName()         { return "ORDER_PLACED"; }
}

class OutForDeliveryState implements OrderState {
    public void next(OrderContext ctx)   { ctx.setState(new DeliveredState()); }
    public void cancel(OrderContext ctx) { System.out.println("Cannot cancel. Order is on its way."); }
    public String getStateName()         { return "OUT_FOR_DELIVERY"; }
}
```

The context holds **one state object** and forwards everything to it:

```java
class OrderContext {
    private OrderState currentState = new OrderPlacedState();   // ⭐ interface type

    public void setState(OrderState state) { this.currentState = state; }

    public void next()   { currentState.next(this);   }         // pure delegation
    public void cancel() { currentState.cancel(this); }

    public String getCurrentState() { return currentState.getStateName(); }
}
```

`OrderContext` has **no `if`, no `switch`, no `String` state.** It doesn't know the order of the lifecycle, and it never will.

> **Analogy:** a traffic light. Red, amber and green aren't *values* the light compares against — each one **is** a mode with its own rules and its own successor. The light doesn't decide what comes next; the current colour does.

---

## 4. The roles

| Role | In our example | Job |
| --- | --- | --- |
| **Context** | `OrderContext` | Holds the current state, delegates every call to it, owns the order's data |
| **State** | the `OrderState` interface | The contract — every action the context can receive |
| **Concrete State** | `OrderPlacedState`, `DeliveredState` | Implements all actions **for one stage**, and decides what comes next |
| **Client** | `main()` | Calls `next()` / `cancel()` on the context; never touches a state object |

> **Important:** the client talks only to the context. It never sees a state class, and it never asks *which* state is active before acting — it just acts, and the current state decides what that means.

---

## 5. ⭐ The real insight: the matrix gets flipped

Every state machine is a grid of **states × actions**:

| | `next()` | `cancel()` | `track()` |
| --- | --- | --- | --- |
| **ORDER_PLACED** | → PREPARING | → CANCELLED | "not picked up yet" |
| **PREPARING** | → OUT_FOR_DELIVERY | → CANCELLED | kitchen status |
| **OUT_FOR_DELIVERY** | → DELIVERED | ✗ refuse | live map |
| **DELIVERED** | ✗ refuse | ✗ refuse | "delivered at 8:42" |
| **CANCELLED** | ✗ refuse | ✗ refuse | — |

- **Naive** = one method per **column**. Each method contains an entire column, so the grid is sliced vertically and every slice repeats the same list of states.
- **State Pattern** = one class per **row**. Each class contains an entire row, so everything true about one stage sits in one file.

That flip is the whole pattern. It also tells you exactly what it costs you:

| Change | Naive | State Pattern |
| --- | --- | --- |
| **New state** (a row) | Edit **every** method | **New class**, nothing else touched ✓ |
| **New action** (a column) | One new method | Edit the **interface + every state class** ✗ |

> **Say this in an interview:** *"State is open for new states and closed for modification — but adding a new **action** means touching every state class. It's the right trade when states grow faster than actions, which is the usual case for a workflow."*

Mitigation: give the interface `default` methods that refuse, so a state only overrides the actions it actually allows.

---

## 6. ⭐ Illegal transitions stop being possible

This is the benefit people forget to mention.

In the naive version, nothing structurally prevents a jump from `ORDER_PLACED` to `DELIVERED` — only the care of whoever wrote the branches. In the State version, **the only way to reach `DeliveredState` is through `OutForDeliveryState.next()`.** The graph of legal transitions is encoded in the code itself, not in a list of conditions you hope is complete.

And refusal gets a home: `OutForDeliveryState.cancel()` just says no. There's no shared method where someone might forget to add that case.

---

## 7. ⭐⭐ Who owns the transitions?

Two legitimate designs, and interviewers probe this:

**(a) Decentralised — each state names its successor** *(what we did above, and what most tutorials show)*

```java
public void next(OrderContext ctx) { ctx.setState(new PreparingState()); }
```

*Pro:* the whole rule for a stage lives in one file.
*Con:* **states know each other.** Insert `DriverAssignedState` between Preparing and OutForDelivery and you **must edit `PreparingState.next()`** — so the "no existing code is modified" claim isn't quite true. You still only touch one neighbour instead of five methods, which is the real improvement.

**(b) Centralised — the context owns a transition table**

```java
Map<Class<?>, OrderState> transitions = Map.of(
    OrderPlacedState.class, new PreparingState(), ...
);
```

*Pro:* states stay ignorant of one another; the whole lifecycle is readable in one place.
*Con:* a central map is back — closer to the switch you were escaping.

> Rule of thumb: **(a)** for a short, stable lifecycle. **(b)** or a real state-machine library when the graph is large, configurable, or must be visualised.

---

## 8. ⭐ States should be stateless — so make them singletons

Notice the state classes have **no fields**. All the data — items, address, payment — lives in the **context**; the state objects carry only *behaviour*. So `new PreparingState()` on every transition allocates a fresh object identical to the last one.

```java
class PreparingState implements OrderState {
    public static final PreparingState INSTANCE = new PreparingState();
    private PreparingState() {}
    // ...
}
ctx.setState(PreparingState.INSTANCE);     // one object shared by every order
```

This is **Flyweight applied to State**, and it's how real systems do it. It also enforces a useful discipline: *the moment a state class wants a field, that data probably belongs in the context.*

In Java there's an even tighter version — an `enum` with abstract methods gives you one class, singleton instances and exhaustive `switch` checking for free:

```java
enum OrderState {
    ORDER_PLACED { void next(OrderContext c) { c.setState(PREPARING); } },
    PREPARING    { void next(OrderContext c) { c.setState(OUT_FOR_DELIVERY); } };
    abstract void next(OrderContext c);
}
```

> Worth mentioning for a small, fixed lifecycle. Use real classes once a state needs dependencies injected.

## 9. ⭐⭐ State vs Strategy (the question you WILL get)

**Structurally identical** — a context holding an interface, with several implementations. The difference is entirely intent:

| | **State** | **Strategy** |
| --- | --- | --- |
| **Who picks?** | **The object itself**, from inside | **The client**, from outside |
| **Do implementations know each other?** | **Yes** — each decides the next one | **No** — totally independent |
| **Changes on its own?** | **Yes** — transitions as events occur | No — stays until you swap it |
| **Models** | *What stage* something is in | *How* to do something |
| **The work itself** | Each state does a **different job** — `cancel()` means something different in every state, and some refuse outright | Every strategy does the **same job** a different way — same goal, different route, often the same result |
| **Swapping one for another** | Changes **what happens next** | Changes **how one job is done** |
| **Example** | Order: Placed → Preparing → Delivered | `Comparator`, `PaymentMethod`, route algorithm |

> **The test:** *Does the object switch its own behaviour, or does someone outside switch it?*
> **Switches itself → State.** **Outside picks → Strategy.**

A second, sharper test: **remove one implementation.** Lose a strategy and you lose one way of doing a job. Lose a state and the lifecycle is **broken** — something now transitions into nothing. Strategies are alternatives; states are a graph.

*(Cross-reference: §6 of the Strategy notes — same table, from the other side.)*

## 10. Where you've already used it

| System | States | Context |
| --- | --- | --- |
| **`Thread.State`** | NEW → RUNNABLE → BLOCKED / WAITING → TERMINATED | The thread |
| **TCP connection** | LISTEN, SYN_SENT, ESTABLISHED, CLOSE_WAIT, … | The socket |
| **Vending machine** | NoCoin, HasCoin, Dispensing, SoldOut | The machine |
| **Media player** | Playing, Paused, Stopped — the *same* play button does three different things | The player |
| **Order / payment / ticket workflows** | Placed, Paid, Shipped, Refunded | The order |
| **Spring Statemachine, AWS Step Functions** | Declared states and transitions | The engine |

> The media player is the cleanest everyday example: one button, and what it does depends entirely on which state the player is in.

---

## 11. Pros / Cons

| Pros | Cons |
| --- | --- |
| **Kills the repeated switch** — the state check disappears from every method | **Class explosion** — one class per state |
| **Everything about one stage in one file** — easy to read and to test | **New action = edit every state class** (§5) |
| **Illegal transitions become structurally impossible** (§6) | **States get coupled to their successors** in the common design (§7) |
| **Open/Closed for new states** — add a class, don't edit methods | **Overkill for 2–3 states** with one action — an enum + switch is clearer |
| State objects are **stateless and shareable** (§8) | Transition logic is **spread out**; no single file shows the whole lifecycle |
| Replaces a stringly-typed field with **compiler-checked types** | Extra indirection on every call |

---

## 12. Interview Quick Recall

- **Type:** Behavioural
- **Core idea:** Give each state its own class and delegate to the current one, so behaviour changes with state and the conditionals vanish
- **Roles:** Context (holds current state + the data) + State interface + Concrete States (one per stage) + Client
- **Key line:** `currentState.next(this);` — the context delegates and **passes itself**, so the state can transition it
- **Trigger phrase:** *"lifecycle"*, *"workflow"*, *"status field"*, *"it depends what stage it's in"*, or the same `switch (status)` appearing in method after method
- **When NOT to use:** Two or three states with one action, and a lifecycle that won't grow — an `enum` + `switch` is honestly simpler
- **Follow-up 1:** *"State vs Strategy?"* → Identical structure. The object picks its **own** next state; the **client** picks a strategy. States know each other, strategies don't (§9)
- **Follow-up 2:** *"Doesn't this just move the switch?"* → No — the state check disappears entirely, because dynamic dispatch **is** the switch. What remains is each state naming its successor (§7)
- **Follow-up 3:** *"Is it really Open/Closed?"* → For new **states**, yes. For a new **action**, you edit every state class; and inserting a state means editing its neighbour (§5, §7)
- **Follow-up 4:** *"Where does the order's data live?"* → In the **context**. States are behaviour-only, and should be singletons (§8)
- **Follow-up 5:** *"Real example?"* → `Thread.State`, TCP sockets, or any order/payment workflow
