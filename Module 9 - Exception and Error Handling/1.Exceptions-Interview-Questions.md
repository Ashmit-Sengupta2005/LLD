# Exceptions — The Questions That Actually Get Asked

> Ordered by how often they come up. The first four cover most interviews.

---

## 0. The hierarchy (you need this to answer everything else)

```
            Throwable
           /         \
      Error           Exception
   (don't catch)     /         \
                 RuntimeException   everything else
                   (UNCHECKED)         (CHECKED)
```

- **`Error`** — JVM-level, unrecoverable: `OutOfMemoryError`, `StackOverflowError`. **You don't catch these**
- **`RuntimeException`** and its children → **unchecked**
- **Everything else under `Exception`** → **checked**

---

## 1. ⭐⭐⭐ Checked vs Unchecked — the #1 question

| | **Checked** | **Unchecked** |
| --- | --- | --- |
| **Extends** | `Exception` (not `RuntimeException`) | `RuntimeException` |
| **Compiler forces handling?** | ✅ Yes — `try/catch` or `throws`, or it won't compile | ❌ No |
| **Means** | Something external failed; recoverable | A **bug in your code** |
| **Examples** | `IOException`, `SQLException`, `FileNotFoundException` | `NullPointerException`, `IllegalArgumentException`, `ArrayIndexOutOfBoundsException` |

> **How to answer:** *"Checked exceptions are checked at compile time — the compiler forces you to handle or declare them, and they represent recoverable external problems like a missing file. Unchecked ones extend `RuntimeException`, aren't enforced by the compiler, and usually mean a programming bug — like dereferencing null."*

---

## 2. ⭐⭐⭐ `throw` vs `throws`

| `throw` | `throws` |
| --- | --- |
| **Actually fires** an exception | **Declares** that a method might throw one |
| Inside the method body | In the method signature |
| One object at a time | Can list several, comma-separated |
| `throw new InsufficientBalanceException("...")` | `void withdraw(int amt) throws IOException` |

```java
void withdraw(double amt) throws SeatUnavailableException {   // declares
    if (amt > balance)
        throw new InsufficientBalanceException("Low balance: " + balance);   // fires
}
```

## 3. ⭐⭐⭐ `final` vs `finally` vs `finalize`

Pure trick question, asked constantly, takes 10 seconds:

- **`final`** — a keyword. Constant variable, non-overridable method, non-extendable class
- **`finally`** — a block that **always runs** after try/catch, used for cleanup
- **`finalize()`** — an old `Object` method the GC called before collecting. **Deprecated, never use it**

> They're unrelated — they just look similar. That's the whole question.

---

## 4. ⭐⭐ Does `finally` always run?

**Yes — even if `try` has a `return`.** The return value is computed, `finally` runs, then the method returns.

**Two exceptions to that:**
- `System.exit(0)` inside the try
- The JVM crashes / the thread is killed

> **The follow-up:** *"What if `finally` also returns?"* → **It overrides the try's return**, silently swallowing exceptions too. It compiles, it's legal, and it's **bad practice** — say that.

---

## 5. ⭐⭐ Catch order & multi-catch

```java
try {
    withdraw(5000);
} catch (InsufficientBalanceException | IllegalStateException e) {   // multi-catch
    System.out.println(e.getMessage());
} finally {
    // cleanup
}
```

**⭐ Child must be caught before parent.** Putting `catch (Exception e)` first makes the later blocks **unreachable → compile error**.

In multi-catch the types must be **unrelated** (no parent/child pair), and `e` is implicitly `final`.

---

## 6. ⭐⭐ Custom exceptions — checked or unchecked?

```java
// unchecked — the default choice
class InsufficientBalanceException extends RuntimeException {
    InsufficientBalanceException(String msg) { super(msg); }
}

// checked — caller is FORCED to handle it
class SeatUnavailableException extends Exception {
    SeatUnavailableException(String msg) { super(msg); }
}
```

> **Say this:** *"I default to **unchecked** for custom exceptions — checked ones force `throws` declarations up the entire call chain and clutter every signature. I'd use a checked exception only when the caller can genuinely recover and I want to force them to deal with it."*

That's the answer interviewers want in an LLD round.

## 7. ⭐ try-with-resources

```java
try (BufferedReader br = new BufferedReader(new FileReader("f.txt"))) {
    return br.readLine();
}   // br.close() called automatically, even on exception
```

- Replaces the old `finally { if (x != null) x.close(); }` boilerplate
- The resource must implement **`AutoCloseable`**
- Resources close in **reverse order** of creation

> **Can you have `try` without `catch`?** → **Yes:** `try-finally`, and try-with-resources (which needs neither).

## 8. ⭐ Exceptions you should be able to name on the spot

| Exception | Cause |
| --- | --- |
| `NullPointerException` | Using a null reference |
| `ArrayIndexOutOfBoundsException` | Bad index |
| `ClassCastException` | Invalid cast |
| `NumberFormatException` | `Integer.parseInt("abc")` |
| `IllegalArgumentException` | Invalid argument passed in |
| `ConcurrentModificationException` | Modifying a collection while iterating it |
| `StackOverflowError` | Infinite recursion (an **Error**, not an Exception) |
| `OutOfMemoryError` | Heap exhausted (an **Error**) |

---

## 9. Best practices (one-liners, often the closing question)

- **Never swallow an exception** — `catch (Exception e) {}` is the worst thing in the file
- **Catch specific exceptions**, not `Exception` or `Throwable`
- **Never catch `Error`** — you can't recover from it
- **Clean up in `finally`** or use try-with-resources
- **Don't use exceptions for control flow** — they're expensive and hide intent

---

## 10. Quick Recall

- **Hierarchy:** `Throwable` → `Error` (don't catch) + `Exception` → `RuntimeException` (unchecked) vs the rest (checked)
- **Checked** = compiler-enforced, external/recoverable. **Unchecked** = `RuntimeException`, your bug
- **`throw`** fires one; **`throws`** declares in the signature
- **`final` / `finally` / `finalize`** — unrelated; know the one-liners
- **`finally` always runs** except `System.exit()` / JVM death; a `return` in `finally` overrides try's
- **Catch child before parent**, or it won't compile
- **Custom exceptions → extend `RuntimeException`** unless you want to force the caller to handle it
- **try-with-resources** needs `AutoCloseable`; `try` without `catch` is legal

---

> **Don't waste time on:** `finalize()` internals, exception chaining APIs, `assert`, writing your own `Throwable` subclass, or memorising the full JDK exception tree. They don't come up at this level.
