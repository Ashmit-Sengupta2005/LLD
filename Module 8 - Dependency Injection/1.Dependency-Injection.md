# Dependency Injection — Interview Notes

> **Say this first:** *"Dependency Injection means a class doesn't create the objects it needs — somebody gives them to it from outside. So instead of `OrderService` doing `new RazorpayPayment()` inside itself, we pass the payment service into its constructor. The class just says what it needs; the caller decides what to actually hand it. That way we can swap Razorpay for Stripe, or pass a fake one in tests, without changing `OrderService` at all."*

---

## 1. The problem

```java
class OrderService {
    private PaymentService payment = new RazorpayPayment();   // ⭐ creates its own dependency
    private InventoryService inventory = new InventoryService();

    public void checkout(Order order) {
        inventory.blockItems(order);
        payment.process(order);
    }
}
```

**What's wrong:**

- **Tightly coupled** — `OrderService` is welded to `RazorpayPayment`. Switching to Stripe means editing this class
- **Untestable** — you can't unit-test `checkout()` without hitting a **real payment API**
- **Doesn't scale** — every new provider means modifying `OrderService` again

> **The root cause:** the class is **creating** its own dependencies instead of being **given** them.

---

## 2. What is Dependency Injection?

**A dependency** = any object a class needs to do its job (here: payment, inventory).

> **Dependency Injection** = a class **receives** its dependencies from outside instead of creating them itself.

**Analogy:** a chef doesn't grow their own tomatoes — a supplier delivers them. The chef just cooks.

---

## 3. The fix

```java
class OrderService {
    private final PaymentService payment;        // ⭐ an interface, not a concrete class

    public OrderService(PaymentService payment) {   // injected from outside
        this.payment = payment;
    }

    public void checkout(Order order) {
        payment.process(order);
    }
}

// Main — the only place where "new" appears
PaymentService payment = new RazorpayPayment();     // swap to StripePayment anytime
OrderService service = new OrderService(payment);
```

**What this bought us:**
- **Loose coupling** — `OrderService` knows the *interface*, never the implementation
- **Testable** — pass a **mock** `PaymentService` in tests; no real API calls
- **Scalable** — new provider = new class; `OrderService` is never touched

---

## 4. ⭐ The SOLID connection (asked almost every time)

- **D — Dependency Inversion Principle:** high-level modules depend on **abstractions**, not concrete classes. DI is *how* you achieve DIP
- **O — Open/Closed Principle:** open to extension (add `StripePayment`), closed to modification (`OrderService` unchanged)

> **⭐ DIP is the principle; DI is the technique that implements it.** Don't mix the two names up — that's the trap.

---

## 5. The three types

| Type | How | Notes |
| --- | --- | --- |
| **Constructor Injection** ⭐ | Passed into the constructor | **The default choice.** Dependencies are `final` (immutable), object is never half-built, easy to test |
| **Setter Injection** | Passed via a setter after creation | Mutable, good for **optional** dependencies. Risk: forget the setter → `NullPointerException` |
| **Interface Injection** | Class implements an interface with an `inject()` method | **Rarely used.** Forces every implementing class to write the method even if it doesn't need it |

```java
// Constructor Injection — know this one
public OrderService(PaymentService payment) { this.payment = payment; }

// Setter Injection
public void setPayment(PaymentService payment) { this.payment = payment; }
```

> **If asked "which do you prefer?"** — **Constructor injection**: it guarantees the object is fully built, lets the field be `final` (thread-safe), and makes missing dependencies a **compile-time** error instead of a runtime crash.

---

## 6. When to use it — and when not to

**Use DI when you see:**

| Symptom | Fix |
| --- | --- |
| Classes using `new` for their collaborators | Constructor injection |
| Can't mock a service in tests | Inject it via an interface |
| Adding a feature breaks old code | Depend on an abstraction |
| Lots of `if`/`switch` to pick a service type | Inject the right implementation |

**Skip DI for:** tiny classes with no dependencies, **static utility classes** (`StringUtils`, date helpers), and one-off scripts. The overhead isn't worth it.

---

## 7. Framework DI (Spring)

Doing it by hand means wiring everything in `main()`. Frameworks do it for you:

```java
@Service
class OrderService {
    private final PaymentService payment;

    @Autowired                                    // Spring injects it automatically
    public OrderService(PaymentService payment) {
        this.payment = payment;
    }
}
```

Spring's **IoC container** creates the objects and injects them, so you write no wiring code.

> **Inversion of Control (IoC)** = the framework controls object creation, not you. **DI is one form of IoC** — another likely follow-up.

---

## 8. Quick Recall

- **DI** = a class **receives** dependencies instead of creating them (`new`)
- **Fixes:** tight coupling, untestable code, and changes rippling across classes
- **Depend on interfaces, not concrete classes** — that's what makes swapping possible
- **Three types:** Constructor ⭐ (default), Setter (optional deps), Interface (rare)
- **Constructor injection wins** — immutable, `final`, never partially built
- **DIP is the principle, DI is the technique**; DI also supports **OCP**
- **Spring** does it with `@Autowired` / its **IoC container**; DI is a form of **IoC**
- **Skip it** for utility classes, tiny classes, and throwaway scripts
