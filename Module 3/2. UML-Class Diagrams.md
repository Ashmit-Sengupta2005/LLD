# UML Class Diagrams — LLD Interview Notes

## 1. What is a UML Class Diagram?

A UML (Unified Modeling Language) class diagram visually represents the **static structure** of a software system: its classes, interfaces, attributes, methods, and relationships.

**Why it is useful**

- Helps communicate and understand a design before or during implementation.
- Makes class responsibilities and relationships clear.
- Helps identify design issues early.
- Useful for documenting a system for developers and teammates.

For LLD interviews, focus mainly on **class diagrams and class relationships** rather than memorizing every UML diagram type.

## 2. Class Diagram Notation

A class is usually drawn as a rectangle with three compartments:

1. **Top:** Class name
2. **Middle:** Attributes (data/fields)
3. **Bottom:** Operations (methods)

Example:

```text
-------------------------
|         Person        |
-------------------------
| - age: int             |
-------------------------
| + isAdult(age: int):   |
|   boolean              |
-------------------------
```

### Visibility markers

| Symbol | Meaning                  |
| ------ | ------------------------ |
| `+`    | Public                   |
| `-`    | Private                  |
| `#`    | Protected                |
| `~`    | Package-level visibility |

### Attribute syntax

```text
visibility name: Type = defaultValue
```

Example: `- age: int = 21`

Multiplicity (when relevant) indicates how many objects can participate in a relationship, such as `0..1`, `1`, `0..*`, or `1..*`.

### Method syntax

```text
visibility methodName(parameter: Type): ReturnType
```

Example: `+ isAdult(age: int): boolean`

- `void` means the method does not return a value.
- Include parameters and return types when they help explain the design.

## 3. Interfaces, Abstract Classes, and Enums

### Interface

- Defines a contract that implementing classes agree to follow.
- In a class diagram, commonly shown with `<<interface>>` above its name and its method signatures below.
- A class implements an interface using a **dashed line with a hollow triangle pointing to the interface** (realization).

### Abstract class

- Cannot be instantiated directly.
- Can contain both implemented and abstract methods.
- Often shown with `<<abstract>>` or an italicized class name; abstract operations may also be italicized.

### Enumeration (enum)

- Represents a fixed set of named values.
- Shown with `<<enumeration>>` and its possible values.

Example:

```text
<<enumeration>>
VehicleType
----------------
CAR
BIKE
TRUCK
```

## 4. Three Perspectives of Class Diagrams

- **Conceptual:** High-level domain concepts and their relationships; usually avoids code details.
- **Specification:** Interfaces, responsibilities, and key operations; focuses on what classes promise to do.
- **Implementation:** Code-level details such as attributes, types, visibility, methods, and relationships.

In an LLD interview, a **specification or lightly detailed implementation view** is often useful. Include enough detail to explain your design without overcrowding the diagram.

## 5. Relationships Between Classes

| Relationship       | Meaning                                                                                                                                                                                      | UML notation                                                                | Example                            |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ---------------------------------- |
| **Association**    | A general relationship: one class knows about or interacts with another.                                                                                                                     | Solid line                                                                  | `Teacher — Student`                |
| **Aggregation**    | A weak whole–part relationship; a weak "has-a" relationship. The contained class can exist independently of the whole.                                                                       | Hollow diamond at the whole                                                 | `Department ◇— Professor`          |
| **Composition**    | A strong whole–part relationship; a strong "has-a" relationship. The contained class cannot exist independently of the whole.                                                                | Filled diamond at the whole                                                 | `House ◆— Room`                    |
| **Generalization** | A **UML modeling concept** — a structural relationship showing that one classifier (child) is a specialized form of another (parent). It captures the **is-a** concept at the diagram level. | Solid line with hollow triangle pointing to the parent (general) classifier | `Dog —▷ Animal`                    |
| **Inheritance**    | An **OOP implementation mechanism** — how a subclass acquires the attributes and behavior of its superclass in code. It is how generalization is _realized_ in a programming language.       | Same arrow notation as generalization (code-level perspective)              | `class Dog extends Animal`         |
| **Realization**    | A class implements an interface, promising to fulfill the contract defined by the interface.                                                                                                 | Dashed line with hollow triangle pointing to interface                      | `Circle - -▷ Shape`                |
| **Dependency**     | One class temporarily uses another; changes to the used class may affect the dependent class.                                                                                                | Dashed arrow pointing to the dependency                                     | `OrderService - -> PaymentService` |

### Important distinctions

- **Association:** General connection between classes.
- **Aggregation:** The part can exist without the whole.
- **Composition:** The whole owns the part's lifecycle; use this when that ownership is meaningful.
- **Generalization:** A UML _diagram-level_ concept -- the arrow showing one classifier is a specialized form of another. It is the _what_ (structure/model).
- **Inheritance:** An OOP _code-level_ mechanism -- the language feature by which a subclass acquires and can extend its superclass's attributes and behavior. It is the _how_ (implementation). Inheritance is how generalization gets realized in code.
- **Composition/Aggregation:** Often express has-a.
- **Dependency:** Usually a weaker or more temporary uses relationship.

> **Generalization vs. Inheritance:** They share the same UML arrow (solid line + hollow triangle), but operate at different levels of abstraction. Generalization is a modeling relationship you draw on a diagram; Inheritance is the language feature (e.g. `extends`) you write in code to implement it.

> UML relationships depend on the actual design. Avoid forcing aggregation or composition when a simple association is enough.

## 6. Interview-Focused Summary

Remember these essentials:

1. A class diagram shows the **static structure** of a system.
2. A class box contains **name, attributes, and methods**.
3. Visibility: `+` public, `-` private, `#` protected, `~` package.
4. Know the difference between a **class, interface, abstract class, and enum**.
5. Be able to draw and explain association, aggregation, composition, generalization/inheritance, realization, and dependency.
6. Focus on clear responsibilities, sensible relationships, and multiplicity when relevant.
7. You usually do **not** need to memorize every UML diagram type in depth for LLD; prioritize class diagrams and communicating design decisions.

### Quick memory aid

- **Generalization:** is-a *(UML diagram -- the structural relationship arrow)*
- **Inheritance:** is-a *(OOP code -- the `extends` mechanism that implements generalization)*
- **Association:** interacts-with / knows-about
- **Aggregation:** weak has-a
- **Composition:** strong has-a / lifecycle ownership
- **Realization:** implements
- **Dependency:** uses
