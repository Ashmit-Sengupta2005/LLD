# synchronized vs volatile vs Atomic — The Three Fixes

---

## 1. `synchronized` — one thread at a time

A thread entering a `synchronized` region must first grab a **monitor lock**. If another thread holds it, this thread **blocks** until it's free. That's what makes the critical section safe.

**Form 1 — synchronized method** (locks on `this`, the whole object):

```java
class SafeCounter {
    private int count = 0;

    public synchronized void increment() { count++; }     // now atomic
    public synchronized int getCount()   { return count; }
}
```

**Form 2 — synchronized block** (lock only the lines that need it):

```java
class SafeCounter {
    private final Object lock = new Object();     // a dedicated lock object
    private int count = 0;

    public void increment() {
        synchronized (lock) {                     // ⭐ only the critical section is locked
            count++;
        }
    }
}
```

> **Why the block is usually better:** if a method does 50 lines of work and only one line touches shared data, locking the whole method makes 49 lines wait for no reason. **Lock the smallest region you can.**

---

## 2. Monitor locks — the points to remember

- **One lock per object** (and a separate one per `Class` for `static` methods)
- **Re-entrant** — a thread already holding the lock can enter another synchronized method of the same object without deadlocking itself
- **Queueing** — threads that can't get the lock go into the **Blocked** state and wait

**Which lock is taken?**

| Code | Lock used |
| --- | --- |
| `synchronized` instance method | `this` |
| `synchronized` static method | the `Class` object |
| `synchronized (obj) { }` | `obj` |

> **⭐ The thing to say:** two threads only block each other if they're locking **the same object**. A `static synchronized` method and an instance one use *different* locks, so they do **not** exclude each other.

**The cost:** locking makes threads wait, which hurts throughput. And acquiring multiple locks in inconsistent order causes **deadlock** — thread A holds lock 1 waiting for lock 2, thread B holds lock 2 waiting for lock 1, and neither ever moves. The standard fix is to always acquire locks in the **same order**.

## 3. `volatile` — visibility only, no locking

`volatile` tells the JVM: **always read and write this variable from main memory**, never from a thread's local CPU cache.

```java
class SharedData {
    volatile boolean flag = false;

    public void writer() { flag = true; }
    public void reader() { if (flag) { /* guaranteed to see true */ } }
}
```

**What it guarantees:**
- ✅ **Visibility** — one thread's write is immediately seen by all others
- ✅ **No caching** — every access goes to main memory
- ❌ **NOT atomicity**

**⭐ The point interviewers push on:**

```java
volatile int count = 0;
count++;        // STILL unsafe
```

`volatile` keeps the value fresh, but `count++` is still three steps — two threads can both read 42 and both write 43. Freshness doesn't stop interleaving.

**Use `volatile` for:** flags, status checks, config values — **one writer, many readers**, with no read-modify-write.

> **Classic use:** a `volatile boolean running` flag to stop a background thread. Without `volatile`, that thread may cache `true` and loop forever.

---

## 4. Atomic variables — lock-free safety

Classes in `java.util.concurrent.atomic`: **`AtomicInteger`**, `AtomicLong`, `AtomicBoolean`, `AtomicReference`.

They give you atomicity **without locks**, so threads never block.

```java
class LikeCounter {
    private final AtomicInteger likes = new AtomicInteger(0);

    public void incrementLikes() { likes.incrementAndGet(); }   // ⭐ atomic, one call
    public int  getCount()       { return likes.get(); }
}
```

> **Analogy:** an Instagram post's Like counter. Millions of taps at once, every one counted, nobody slowed down by a lock.

### How it works: CAS (Compare-And-Swap)

A **single CPU instruction** that says:

> *"If this variable still holds the value I expect, replace it with the new value. If not, I lost the race — I'll retry."*

```java
int prev, next;
do {
    prev = likes.get();                        // read current value
    next = prev + 1;                           // compute new value
} while (!likes.compareAndSet(prev, next));    // swap only if nobody changed it meanwhile
```

**Two threads incrementing from 10:**

| Step | Thread U1 | Thread U2 |
| --- | --- | --- |
| `prev = get()` | reads 10 | reads 10 |
| `next = prev + 1` | wants 11 | wants 11 |
| `compareAndSet(10, 11)` | ✅ succeeds → value is 11 | ❌ fails — value is no longer 10 |
| Retry | exits the loop | retries: `prev = 11`, sets **12** |

**Nothing is lost, and nobody was blocked.** The loser just tries again.

> **Compare-And-Swap vs Compare-And-Set:** the same idea at two levels. **CAS** is the hardware instruction; **`compareAndSet()`** is the Java method that uses it.

**In real code write `incrementAndGet()`**, not the loop — the loop is only for showing how CAS works, and for custom update logic.

| Pros | Cons |
| --- | --- |
| No locking, no blocking → high throughput | **Retries pile up under heavy contention** — many threads failing and looping burns CPU |
| Simple API: `get()`, `set()`, `incrementAndGet()`, `compareAndSet()` | Works on **one variable only** — can't atomically update two fields together |

---

## 5. ⭐ The comparison table

| Feature | `synchronized` | `volatile` | `AtomicInteger` |
| --- | --- | --- | --- |
| **Atomicity** | ✅ Yes | ❌ No | ✅ Yes (single variable) |
| **Visibility** | ✅ Yes | ✅ Yes | ✅ Yes |
| **Blocking?** | ✅ Blocks other threads | ❌ Non-blocking | ❌ Non-blocking |
| **Performance** | Lowest (lock overhead) | Highest | High |
| **Use for** | Multi-step / multi-variable operations | Simple flags, config — one writer, many readers | Counters, single-value updates |

---

## 6. Quick Recall

- **`synchronized`** — monitor lock, one thread at a time. Gives **atomicity + visibility**, costs blocking. Prefer a **block** over a whole method
- **Monitor lock** is per-object, **re-entrant**; `static synchronized` locks the **Class**, so it's a different lock from the instance one
- **`volatile`** — **visibility only**. `volatile count++` is still broken. Use for flags, not counters
- **Atomic classes** — atomicity without locks, built on **CAS**: *"if it's still what I expect, swap it; else retry"*
- **Pick by the operation:** flag → `volatile`; one counter → `Atomic`; several variables or multi-step logic → `synchronized`
- **Follow-up — "why not synchronize everything?"** → correctness is fine, but you serialise the whole app and risk **deadlock**. Lock the narrowest section you can
