# Read-Write Locks & Semaphores

---

## 1. Read-Write Lock — for read-heavy data

**The problem:** stock prices, config caches, product catalogs are read constantly and written rarely. A normal lock forces **one reader at a time**, even though readers don't interfere with each other at all. That's wasted parallelism.

**`ReentrantReadWriteLock` splits the lock in two:**

| | Who can hold it | Blocks |
| --- | --- | --- |
| **Read lock** | **Many threads at once** | Only blocked while a writer holds the lock |
| **Write lock** | **Exactly one thread** | Blocks all readers *and* other writers |

> **Analogy:** a library. Any number of visitors can read at the same time. When the librarian re-shelves a book, that aisle is closed to everyone.

```java
class StockData {
    private double price = 100.0;
    private final ReadWriteLock lock = new ReentrantReadWriteLock();

    public void updatePrice(double newPrice) {
        lock.writeLock().lock();            // exclusive
        try {
            price = newPrice;
        } finally {
            lock.writeLock().unlock();
        }
    }

    public double readPrice() {
        lock.readLock().lock();             // shared — many readers together
        try {
            return price;
        } finally {
            lock.readLock().unlock();
        }
    }
}
```

> **Use it only when reads heavily outnumber writes.** With frequent writes it performs **worse** than a plain lock, because of the extra bookkeeping and because writers can get starved behind a steady stream of readers.

## 2. Semaphore — limiting concurrent access

**The problem:** a TUF+ account allows only N devices logged in at once. This isn't mutual exclusion — you don't want **one**, you want **at most N**.

**A `Semaphore` holds N permits.** A thread takes a permit before entering, returns it when done. No permits left → it waits, or fails, or waits with a timeout.

> **Analogy:** a club with exactly N entry tokens. Take one to get in, return it on the way out. No tokens left, no entry.

```java
class TUFPlusAccount {
    private final Semaphore deviceSlots;

    public TUFPlusAccount(int maxDevices) {
        this.deviceSlots = new Semaphore(maxDevices);
    }

    public boolean login(String user) {
        if (deviceSlots.tryAcquire()) {          // took a permit
            System.out.println(user + " logged in.");
            return true;
        }
        System.out.println(user + " denied — too many devices.");
        return false;
    }

    public void logout(String user) {
        deviceSlots.release();                   // returned the permit
    }
}
```

**The methods:**

| Method | Behaviour |
| --- | --- |
| `acquire()` | Waits until a permit is free (interruptible) |
| `tryAcquire()` | Instant attempt — `true` or `false` |
| `tryAcquire(t, unit)` | Waits up to a limit |
| `release()` | Returns a permit |

**⭐ The key difference from a lock: a semaphore has NO owner.**
Any thread may `release()` a permit another thread acquired. That makes it useful for **cross-thread signalling** and resource pools, but it also means you must **balance acquire and release yourself** — a missing `release()` leaks a permit forever, and an extra one invents a permit that never existed.

**Other points:**
- `new Semaphore(n, true)` → **fair**, FIFO acquisition
- `Semaphore(1)` behaves like a lock, but **without ownership** — so it's a *binary semaphore*, not a mutex
- Release in a `finally` block, and **only if the acquire succeeded**

**Use cases:** database connection pools, rate-limiting concurrent API calls, parking-lot capacity, capping concurrent tasks.

## 3. ⭐ The comparison table

| Feature | **Monitor (`synchronized`)** | **ReentrantLock** | **Semaphore** |
| --- | --- | --- | --- |
| **Type** | Intrinsic monitor | Explicit Lock API | Permit-based |
| **How many threads** | 1 | 1 | **Up to N** |
| **Reentrant** | ✅ | ✅ | Not ownership-based |
| **Instant attempt** | ❌ | ✅ `tryLock()` | ✅ `tryAcquire()` |
| **Timed attempt** | ❌ | ✅ | ✅ |
| **Ownership** | Thread-bound | Thread-bound | **None** |
| **Can another thread release it?** | ❌ | ❌ | ✅ |
| **Waiting mechanism** | `wait()` / `notify()` | `Condition.await()` / `signal()` | Permit availability |
| **Best for** | Simple mutual exclusion | Flexible, timed, fair locking | **Limiting concurrency** |
| **Example** | Shared counter | Ticket booking with timeout | DB connection pool |

**Choosing:**
- **`synchronized`** — short, simple critical section. Default choice
- **`ReentrantLock`** — need timeout, interruptibility, fairness, or multiple conditions
- **`ReadWriteLock`** — read-heavy data with rare writes
- **`Semaphore`** — "at most N at a time", or cross-thread release

---

## 4. Quick Recall

- **`ReadWriteLock`** — many readers **or** one writer. Only worth it when reads ≫ writes
- **`Semaphore`** — N permits; `acquire()` / `release()`. Caps **how many**, not **which one**
- **⭐ Semaphore has no ownership** — any thread can release, so acquisitions and releases must balance
- **`Semaphore(1)` ≠ mutex** — same effect, but no owner, so anyone can release it
- **Both support fairness** via the `true` constructor flag
- **Always release in `finally`**, and only when the acquire actually succeeded
