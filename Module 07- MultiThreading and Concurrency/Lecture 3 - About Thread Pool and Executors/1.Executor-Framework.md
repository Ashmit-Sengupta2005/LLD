# Executor Framework — Why We Stop Creating Threads by Hand

> Lecture 2 already introduced `ExecutorService`, `submit()` and `Future`. This file covers **why** the framework exists and the pieces around it.

---

## 1. The problem: a new thread for every request

A ride-matching system like Uber. Every ride request must find a driver, so the obvious move is to spin up a thread per request:

```java
class RideMatchingService {
    public void requestRide(String riderId) {
        Thread matchThread = new Thread(() -> {       // ⭐ a brand-new thread, every single time
            System.out.println("Matching rider " + riderId + " to a driver...");
            try { Thread.sleep(1000); }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            System.out.println("Ride matched for rider " + riderId);
        });
        matchThread.start();
    }
}
```

Works perfectly for 2 riders. Breaks badly at 10,000.

---

## 2. Why manual thread creation fails at scale

| Problem | What goes wrong |
| --- | --- |
| **Thread explosion** | One thread per task means 10,000 tasks = 10,000 threads. The system is overwhelmed and slows to a crawl |
| **Memory exhaustion** | Every thread needs its **own stack** (roughly 1 MB). Thousands of threads = out of memory, crashes |
| **Thread leaks** | Threads that are never properly finished keep holding resources forever, quietly degrading the app |
| **Context switching overhead** | Far more threads than cores means the CPU spends its time **saving and loading states** instead of doing work |

> **The core mistake:** the number of threads is being driven by the number of *tasks*, when it should be driven by the number of *cores*.

---

## 3. The fix: thread pools

> **Keep a fixed set of threads ready, and feed tasks to them.** Threads are reused, never thrown away.

**Analogy:** A restaurant doesn't hire a new chef for every order. It keeps, say, 10 chefs, and orders queue up for whoever is free next. Hiring per order would bankrupt the kitchen.

So: tasks can be unlimited, **threads are capped**. Extra tasks simply wait in a queue.

---

## 4. The Executor Framework

Part of `java.util.concurrent`. Its whole idea is to **split two things that used to be tangled together**:

| | Who decides | Example |
| --- | --- | --- |
| **Task submission** | You — *what* to do | "send this email" |
| **Task execution** | The framework — *how and when* it runs, on which thread | pool thread #4 picks it up |

You stop writing `new Thread(...)` and just **hand over tasks**.

---

## 5. The four pieces

**1. `Executor` — the base interface**

```java
void execute(Runnable command);
```
Runs a `Runnable` asynchronously. Returns nothing, tells you nothing about the outcome.

**2. `ExecutorService` — extends `Executor`, adds lifecycle control**

| Method | Purpose |
| --- | --- |
| `submit(task)` | Takes `Runnable` **or** `Callable`, returns a `Future` to track it |
| `shutdown()` | Orderly shutdown — rejects new tasks, finishes the submitted ones |
| `shutdownNow()` | Tries to stop everything immediately |

**3. `ThreadPoolExecutor` — the actual implementation doing the work**

Everything below is built on this class. Its four key parameters:

| Parameter | Meaning |
| --- | --- |
| `corePoolSize` | How many threads to keep alive in the pool normally |
| `maximumPoolSize` | The hard ceiling on thread count |
| `keepAliveTime` | How long an idle extra thread survives before being killed |
| `workQueue` | The queue holding tasks that are waiting for a free thread |

**4. `Executors` — a utility class of ready-made factory methods**

```java
Executors.newFixedThreadPool(10);    // 10 threads, fixed
Executors.newCachedThreadPool();     // grows and shrinks on demand
Executors.newSingleThreadExecutor(); // exactly 1 thread
```

> These are just pre-configured `ThreadPoolExecutor` objects. `Executors` is convenience; `ThreadPoolExecutor` is the engine.

## 6. Example: 25 emails, 10 threads

```java
class EmailService {
    private static final ExecutorService executor = Executors.newFixedThreadPool(10);

    public static void sendEmail(String recipient) {
        executor.execute(() -> {
            System.out.println("Sending email to " + recipient
                               + " on " + Thread.currentThread().getName());
            try { Thread.sleep(1000); }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            System.out.println("Email sent to " + recipient);
        });
    }

    public static void main(String[] args) {
        for (int i = 1; i <= 25; i++) {
            sendEmail("user" + i + "@gmail.com");
        }
        executor.shutdown();
    }
}
```

**What actually happens:** 25 tasks are submitted instantly, but only **10 run at a time**. The other 15 wait in the queue, and each is picked up as a thread frees itself. Print `Thread.currentThread().getName()` and you'll see the same 10 thread names repeating — proof they're being **reused**.

**Why this is better:**
- **Simpler** — no thread creation or management code of your own
- **Efficient** — thread creation cost is paid once, not per task
- **Graceful shutdown** — submitted work finishes before the app exits

## 7. `execute()` vs `submit()`

| | `execute()` | `submit()` |
| --- | --- | --- |
| Accepts | `Runnable` only | `Runnable` **and** `Callable` |
| Returns | nothing (`void`) | a **`Future`** |
| Can you get the result? | ❌ No | ✅ Yes, via `future.get()` |
| Can you see exceptions? | ❌ Lost (printed to console at best) | ✅ Surfaced by `get()` as `ExecutionException` |
| Use for | fire-and-forget — logging, emails, notifications | work whose **result or completion** you care about |

```java
ExecutorService executor = Executors.newFixedThreadPool(2);

Future<Integer> future = executor.submit(() -> {   // Callable, returns a value
    Thread.sleep(1000);
    return 77;
});

System.out.println("Doing other work...");         // ⭐ runs immediately, not blocked
Integer result = future.get();                     // ⭐ blocks here until 77 is ready
System.out.println("Result: " + result);

executor.shutdown();
```

> **The pattern to remember:** submit → do other work → `get()` **last**. The whole benefit disappears if you call `get()` right after `submit()`.

**An underrated reason to prefer `submit()`:** with `execute()`, an exception inside your task can vanish silently. `submit()` stores it in the `Future` and rethrows it when you call `get()`.

---

## 8. `shutdown()` vs `shutdownNow()`

| | `shutdown()` | `shutdownNow()` |
| --- | --- | --- |
| New tasks | Rejected | Rejected |
| Already-running tasks | **Allowed to finish** | **Interrupted** to stop them |
| Queued tasks | Still executed | Dropped |
| Returns | `void` | `List<Runnable>` — the tasks that never got to run |

```java
executor.shutdown();                                     // polite: finish what we started
List<Runnable> pending = executor.shutdownNow();         // urgent: stop now, hand back the rest
```

> **`shutdownNow()` only *attempts* to stop things** — it interrupts the threads, and a task that ignores interrupts will keep running. It's a request, not a guarantee.

**Always shut down.** Pool threads are non-daemon by default and stay alive, so without a shutdown your program may simply never exit.

---

## 9. Quick Recall

- **Never create a thread per task** — thread explosion, memory exhaustion, thread leaks, switching overhead
- **Executor Framework decouples** *what* to run (task submission) from *how/when* it runs (task execution)
- **Four pieces:** `Executor` (`execute`) → `ExecutorService` (`submit`, `shutdown`) → `ThreadPoolExecutor` (the real implementation) → `Executors` (factory shortcuts)
- **`ThreadPoolExecutor` params:** `corePoolSize`, `maximumPoolSize`, `keepAliveTime`, `workQueue`
- **`execute()`** = fire-and-forget, no result, exceptions can be lost. **`submit()`** = returns a `Future`, gives you the result *and* the exception
- **`shutdown()`** finishes pending work; **`shutdownNow()`** interrupts and returns the unrun tasks
- **Tasks are unlimited, threads are capped** — that's the entire point of a pool
