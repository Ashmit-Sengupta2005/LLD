# Fixed vs Cached vs Scheduled Thread Pools

All three come from the `Executors` factory class, and all three are `ThreadPoolExecutor` underneath — they just differ in **how many threads they keep and when**.

---

## 1. Fixed Thread Pool

```java
ExecutorService executor = Executors.newFixedThreadPool(10);
```

**A fixed number of threads, always.** A submitted task goes to a free thread; if every thread is busy, the task **waits in the queue** until one frees up.

**Use when:** you roughly know your load and want a hard cap on concurrency — handling a steady stream of user requests, processing a batch of files.

| Advantages | Disadvantages |
| --- | --- |
| **Predictable resource usage** — the thread count never surprises you | **Limited scalability** — during a spike, tasks pile up in the queue and wait |
| **Control** — you set the ceiling, so the system can't be overloaded | **Underutilisation** — with few tasks, threads sit idle doing nothing |

> **The safe default.** Most production code uses a fixed pool sized around the core count (CPU work) or higher (I/O work).

---

## 2. Cached Thread Pool

```java
ExecutorService executor = Executors.newCachedThreadPool();
```

**Creates threads on demand and reuses idle ones.** A thread idle for more than **60 seconds** is killed off. The pool grows during a burst and shrinks back to nothing when quiet.

**Use when:** tasks are **short-lived and bursty** — sudden traffic spikes, small background jobs, unpredictable load.

| Advantages | Disadvantages |
| --- | --- |
| **Scalable** — grows instantly to absorb a burst | **⭐ Thread explosion risk** — a huge flood of tasks creates a huge number of threads |
| **Efficient reuse** — idle threads are reused instead of recreated | **Unpredictable usage** — thread count swings, making resources hard to plan |

> **The trap:** a cached pool has **no upper limit**. Give it 50,000 tasks at once and it will try to make 50,000 threads — exactly the thread explosion the Executor Framework was meant to prevent. Safe only for short tasks at moderate volume.

---

## 3. Scheduled Thread Pool

```java
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);
```

**For tasks that run after a delay, or repeatedly at fixed intervals.** This is Java's built-in cron.

```java
class SessionCleaner {
    public static void main(String[] args) {
        ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);

        Runnable task = () -> System.out.println("Cleaning up expired sessions...");

        //              task, initialDelay, period, unit
        scheduler.scheduleAtFixedRate(task, 0, 5, TimeUnit.SECONDS);
    }
}
```

Here the cleanup runs **immediately** (`initialDelay = 0`) and then **every 5 seconds**, forever.

**Use when:** periodic data sync, cache or session cleanup, health checks, scheduled reports, retrying after a delay.

| Advantages | Disadvantages |
| --- | --- |
| **Scheduling built in** — delayed and periodic execution with one call | **Pointless for ordinary tasks** that just need to run once, now |
| **Flexible** — fixed-rate or fixed-delay policies | **Extra overhead** of tracking timings and intervals |

**`scheduleAtFixedRate` vs `scheduleWithFixedDelay`** — the usual follow-up:

- **`AtFixedRate`** — starts every 5 seconds **no matter how long the task takes**. If a run takes 7 seconds, the next one is already overdue and starts immediately
- **`WithFixedDelay`** — waits 5 seconds **after the previous run finishes**. The gap is always 5 seconds, so runs never overlap

---

## 4. Single Thread Executor

```java
ExecutorService executor = Executors.newSingleThreadExecutor();
```

Exactly **one** thread, with a queue behind it. Tasks therefore run **one at a time, in the order submitted**.

**Use when order matters:** writing to a log file, applying updates to one shared resource sequentially. It gives you background execution *without* any concurrency problems, since only one thread ever touches the data.

---

## 5. Side-by-side

| | **Fixed** | **Cached** | **Scheduled** | **Single** |
| --- | --- | --- | --- | --- |
| **Thread count** | Fixed N | Grows/shrinks, **unbounded** | Fixed N | Exactly 1 |
| **Idle threads** | Kept alive | Killed after 60s | Kept alive | Kept alive |
| **Extra tasks** | Queued | New thread created | Queued by schedule | Queued |
| **Best for** | Steady, known load | Short bursty tasks | Delayed / repeating jobs | Strict ordering |
| **Main risk** | Queue delays during spikes | **Thread explosion** | Overhead when not needed | No concurrency at all |

---

## 6. Quick Recall

- **Fixed** — N threads always; extras queue. Predictable, the usual choice
- **Cached** — threads made on demand, idle ones die after 60s. Great for bursts, **dangerous without a limit**
- **Scheduled** — delayed and repeating tasks; `scheduleAtFixedRate` (clock-driven) vs `scheduleWithFixedDelay` (gap after finishing)
- **Single** — one thread, guaranteed order
- **All four are `ThreadPoolExecutor` underneath**; `Executors` only pre-fills its parameters
- **Follow-up — "which would you use in production?"** → Fixed, or a hand-built `ThreadPoolExecutor` with a **bounded queue**, so load is capped instead of unbounded
