# Deadlock Prevention & Handling

Every technique below works by **breaking one Coffman condition**. That's the only way a deadlock can be stopped.

---

## 1. Lock Ordering — breaks **Circular Wait**

> **The rule:** every thread acquires locks in the **same global order**, no matter what order the work arrives in.

If all threads go A → B → C, a cycle is impossible — nobody can ever hold a later lock while waiting for an earlier one.

In the bank example the bug was T1 locking A→B while T2 locked B→A. The fix is to **sort the locks by a unique ID** before taking them:

```java
public static void transfer(Resource a, Resource b, int amount) {
    Resource[] locks = { a, b };
    // ⭐ sort by unique ID → both threads now lock in the SAME order
    Arrays.sort(locks, (x, y) -> Integer.compare(x.id, y.id));

    synchronized (locks[0]) {
        synchronized (locks[1]) {
            // transfer safely
        }
    }
}
```

Call `transfer(r1, r2)` or `transfer(r2, r1)` — after sorting, **both lock 101 before 102**. The cycle can't form.

> **This is the most used fix in real systems.** Any stable, unique key works: account ID, object hash, memory address, table name.

## 2. `tryLock()` with timeout — breaks **Hold and Wait**

Instead of waiting forever for the second lock, wait a limited time. Fail → **release everything and back off**.

```java
boolean gotA = false, gotB = false;
try {
    gotA = a.lock.tryLock(100, TimeUnit.MILLISECONDS);
    if (gotA) {
        gotB = b.lock.tryLock(100, TimeUnit.MILLISECONDS);
        if (gotB) {
            // got both — do the work
        } else {
            System.out.println("could not lock B — backing off");
        }
    }
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    if (gotB) b.lock.unlock();      // ⭐ release in reverse order
    if (gotA) a.lock.unlock();      // ⭐ only unlock what you acquired
}
```

Now a thread never holds lock A **indefinitely** while waiting for B — the wait has a deadline, and on failure it gives up its locks so others can proceed.

> **⭐ The catch — livelock.** If both threads time out, back off and retry **in lockstep**, they can keep colliding forever: busy, but achieving nothing. The standard fix is a **random backoff** before retrying. ("Deadlock = both frozen. Livelock = both busy, still stuck.")

See Lecture 5 for `tryLock()` in detail.

## 3. Minimize nested locking — breaks **Hold and Wait**

The simplest fix of all: **don't hold two locks at once**. Take one lock, finish, release it, then take the next.

```java
Runnable task1 = () -> {
    resource1.update(100);     // lock 1 taken and released
    resource2.update(200);     // lock 2 taken separately
};

Runnable task2 = () -> {
    resource2.update(300);     // reverse order — and still safe
    resource1.update(400);
};
```

Even though T1 and T2 use the resources in opposite orders, **no thread ever holds one lock while reaching for another**, so there's no chain to form a cycle.

> **The limitation:** this only works when the two operations **don't have to be atomic together**. A bank transfer can't be split this way — releasing the lock between withdraw and deposit leaves a window where the money exists nowhere. When atomicity is required, use **lock ordering** instead.

## 4. Handling deadlocks — the database approach

Instead of preventing deadlocks, databases **let them happen, detect them, and kill one victim**. Both schemes below use a **timestamp** given at start — **older = higher priority**.

| | **Wait-Die** (non-preemptive) | **Wound-Wait** (preemptive) |
| --- | --- | --- |
| T1 is **older** than the holder | T1 **waits** | T1 **wounds** T2 — forces it to roll back |
| T1 is **younger** than the holder | T1 **dies** — aborts and restarts later | T1 **waits** |
| Who gets rolled back? | The **requesting** thread | The **holding** thread |
| Forcible removal of locks? | ❌ No | ✅ Yes |

**Both break Circular Wait**, because waiting is only ever allowed in one direction along the age order — a cycle would need someone waiting "backwards", which is forbidden.

**Key points:**
- An aborted transaction **restarts with its original timestamp**, so it keeps ageing and eventually becomes the oldest. This prevents **starvation** — nobody is rolled back forever
- **Wait-Die** rolls back more often (a young transaction dies even if it would have waited briefly)
- **Wound-Wait** causes fewer rollbacks overall, which is why it's generally preferred

> **Memory aid:** in **Wait-Die** the *requester* dies; in **Wound-Wait** the *holder* gets wounded.

## 5. Detecting a deadlock in a real application

- **Symptom:** the app hangs, CPU usage is near zero, requests stop completing
- **Tool:** take a **thread dump** (`jstack <pid>`, or Ctrl+Break on the console). The JVM detects cycles itself and prints **"Found one Java-level deadlock"** along with both threads and the locks they're holding and waiting for
- `jconsole` / VisualVM show the same thing through a UI

---

## 6. ⭐ Deadlock vs Livelock vs Starvation

| | **Deadlock** | **Livelock** | **Starvation** |
| --- | --- | --- | --- |
| Threads are | Blocked, frozen | **Running**, retrying endlessly | Running, but one is always skipped |
| CPU usage | ~Zero | High | Normal |
| Progress | None, ever | None, despite activity | Others progress, one doesn't |
| Fix | Lock ordering, timeouts | **Random backoff** | Fair locks, FIFO queues |

---

## 7. Quick Recall

- **Every fix breaks one Coffman condition** — know which one goes with which technique
- **Lock Ordering** → breaks **Circular Wait**. Sort locks by a unique ID. **The go-to fix**
- **`tryLock(timeout)`** → breaks **Hold and Wait**. Back off and release on failure; add **random backoff** to avoid livelock
- **Minimize nested locking** → breaks **Hold and Wait**. Only valid when the operations needn't be atomic together
- **Databases handle instead of prevent:** **Wait-Die** (requester dies) and **Wound-Wait** (holder is wounded), both ordered by **timestamp — older wins**
- **Detect with a thread dump** (`jstack`) — the JVM reports Java-level deadlocks automatically
- **Deadlock = stuck and idle. Livelock = stuck and busy. Starvation = everyone else progresses but you**
