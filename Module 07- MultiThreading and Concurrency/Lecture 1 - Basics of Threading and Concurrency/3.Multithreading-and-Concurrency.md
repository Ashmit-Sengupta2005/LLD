# Multithreading, Concurrency & Parallelism — Interview Q&A

---

## Q0. Why do we need this at all? (the motivation)

Press play on Netflix and two things must happen: **loading the video data** and **buffering the content**. If each takes 5 seconds and they run one after the other, you stare at a spinner for **10 seconds**. Run them at the same time and it's **5 seconds**.

> **Analogy:** A restaurant kitchen. One chef chops, one cooks, one plates — all at once. Nobody waits for the previous person to finish, so the dish goes out far sooner.

The same idea powers web servers taking hundreds of requests and apps pushing real-time updates. **Multithreading and concurrency are how we get this in software.**

---

## Q1. What is multithreading? Why use it?

**Multithreading is a technique where one program runs multiple threads at the same time, each thread being the smallest unit of execution inside the process.**

Instead of doing task 1, then task 2, then task 3, the CPU switches between them rapidly (or runs them truly in parallel on multiple cores), so the work appears to happen all together.

Put simply: **break one program into smaller independent parts and run them side by side.** They share the same memory, so they can easily exchange data and work as a team.

**Why use it:**

- **Better performance** — multiple tasks run at once. Read a file *while* processing data, instead of one after the other
- **Non-blocking** — threads don't wait on each other. One thread can crunch data while another sits waiting on a slow database query
- **Resource sharing** — threads in a process share memory, so communication between them is cheap and fast compared to separate processes
- **Scalability in backends** — a server can serve many requests simultaneously, raising throughput and cutting response times under heavy traffic

**Additional benefits:**
- **Responsive UIs** — slow work goes to a background thread, so the main thread keeps reacting to clicks and never "freezes"
- **Efficient CPU use** — on a multi-core machine, threads spread across all cores instead of leaving most of them idle
- **Real-time processing** — games and video streaming process different pieces of data in parallel, cutting latency and keeping things smooth

## Q2. What is concurrency? What is parallelism?

**Concurrency = dealing with many tasks over a period of time** (they may not literally run at the same instant).
**Parallelism = actually executing many tasks at the same instant**, on different cores.

| **Concurrency** | **Parallelism** |
| --- | --- |
| Managing multiple tasks over time, not necessarily at the same moment | Truly simultaneous execution, usually across multiple cores |
| Works fine on a **single core** by switching between tasks quickly | **Needs multiple cores** or processors for real simultaneity |
| Tasks only *appear* to run together — made possible by context switching | Tasks really do run together — no context switching needed |
| Focus: how to **manage and interleave** many tasks | Focus: **execute simultaneously** to finish sooner |

> **The one-liner to remember:** *Concurrency is dealing with many things at once. Parallelism is doing many things at once.*

> **Kitchen version:** One chef juggling three dishes by rotating between them is **concurrency**. Three chefs each cooking one dish is **parallelism**.

**Follow-up — "can you have one without the other?"**
Yes. A single-core machine running many threads is **concurrent but not parallel**. A program splitting one big array across 8 cores is **parallel**. The point: parallelism needs the hardware, concurrency only needs a scheduler.
