# Factory Pattern — Interview Notes

The Factory Pattern hides object creation behind a **single method**, so the client says *what* it wants and never calls `new` on a concrete class itself.

## 1. What is the Factory Pattern?

The **Factory Pattern** provides a way to create objects **without exposing the creation logic** to the client. Instead of calling `new ClassName()` directly, you call a **factory method** that decides which class to instantiate based on some input.

The client works with the **interface/abstract type** — it never knows (or cares about) the concrete class behind the scenes.

---

## 2. Why is it a Creational Pattern?

Because it controls **how and which objects are created**. The decision of "which concrete class to instantiate" is moved out of the client code and into a dedicated factory.

---

## 3. When do you need it? (Real use cases)

Use Factory when:

- The client needs to work with **multiple types** that share a common interface
- The **decision of which class** to use is made at **runtime** (based on config, input, etc.)
- You want to **decouple** object creation from business logic
- Adding new types should **not require modifying** existing client code

**Examples:**

- **Logistics app** — create `Road`, `Air`, or `Ship` transport based on user input
- **Notification system** — create `Email`, `SMS`, or `Push` notification based on preference
- **Payment gateway** — create `UPI`, `CreditCard`, or `NetBanking` handler based on selection
- **Shape drawing tool** — create `Circle`, `Square`, or `Triangle` based on user choice

> Analogy: A pizza shop — you say "Margherita", the kitchen (factory) makes it and hands it over. You don't go into the kitchen yourself.

---

## 4. How does it work? (Key mechanics)

Three components always involved:

| Component                        | Purpose                                                           |
| -------------------------------- | ----------------------------------------------------------------- |
| **Product (Interface/Abstract)** | Defines the common contract all products must follow              |
| **Concrete Products**            | Actual classes that implement the Product interface               |
| **Factory Class**                | Contains the method that returns the right product based on input |

---

## 5. Without Factory vs. With Factory

### Without Factory (Bad Practice)

- Object creation logic is **embedded inside business logic**
- The service class directly does `new Air()`, `new Road()`, etc.
- Adding a new type means **modifying the service class** — violates Open/Closed Principle
- **Tight coupling** between service and concrete classes

### With Factory (Good Practice)

- Object creation is moved to a **separate factory class**
- The service class just calls `Factory.get(input)` and uses the returned object
- Adding a new type only requires **modifying the factory** — service stays untouched
- **Loose coupling** — service depends only on the interface, not concrete classes

---

## 6. The Problem Factory Solves — Interview Explanation

> "Without Factory, if I have a `LogisticsService` that creates `Road` or `Air` objects inside its `send()` method, then every time I add a new transport mode like `Ship`, I have to open and modify `LogisticsService`. This violates Open/Closed Principle and creates tight coupling. With Factory, I move all creation logic to `LogisticsFactory`. Now `LogisticsService` just asks the factory for an object — it doesn't care which concrete class is returned. Adding `Ship` only means updating the factory."

## 8. Pros of Factory Pattern

- **Loose Coupling** — client depends on interface, not concrete classes
- **Open/Closed Principle** — add new types without modifying existing code
- **Single Responsibility** — creation logic is centralized in one place
- **Flexibility** — object type decided at runtime based on input/config
- **Reusability** — factory can be reused across multiple parts of the app
- **Easier Testing** — can mock the factory or individual products independently

---

## 9. Cons of Factory Pattern

- **Extra code** — introduces additional factory classes/interfaces (overhead for small programs)
- **Increased complexity** — might be overkill when you only have 1–2 concrete types
- **Factory modification** — adding a new product still requires updating the factory method (unless you use Abstract Factory or reflection)

---

## 10. Interview Quick Recall

- **Pattern type:** Creational
- **Core idea:** Delegate object creation to a factory method — client never calls `new` on concrete classes
- **Three components:** Product (interface) + Concrete Products + Factory Class
- **Key benefit:** Decouples creation from usage → follows Open/Closed & Single Responsibility Principles
- **When to use:** Multiple types behind a common interface, type decided at runtime
- **When NOT to use:** Only one concrete type exists, or the creation logic is trivially simple
- **Common follow-up:** "How is it different from Abstract Factory?" → Factory creates **one family of objects**, Abstract Factory creates **families of related objects**
