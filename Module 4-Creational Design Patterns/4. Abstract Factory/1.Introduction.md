# Abstract Factory Pattern — Interview Notes

## 1. What is the Abstract Factory Pattern?

The **Abstract Factory Pattern** provides an interface for creating **families of related objects** without specifying their concrete classes. Instead of one factory producing one type of object (like Factory Pattern), an Abstract Factory produces a **group of related objects** that are designed to work together.

> "Factory of factories — each factory produces a complete, consistent family of products."

---

## 2. How is it different from Factory Pattern?

| Aspect                  | Factory Pattern                          | Abstract Factory Pattern                          |
| ----------------------- | ---------------------------------------- | ------------------------------------------------- |
| **Creates**             | One type of object                       | A **family** of related objects                   |
| **Factory method**      | Single method returning one product      | Multiple methods, each returning a different product |
| **Use case**            | "Give me a payment gateway"              | "Give me a gateway **and** its matching invoice"  |
| **Abstraction level**   | One level (product interface)            | Two levels (factory interface + product interfaces)|

> Factory = "Which **one** object to create?"
> Abstract Factory = "Which **family** of objects to create?"

---

## 3. When do you need it? (Real use cases)

Use Abstract Factory when:

- Multiple **related objects** must be created as a **cohesive set**
- The type of objects depends on a **context** (country, theme, platform)
- **Consistency** across a family must be maintained (e.g., India gateway + India invoice)
- Client code should be **independent** of concrete product classes

**Examples:**

- **Checkout service** — region-specific payment gateway + matching invoice format (Razorpay + GST for India, PayPal + US Invoice for US)
- **UI toolkit** — platform-specific Button + Checkbox + TextField (Windows style vs Mac style)
- **Database layer** — DB-specific Connection + Command + Reader (MySQL family vs PostgreSQL family)
- **Document export** — format-specific Header + Body + Footer (PDF family vs HTML family)

> Analogy: A regional kitchen — an Indian kitchen produces naan + curry + lassi (all Indian). A Japanese kitchen produces rice + sushi + matcha (all Japanese). You pick the kitchen (factory), and everything it produces is **consistent**.

---

## 4. How does it work? (Key mechanics)

| Component                | Purpose                                                          |
| ------------------------ | ---------------------------------------------------------------- |
| **Abstract Products**    | Interfaces for each product type (`PaymentGateway`, `Invoice`)   |
| **Concrete Products**    | Actual implementations (`RazorpayGateway`, `GSTInvoice`, etc.)   |
| **Abstract Factory**     | Interface declaring creation methods for each product type       |
| **Concrete Factories**   | Region/context-specific factories (`IndiaFactory`, `USFactory`)  |
| **Client**               | Uses only the factory interface — never touches concrete classes |

### Flow:

1. Client receives a **factory** (e.g., `IndiaFactory`)
2. Client calls `factory.createPaymentGateway()` → gets `RazorpayGateway`
3. Client calls `factory.createInvoice()` → gets `GSTInvoice`
4. Both products are **guaranteed to be compatible** (same region/family)

## 5. Without Abstract Factory vs. With Abstract Factory

### Without (Bad Practice)

```java
class CheckoutService {
    public void checkOut(double amount) {
        // Hardcoded — tightly coupled
        if (gatewayType.equals("razorpay")) {
            paymentGateway = new RazorpayGateway();
        } else {
            paymentGateway = new PayUGateway();
        }
        paymentGateway.processPayment(amount);
        Invoice invoice = new GSTInvoice(); // always GST, even for US!
        invoice.generateInvoice();
    }
}
```

**Problems:**
- Object creation mixed with business logic
- Concrete classes hardcoded — tight coupling
- Adding a new region → modify `CheckoutService`
- No guarantee gateway and invoice are from the same region

### With Abstract Factory (Good Practice) ✅

```java
class CheckoutService {
    private PaymentGateway paymentGateway;
    private Invoice invoice;

    public CheckoutService(RegionFactory factory, String gatewayType) {
        this.paymentGateway = factory.createPaymentGateway(gatewayType);
        this.invoice = factory.createInvoice();
    }

    public void completeOrder(double amount) {
        paymentGateway.processPayment(amount);
        invoice.generateInvoice();
    }
}
```

- `CheckoutService` doesn't know about Razorpay, PayPal, GST, or US Invoice
- Swap regions by passing a different factory — **zero changes** to the service
- Gateway + Invoice are always from the **same family** — consistency guaranteed

---

## 6. The Interview Explanation

> "Without Abstract Factory, my `CheckoutService` hardcodes `new RazorpayGateway()` and `new GSTInvoice()` inside business logic. If I need to support US payments, I have to modify the service — violating Open/Closed Principle. Worse, nothing prevents me from accidentally pairing a US gateway with an Indian invoice.
>
> With Abstract Factory, I define a `RegionFactory` interface with `createPaymentGateway()` and `createInvoice()`. `IndiaFactory` returns Razorpay + GST, `USFactory` returns PayPal + US Invoice. The service just calls the factory — it's completely decoupled. Adding a new region means adding one new factory class. The service never changes."

## 8. Pros of Abstract Factory Pattern

- **Encapsulates object creation** — client never touches `new ConcreteClass()`
- **Guarantees consistency** — related products always come from the same family
- **Scalable** — add new regions/themes by adding new factory classes
- **Follows Open/Closed Principle** — extend without modifying existing code
- **Follows Dependency Inversion** — client depends on abstractions, not concrete classes
- **Easy to test** — mock the factory interface for unit tests

---

## 9. Cons of Abstract Factory Pattern

- **Increased complexity** — multiple interfaces, factories, and product classes
- **Hard to extend product families** — adding a new product type (e.g., `Receipt`) requires updating **all** factory implementations
- **More boilerplate** — many classes even for basic use cases
- **Runtime flexibility is harder** — factories are typically chosen at setup time, not dynamically swapped mid-execution

---

## 10. Interview Quick Recall

- **Pattern type:** Creational
- **Core idea:** Create **families of related objects** through a factory interface — client never knows the concrete classes
- **Key components:** Abstract Products + Concrete Products + Abstract Factory + Concrete Factories + Client
- **Key benefit:** Guarantees related objects are **consistent** (same family) + complete decoupling
- **Solves:** Hardcoded object creation, inconsistent product combinations, tight coupling
- **When to use:** Multiple related objects that must work together, context-dependent creation (region, platform, theme)
- **When NOT to use:** Only one product type exists (use Factory Pattern instead), or the system is too small to justify the abstraction layers
- **Common follow-up:** "How is it different from Factory?" → Factory creates **one product**, Abstract Factory creates **a family of related products**
