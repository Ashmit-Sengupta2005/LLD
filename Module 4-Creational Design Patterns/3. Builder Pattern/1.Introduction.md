# Builder Pattern — Interview Notes

## 1. What is the Builder Pattern?

The **Builder Pattern** separates the construction of a complex object from its representation. It lets you build an object **step by step**, configuring only the parts you need, while keeping the final object clean and consistent.

> "Same construction process, different representations."

---

## 2. Why is it a Creational Pattern?

Because it controls **how complex objects are constructed**. Instead of one massive constructor call, you configure the object piece by piece through a dedicated Builder class.

---

## 3. When do you need it? (Real use cases)

Use Builder when:

- An object has **many fields** — especially when most are **optional**
- You want the final object to be **immutable** (read-only after creation)
- You need **validation rules** enforced at build time
- You want **readable, fluent construction** instead of long parameter lists

**Examples:**

- **Custom burger/pizza order** — choose bun, patty, toppings, sides, drink step by step
- **HTTP request builder** — set URL, headers, body, timeout independently
- **gRPC ServerBuilder** — configure port, services, credentials before starting
- **AWS SDK request objects** — chain `.WithX()` methods for clearer setup

> Analogy: Ordering a custom burger — you pick bun, patty, cheese, toppings one by one. The chef (builder) assembles it step by step and hands you the final burger.

---

## 4. The Problem Builder Solves

### Constructor Approach (Bad)

```cpp
BurgerMeal("wheat", "veg", false, {}, "", "");
```

**Problems:**
- Hard to read — what does `false` or `""` mean?
- Must pass placeholder values for fields you don't want
- One wrong argument order → silent bugs
- Adding new fields → modify every constructor call

### Telescoping Constructor Anti-Pattern (Also Bad)

```cpp
BurgerMeal(string bun, string patty);
BurgerMeal(string bun, string patty, bool cheese);
BurgerMeal(string bun, string patty, bool cheese, string side);
BurgerMeal(string bun, string patty, bool cheese, string side, string drink);
```

**Problems:**
- Explodes with combinations
- Confusing overloaded signatures
- Forced parameter ordering

### Builder Approach (Good) ✅

```cpp
BurgerMeal burger = BurgerMeal::Builder("wheat", "veg")
                        .withCheese(true)
                        .withToppings({"lettuce", "onion"})
                        .withDrink("coke")
                        .build();
```

- Readable — each method says exactly what it configures
- Flexible — set only what you need
- Safe — validation happens in `build()`

---

## 5. How does it work? (Key mechanics)

| Component              | Purpose                                                       |
| ---------------------- | ------------------------------------------------------------- |
| **Product**            | The complex object being built (e.g., `BurgerMeal`)          |
| **Builder**            | Inner class that holds construction state and fluent methods  |
| **Private Constructor**| Forces all creation through the Builder                       |
| **`build()` method**   | Validates and returns the final immutable object              |

### Key mechanics explained:

1. **Private Constructor** — `BurgerMeal` constructor is private, so you can't do `new BurgerMeal(...)` directly
2. **Builder stores state** — required fields in Builder's constructor, optional fields via fluent methods
3. **Fluent API** — each setter returns `*this` (or `this` in Java), enabling method chaining
4. **Immutability** — final object's fields are `const` / `final`, making it read-only after creation
5. **Validation at build time** — `build()` checks all rules before creating the object

## 6. Interview Comparison Table

| Aspect             | Constructor Approach            | Builder Pattern                         |
| ------------------ | ------------------------------- | --------------------------------------- |
| Readability        | Poor (long argument list)       | Excellent (fluent and expressive)       |
| Flexibility        | Low (all-or-nothing)            | High (configure only what's needed)     |
| Maintainability    | Hard to scale                   | Easy to extend (add one method)         |
| Safety             | Error-prone ordering            | Centralized validation in `build()`     |
| Immutability       | Hard to enforce                 | Natural — private constructor + const   |

---

## 7. When to Use vs. When to Avoid

### ✅ Use when:
- Object has **5+ fields**, many of them optional
- You want **immutability** after construction
- You need **validation rules** enforced in one place
- You want **clean, readable** object creation (fluent API)

### ❌ Avoid when:
- Class has only **1–2 fields** — a simple constructor is enough
- Object is **trivial** — Builder adds unnecessary boilerplate
- No optional fields exist — no benefit over a regular constructor

---

## 8. Pros of Builder Pattern

- **Readable construction** — fluent methods act like named parameters
- **Centralized validation** — rules enforced once in `build()`
- **Supports immutability** — final object is `const` and consistent
- **Scales well** — adding a new optional field = adding one method
- **No placeholder values** — skip what you don't need
- **Same process, different objects** — same Builder flow can produce varied configurations

---

## 9. Cons of Builder Pattern

- **More boilerplate** — Builder adds an extra inner class and more code
- **Overkill for small models** — unnecessary complexity for 1–2 field objects
- **Two-step creation** — object isn't created until `build()` is called
- **Mutable Builder, immutable Product** — Builder itself is mutable during construction

---

## 10. C++ Specific Tips

Builder in C++ pairs well with:

- **`std::optional`** — represent truly optional fields safely (no empty string hacks)
- **`std::move`** — avoid expensive copies during building (move strings, vectors into the final object)
- **RAII** — final object owns resources (files, sockets) safely after construction
- **`const` fields** — enforce immutability in the Product class

## 12. Interview Quick Recall

- **Pattern type:** Creational
- **Core idea:** Build complex objects step by step — separate construction from representation
- **Key components:** Product + Builder (inner class) + Private Constructor + `build()`
- **Fluent API:** Each setter returns `this`/`*this` for method chaining
- **Key benefit:** Readable, flexible, immutable objects with centralized validation
- **Solves:** Telescoping constructor anti-pattern, unreadable long parameter lists
- **When NOT to use:** Trivial objects with 1–2 fields — constructor is simpler
- **Common follow-up:** "How is Builder different from Factory?" → Factory decides **which class** to create; Builder decides **how to configure** a single complex class
