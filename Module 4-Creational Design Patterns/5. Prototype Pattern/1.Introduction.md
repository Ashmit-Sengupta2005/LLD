# Prototype Pattern — Interview Notes

## 1. What is the Prototype Pattern?

The **Prototype Pattern** is a creational design pattern that creates new objects by **cloning existing ones** instead of constructing them from scratch. It provides a mechanism to copy the original object to a new one without making the code dependent on their classes.

> "Instead of building from scratch, copy what already works and tweak it."

---

## 2. Real-life Analogy (Photocopy Machine)

Think of preparing ten offer letters. Instead of typing the same letter ten times, you write it once, photocopy it, and change just the name on each copy. This is how the Prototype Pattern works: start with a **base object** and produce modified copies with minimal changes.

---

## 3. When do you need it? (Real use cases)

Use Prototype Pattern when:

- **Object creation is resource-intensive or complex** (e.g., loading templates, parsing configs)
- You require **many similar objects with slight variations**
- You want to avoid writing **repetitive initialization logic**
- You need **runtime object creation without tight class coupling**

**Examples:**

- **Email template system** — a pre-configured email prototype is cloned per user, with only the name/content changed
- **Game characters** — a base character with stats, equipment, and abilities is cloned and slightly modified for NPCs
- **Document templates** — a configured report template is cloned and filled with different data
- **Database connection configs** — a base config is cloned and tweaked per environment (dev, staging, prod)

> Analogy: A configured game character is like a master template. You clone it for each new player — same base stats, same equipment — then customize the name and appearance. No need to re-equip everything from scratch.

---

## 4. How does it work? (Key mechanics)

| Component              | Purpose                                                            |
| ---------------------- | ------------------------------------------------------------------ |
| **Prototype Interface**| Declares a `clone()` method that all prototypes must implement     |
| **Concrete Prototype** | Actual class that implements `clone()` — defines how copying works |
| **Registry (optional)**| Stores pre-configured prototypes and hands out clones on request   |
| **Client**             | Requests clones from prototypes or registry — never calls `new`   |

### Flow:

1. A **prototype object** is created and configured once (expensive setup)
2. Client calls `prototype.clone()` → gets a **copy** of the object
3. Client **customizes** the clone (change name, content, etc.)
4. Original prototype remains **unchanged** — ready for more clones

---

## 5. Without Prototype vs. With Prototype

### Without (Bad Practice)

```java
class EmailService {
    public void sendWelcomeEmails() {
        // Every email rebuilds the same template from scratch
        WelcomeEmail email1 = new WelcomeEmail();  // heavy init
        email1.send("user1@example.com");

        WelcomeEmail email2 = new WelcomeEmail();  // heavy init AGAIN
        email2.setContent("Welcome to TUF Premium.");
        email2.send("user2@example.com");

        WelcomeEmail email3 = new WelcomeEmail();  // heavy init AGAIN
        email3.setContent("Let's get started!");
        email3.send("user3@example.com");
    }
}
```

**Problems:**
- Template setup (tokens, subject, style) **repeats** for every email object
- Wastes time and increases chances of **inconsistency**
- No cloning mechanism — each instance must be **constructed from scratch**
- Adding more template types forces **more duplicate construction code**

### With Prototype (Good Practice) ✅

```java
class EmailService {
    public void sendWelcomeEmails(EmailTemplateRegistry registry) {
        // Clone from a pre-configured prototype — no heavy init
        EmailTemplate email1 = registry.getTemplate("welcome");
        email1.send("user1@example.com");

        EmailTemplate email2 = registry.getTemplate("welcome");
        email2.setContent("Welcome to TUF Premium.");
        email2.send("user2@example.com");

        EmailTemplate email3 = registry.getTemplate("welcome");
        email3.setContent("Let's get started!");
        email3.send("user3@example.com");
    }
}
```

- Heavy setup happens **once** during prototype registration
- Each `getTemplate()` returns a **clone** — fast and independent
- Original prototype stays **unchanged**
- Adding new templates = register a new prototype, **zero changes** to client code

## 6. Deep Cloning vs. Shallow Cloning

This is a **critical concept** for interviews:

| Aspect           | Shallow Clone                                           | Deep Clone                                                |
| ---------------- | ------------------------------------------------------- | --------------------------------------------------------- |
| **What's copied**| Primitive fields + **references** (not the objects)      | Primitive fields + **new copies** of referenced objects    |
| **Shared state** | Clone and original **share** mutable referenced objects  | Clone and original are **fully independent**              |
| **Risk**         | Modifying the clone can **accidentally change** original | No risk — they don't share any mutable state              |
| **When to use**  | All referenced objects are **immutable** or primitives   | Referenced objects are **mutable** and must be independent |

### In Java:

- `Object.clone()` performs a **shallow copy** by default
- For deep cloning, you must **manually copy** mutable referenced objects in the `clone()` method or use a copy constructor

```java
// Shallow — clone and original share the same EmailStyle object
EmailStyle style = original.style;  // ❌ same reference

// Deep — clone gets its own independent copy
EmailStyle style = new EmailStyle(original.style);  // ✅ new object
```

> **Interview tip:** "Java's default `clone()` is shallow. For prototype objects — especially templates or configurations — I always implement deep cloning to prevent shared mutation bugs."

---

## 7. The Interview Explanation

> "Without Prototype, my email service calls `new WelcomeEmail()` for every user — repeating expensive template parsing, token loading, and style configuration each time. That's wasteful and error-prone.
>
> With Prototype, I configure a `WelcomeEmail` prototype once, register it in a `TemplateRegistry`, and clone it for each user. The clone is cheap — just copying fields — and I customize only what's different (like the recipient name). The original stays untouched. This follows the Prototype Pattern: create by cloning, not by constructing."

## 9. Pros of Prototype Pattern

- **Faster object creation** — no need to reinitialize from scratch
- **Reduces duplication** — less repeated setup logic for similar objects
- **Runtime configuration** — easy to customize clones per request
- **Works well with registries** — centralized template management becomes simple
- **Follows Open/Closed Principle** — add new prototypes without modifying client code
- **Avoids subclass explosion** — instead of creating many subclasses, clone and configure

---

## 10. Cons of Prototype Pattern

- **Deep cloning needs design effort** — you must carefully decide what to copy and how
- **Circular references can complicate copying** — especially with shared ownership graphs
- **Java's `Cloneable` is poorly designed** — `clone()` returns `Object`, requires casting, and has no compile-time safety
- **Hidden complexity** — easy to introduce bugs if some fields are shallow-copied when they should be deep-copied

---

## 11. Interview Quick Recall

- **Pattern type:** Creational
- **Core idea:** Create new objects by **cloning existing prototypes** — avoid expensive construction
- **Key components:** Prototype Interface + Concrete Prototype + Registry (optional) + Client
- **Key benefit:** Efficient creation of many **similar objects** with minimal setup overhead
- **Solves:** Repetitive expensive initialization, tight coupling to concrete constructors
- **When to use:** Object creation is costly, many similar objects needed, runtime flexibility required
- **When NOT to use:** Objects are simple to construct, or cloning semantics are too complex (deep circular references)
- **Common follow-up:** "Shallow vs Deep cloning?" → Shallow copies references, Deep copies the actual objects. Use deep when mutable state must be independent.
