# Singleton Pattern — Interview Notes

## 1. What is the Singleton Pattern?

A **Singleton** ensures that a class has **only one instance** throughout the application's lifecycle and provides a **global access point** to that instance.

No matter how many times you call `getInstance()`, you always get back the **same object**.

---

## 2. Why is it a Creational Pattern?

Because it controls **how objects are created**. Instead of creating a new object every time (via `new`), it returns the already-existing instance.

---

## 3. When do you need it? (Real use cases)

Use Singleton when having multiple instances would cause problems:

- **Logger** — all parts of the app should write to the same log file
- **Database connection** — one shared connection pool
- **Configuration manager** — one centralized config object
- **Print spooler** — one queue managing all print jobs

> If everyone creates their own logger, you get overwritten logs, multiple file handles, and sync issues. One Singleton logger solves this.

---

## 4. How does it work? (Key mechanics)

Three things always involved:

| Component                                  | Purpose                                                 |
| ------------------------------------------ | ------------------------------------------------------- |
| **Private constructor**                    | Blocks anyone from doing `new ClassName()` from outside |
| **Static variable**                        | Holds the one shared instance                           |
| **Public static method (`getInstance()`)** | The only way to get the instance                        |

---

## 5. Two Approaches: Eager vs. Lazy Loading

### Eager Loading

- Instance is created **when the class loads**, even before it is needed.
- **Always thread-safe** (no synchronization needed).
- **Downside:** wastes memory if the instance is never actually used.

> Analogy: A fire extinguisher — always there, even if a fire never happens.

### Lazy Loading

- Instance is created **only when first requested** (when `getInstance()` is called for the first time).
- **Saves memory** if the instance is never used.
- **Downside:** Not thread-safe by default.

> Analogy: A coffee machine — only brews when you press the button.

---

## 6. Thread Safety — The Critical Part for Interviews

In a **multi-threaded** environment, two threads could simultaneously call `getInstance()` for the first time, both see `null`, and both create separate instances — **breaking the Singleton guarantee**.

### Ways to make Lazy Loading thread-safe:

#### A. Synchronized Method

- Wrap `getInstance()` with `synchronized`.
- Simple, but **slow** — every call acquires a lock, even after the instance already exists.

#### B. Double-Checked Locking (Preferred in interviews)

- Check `null` once **outside** the lock (fast path for already-created instances).
- Check `null` again **inside** the lock (prevents race condition during first creation).
- Uses `volatile` on the instance variable so all threads see the latest value (avoids CPU cache issues).
- **Efficient + thread-safe.**

#### C. Bill Pugh Singleton (Best Practice)

- Uses a **static inner class** (`Holder`) that holds the instance.
- The inner class is only loaded when `getInstance()` is called — so it is **lazy**.
- Java's class-loading mechanism guarantees thread safety automatically — **no `synchronized` or `volatile` needed**.
- Clean, efficient, and the cleanest approach overall.

#### D. Eager Loading

- No thread safety concern at all since the instance is created before any thread can request it.

---

## 7. Quick Comparison Table

| Approach                | Lazy? | Thread-safe? | Notes                           |
| ----------------------- | ----- | ------------ | ------------------------------- |
| Eager Loading           | No    | Yes          | Simple; wastes memory if unused |
| Lazy (basic)            | Yes   | No           | Not safe for multi-threading    |
| Synchronized Method     | Yes   | Yes          | Safe but slow                   |
| Double-Checked Locking  | Yes   | Yes          | Efficient; needs `volatile`     |
| Bill Pugh (Inner class) | Yes   | Yes          | Best practice; cleanest         |

---

## 8. Pros of Singleton

- Guarantees only one instance — good for shared resources
- Provides a centralized global access point
- Lazy implementations defer creation until needed (memory efficient)
- Clean when designed well (e.g., Bill Pugh)

---

## 9. Cons of Singleton (Know these for interviews)

- **Hard to unit test** — global state is difficult to mock or isolate
- **Tight coupling** — classes depending on Singleton are tied to its implementation
- **Violates SRP** — it manages its own lifecycle _and_ does its core job
- **Race conditions** — lazy implementations need careful handling in multi-threaded scenarios
- **Anti-pattern risk** — overusing it leads to hidden global state

---

## 10. Interview Quick Recall

- **Pattern type:** Creational
- **Core idea:** One instance, global access point
- **Three components:** Private constructor + Static variable + `getInstance()`
- **Best implementation:** Bill Pugh (static inner class) — lazy + thread-safe with no extra keywords
- **`volatile` keyword purpose:** Ensures all threads read the latest value from main memory, not a cached copy
- **When NOT to use:** When you need testability or the class has state that differs per context
