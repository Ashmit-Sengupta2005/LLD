# Chain of Responsibility — Interview Notes

The Chain of Responsibility Pattern gives a request to a **line of handlers**, each of which either **handles it or passes it to the next one** — so the sender never knows which handler will deal with it, or even how many there are.

---

## 1. The scenario

An e-commerce support desk. A ticket comes in, and depending on its type a different team should pick it up:

```
ticket  →  General  →  Billing  →  Technical  →  Delivery  →  (nobody)
             ↓           ↓            ↓             ↓
         "general"   "refund"    "technical"   "delivery"
```

The obvious way is one method holding every team's claim:

```java
class SupportService {
    public void handleRequest(String type) {
        if (type.equals("general"))        System.out.println("Handled by General Support");
        else if (type.equals("refund"))    System.out.println("Handled by Billing Team");
        else if (type.equals("technical")) System.out.println("Handled by Technical Support");
        else if (type.equals("delivery"))  System.out.println("Handled by Delivery Team");
        else                               System.out.println("No handler available");
    }
}
```

It works. Then: *"add a Fraud team, route VIP customers to a priority queue first, and let support leads reorder the teams without a deploy."*

---

## 2. The problem

- **Every new team means editing this method** — and it's the same method every other team lives in (violates Open/Closed)
- **The order is welded into the source** — reordering teams means rewriting the `if-else` chain by hand
- **One class knows every team's business** — the routing rules *and* what each team does
- **Nothing can be reused or tested alone** — Billing's logic is trapped inside a branch of someone else's method
- **The sender is coupled to the whole roster** — `SupportService` must know that four teams exist, and in what order

> The root cause: **the decision "is this mine?" belongs to each team, not to a central dispatcher.** One method is being forced to speak on behalf of everyone.

---

## 3. The fix: give each handler its own class, and a pointer to the next

```java
abstract class SupportHandler {
    protected SupportHandler next;                        // ⭐ the link in the chain

    public void setNext(SupportHandler next) { this.next = next; }

    public abstract void handle(String requestType);
}
```

Each handler answers only for itself, and forwards anything else:

```java
class BillingSupport extends SupportHandler {
    public void handle(String type) {
        if (type.equalsIgnoreCase("refund")) {
            System.out.println("BillingSupport: handling refund");
        } else if (next != null) {
            next.handle(type);                            // not mine - pass it on
        }
    }
}
```

The client links them up and hands the ticket to the **front** of the chain:

```java
general.setNext(billing);
billing.setNext(technical);
technical.setNext(delivery);

general.handle("refund");       // walks General -> Billing, handled there
general.handle("delivery");     // walks all the way to Delivery
```

The sender calls **one** object and never learns who actually did the work. Reordering the teams is now three lines of wiring, not a rewrite.

> **Analogy:** a customer-service phone tree, or passing a form down a row of desks. You hand it to the first desk; it either stamps it or slides it along. You never find out how far it travelled.

---

## 4. The roles

| Role | In our example | Job |
| --- | --- | --- |
| **Handler** | `SupportHandler` | Declares `handle()` and holds the `next` link |
| **Concrete Handler** | `BillingSupport`, `TechnicalSupport` | Decides *"is this mine?"* — handles it, or forwards |
| **Client** | `main()` | Builds the chain and hands the request to the **first** handler only |

> **Important:** the client knows the chain's *shape*, not its *logic*. And each handler knows only its own rule plus one pointer — never the full roster.

---

## 5. ⭐ Put the plumbing in the base class

The version in §3 (and in most tutorials) repeats this in **every single handler**:

```java
else if (next != null) next.handle(type);     // copy-pasted N times
```

That's the duplication the pattern was supposed to remove. Push it up into the base class and let subclasses declare only their rule:

```java
abstract class SupportHandler {
    private SupportHandler next;

    public SupportHandler setNext(SupportHandler next) {   // returns next -> fluent wiring
        this.next = next;
        return next;
    }

    // The walking logic lives HERE, once, and never changes
    public final void handle(Ticket ticket) {
        if (canHandle(ticket))      process(ticket);
        else if (next != null)      next.handle(ticket);
        else                        System.out.println("No handler found for " + ticket);
    }

    protected abstract boolean canHandle(Ticket ticket);   // my rule
    protected abstract void process(Ticket ticket);        // my work
}
```

A concrete handler is now pure business logic, with no plumbing at all:

```java
class BillingSupport extends SupportHandler {
    protected boolean canHandle(Ticket t) { return t.type().equals("refund"); }
    protected void process(Ticket t)      { System.out.println("Billing: refunding " + t.amount()); }
}
```

And wiring becomes one readable line:

```java
general.setNext(billing).setNext(technical).setNext(delivery);
```

This is **Template Method inside Chain of Responsibility** — `handle()` is the fixed algorithm, `canHandle()`/`process()` are the holes subclasses fill. Worth showing in an interview; it's a clear step above the textbook version.

---

## 6. ⭐⭐ "Doesn't the if-else just move into the handlers?"

**A fair objection, and sometimes the answer is yes — it's a bad fit.** Look honestly at the support example:

```java
canHandle(t) { return t.type().equals("refund"); }     // exact match on a key
```

If every handler does an **exact match on a type string**, you haven't built a chain — you've built a **lookup done the slow way.** A map is simpler, O(1), order-independent, and can't miss:

```java
Map<String, Handler> routes = Map.of(
    "general", general, "refund", billing, "technical", technical, "delivery", delivery
);
routes.getOrDefault(type, fallback).handle(ticket);     // no chain needed
```

CoR earns its keep when a map **can't express the rule**:

| Situation | Why a map fails |
| --- | --- |
| **Ranges / predicates** — expense < 1k → Lead, < 10k → Manager, else CEO | There's no key. The handler inspects the request's *content* |
| **Order matters** — auth must run before rate-limiting before validation | A map is unordered by design |
| **Several handlers may act** on one request | A map gives you exactly one |
| **The chain is configured at runtime** — per tenant, per environment, from a config file | A hardcoded map isn't configurable |
| **Overlapping rules** — first match wins, and that's deliberate | A map needs keys to be disjoint |

> **Say this:** *"If each handler is just matching a type key, I'd use a map. Chain of Responsibility is for when the handler's condition is a predicate over the request, or when order and short-circuiting matter."*

That single answer separates people who memorised the pattern from people who know when to use it.

---

## 7. ⭐⭐ Two flavours — and the textbook one is the rarer one

**(a) Pure CoR — first handler that can, does; the chain stops.** The support desk, approval limits, ATM cash dispensing. Exactly one handler acts.

**(b) Filter / pipeline — every handler runs, each doing a slice of the work.** Any one of them may **short-circuit** and end the request early:

```java
// a servlet filter - the shape you will actually meet in production code
public void doFilter(Request req, Response res, FilterChain chain) {
    if (!isAuthenticated(req)) { res.setStatus(401); return; }   // short-circuit, chain stops

    long start = System.nanoTime();
    chain.doFilter(req, res);                                    // ⭐ hand on to the rest
    log(System.nanoTime() - start);                              // work AFTER, on the way back
}
```

Flavour (b) is overwhelmingly more common in real systems — Servlet filters, Spring Security's filter chain, OkHttp interceptors, Express/Koa middleware, Netty's pipeline. Three things to notice:

- the **next** link is passed *in* (`chain`) rather than stored as a field, so one filter can sit in many chains
- a handler can do work **before and after** delegating, which is how timing, logging and transaction wrappers are built
- **not delegating is a feature** — that's how auth rejects a request

> Because (b) runs every link and does work on the way back, it looks a lot like **Decorator**. The distinguishing question is §9.

---

## 8. ⭐ The request can fall off the end

The chain's weak spot: if nobody claims the ticket, it vanishes silently. The naive `if-else` at least had an `else`.

Fixes, in order of preference:

```java
// 1. A catch-all terminal handler - always last, always claims it
class FallbackHandler extends SupportHandler {
    protected boolean canHandle(Ticket t) { return true; }                 // claims everything
    protected void process(Ticket t)      { escalateToHuman(t); }
}

// 2. Make handle() return a boolean, so the caller knows
boolean handled = general.handle(ticket);
if (!handled) log.warn("Unrouted ticket: {}", ticket);

// 3. Throw at the end of the base class's handle()
```

> Always mention this. "What if nothing handles it?" is the standard follow-up, and a terminal handler is the clean answer — it also removes the `next == null` check from the base class.

## 9. ⭐⭐ CoR vs Decorator vs Observer (the confusion set)

All three chain or fan out objects behind one interface. The differences are sharp:

| | **Chain of Responsibility** | **Decorator** | **Observer** |
| --- | --- | --- | --- |
| **Does every link run?** | **No** — one handles it, the rest never see it | **Yes** — every layer always runs | **Yes** — all are notified |
| **Can a link stop the flow?** | **Yes — that's the point** | No — it always delegates inward | No |
| **Order matters?** | **Yes**, decisively | Yes, but only for the result | **No** — broadcast |
| **Purpose** | Find who should handle this | Add behaviour to one object | Tell everyone something happened |
| **Shape** | Linked list, exits early | Nested wrappers, all the way down | One-to-many fan-out |
| **Example** | Approval limits, support routing | `BufferedInputStream`, pizza toppings | Newsletter, event listeners |

> **The test:** *Is the chain looking for someone to do the job, or is everyone contributing to one job?*
> **Looking for an owner → CoR.** **Everyone contributes → Decorator.** **Everyone just gets told → Observer.**

Flavour (b) from §7 sits deliberately between CoR and Decorator — a filter chain both wraps *and* can short-circuit. Saying that out loud is a good answer, not a confused one.

## 10. Where you've already used it

| System | Handlers | Link to next |
| --- | --- | --- |
| **Servlet / Spring Security filters** | Auth, CSRF, CORS, rate limit, logging | `chain.doFilter(req, res)` |
| **Express / Koa middleware** | Each `app.use(...)` | `next()` |
| **OkHttp / Retrofit interceptors** | Retry, auth header, cache, logging | `chain.proceed(request)` |
| **`try/catch` up the call stack** | Each enclosing `catch` block | Rethrow, or let it propagate |
| **DOM event bubbling** | Each ancestor element | Automatic, until `stopPropagation()` |
| **`java.util.logging` handlers** | Logger → parent logger → root | `getParent()` |
| **ATM cash dispenser** | ₹2000 → ₹500 → ₹100 handler | Pass the remainder on |

> Exception handling is the one everybody has used without noticing: a thrown exception walks up the stack until some `catch` claims it, and if none does, it reaches the top and the thread dies — **the unhandled-request problem from §8, built into the language.**

---

## 11. Pros / Cons

| Pros | Cons |
| --- | --- |
| **Sender is decoupled from receivers** — it calls one object and never learns who acted | **The request may go unhandled** (§8) |
| **Open/Closed** — a new handler is a new class plus one wiring line | **Order is load-bearing** — wire it wrong and the behaviour is wrong, silently |
| **Each handler is small, single-purpose and testable alone** | **Hard to debug** — the flow is a runtime structure, not visible in the source |
| **The chain is built at runtime** — reorder, insert, or configure per tenant | **Long chains cost** — every handler is a call and a check |
| **Short-circuiting is free** — stop as soon as someone claims it | **No guarantee of who handles it** — awkward when you need certainty |
| Models *first match wins* naturally | **Overkill for exact-key routing** — use a map (§6) |

---

## 12. Interview Quick Recall

- **Type:** Behavioural
- **Core idea:** Line handlers up; each either handles the request or passes it to the next, so the sender never knows who will
- **Roles:** Handler (abstract, holds `next`) + Concrete Handlers (one rule each) + Client (builds the chain, calls only the head)
- **Key line:** `else if (next != null) next.handle(request);` — better still, put it in the base class **once** (§5)
- **Trigger phrase:** *"escalate"*, *"approval levels"*, *"middleware"*, *"filters"*, *"pass it along until someone deals with it"*, *"first match wins"*
- **When NOT to use:** Exact-match routing on a type key — a `Map<String, Handler>` is simpler and O(1) (§6)
- **Follow-up 1:** *"Doesn't the if-else just move into each handler?"* → Each handler now owns only **its own** condition, not everyone's. And if the condition is just a key match, use a map instead (§6)
- **Follow-up 2:** *"What if nobody handles it?"* → A catch-all terminal handler, or `handle()` returns a boolean so the caller knows (§8)
- **Follow-up 3:** *"CoR vs Decorator?"* → Decorator runs **every** layer and can't stop; CoR stops at the first handler that claims the request (§9)
- **Follow-up 4:** *"Real example?"* → Servlet / Spring Security filter chains (`chain.doFilter`), or exception propagation up the call stack
- **Follow-up 5:** *"Can more than one handler act?"* → Yes — that's the filter/pipeline flavour, and it's the one you meet most in production (§7)
