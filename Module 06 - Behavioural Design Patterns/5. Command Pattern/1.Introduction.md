# Command Pattern — Interview Notes

The Command Pattern wraps a request — a method call — into its **own object**, so the request can be stored, passed around, queued, logged and undone later, instead of being executed on the spot.

---

## 1. The scenario

You're building a **smart-home remote control**. It has a few buttons, and they control devices:

```
Button 1  →  Light ON
Button 2  →  Light OFF
Button 3  →  AC ON
Button 4  →  AC OFF
Undo      →  reverse whatever happened last
```

The obvious way is to give the remote one method per button:

```java
class NaiveRemoteControl {
    private Light light;
    private AC ac;
    private String lastAction = "";

    public void pressLightOn()  { light.on();  lastAction = "LIGHT_ON";  }
    public void pressLightOff() { light.off(); lastAction = "LIGHT_OFF"; }
    public void pressACOn()     { ac.on();     lastAction = "AC_ON";     }
    public void pressACOff()    { ac.off();    lastAction = "AC_OFF";    }

    public void pressUndo() {
        switch (lastAction) {
            case "LIGHT_ON":  light.off(); break;
            case "LIGHT_OFF": light.on();  break;
            case "AC_ON":     ac.off();    break;
            case "AC_OFF":    ac.on();     break;
        }
    }
}
```

It works. Then the product team says: *"add a Fan, a TV and a geyser, and make undo work for the last 10 actions."*

---

## 2. The problem

- **The remote knows every device personally** — it holds `Light`, `AC`, and calls their methods directly. A new device means editing the remote (violates Open/Closed)
- **One method per button** — 6 devices × 2 actions = 12 methods on a class whose only real job is to say *"a button was pressed"*
- **Buttons are hardcoded** — `pressLightOn()` is button 1 forever. A real remote lets you **re-assign** what a button does
- **Undo is a `switch` on a string** — fragile, and it remembers only **one** action. Multi-level undo means a list of strings and a bigger switch
- **Two jobs in one class** — the remote both *triggers* actions and *knows how to perform* every one of them

> The root cause: **a method call is not a thing you can hold.** You can't put `light.on()` in an array, push it on a stack, or send it over a queue. Only objects can do that.

---

## 3. The fix: make the request itself an object

Every action becomes a tiny class that knows **its receiver** and **how to undo itself**:

```java
interface Command {
    void execute();
    void undo();
}

class LightOnCommand implements Command {
    private Light light;                        // the receiver it was born with
    public LightOnCommand(Light light) { this.light = light; }

    public void execute() { light.on();  }
    public void undo()    { light.off(); }      // ⭐ each command knows its own reversal
}
```

The remote now holds an **array of `Command`** and nothing else:

```java
class RemoteControl {
    private Command[] buttons = new Command[4];
    private Stack<Command> history = new Stack<>();

    public void setCommand(int slot, Command c) { buttons[slot] = c; }   // assign at runtime

    public void pressButton(int slot) {
        buttons[slot].execute();
        history.push(buttons[slot]);            // ⭐ remembering is now trivial
    }

    public void pressUndo() {
        if (!history.isEmpty()) history.pop().undo();
    }
}
```

The remote has **no `Light`, no `AC`, no `if`, no `switch`**. It only knows: *press slot → call `execute()` → push it*.

> **Analogy:** a waiter at a restaurant. You hand over an **order slip**; the waiter doesn't cook. They carry the slip to whichever chef handles it, and the slip can be queued, re-ordered or cancelled. The waiter is the **invoker**, the slip is the **command**, the chef is the **receiver**.

---

## 4. The four roles

| Role | In our example | Job |
| --- | --- | --- |
| **Receiver** | `Light`, `AC` | Knows how to actually do the work (`on()`, `off()`) |
| **Command** | the `Command` interface | The contract — `execute()` + `undo()` |
| **Concrete Command** | `LightOnCommand`, `ACOffCommand` | Binds one receiver to one action |
| **Invoker** | `RemoteControl` | Triggers commands; knows nothing about receivers |
| **Client** | `main()` | Creates receivers + commands and wires them into slots |

> **Important:** the invoker never knows the receiver. The **client** does the wiring once, and after that the remote is pure plumbing.

---

## 5. ⭐ Why undo becomes easy (the real selling point)

| Naive | Command |
| --- | --- |
| `lastAction = "LIGHT_ON"` — a **string** | `history.push(command)` — a **real object** |
| Undo = a `switch` listing every action | Undo = `history.pop().undo()` |
| One level of undo | **Unlimited** — it's a stack |
| New device → edit the switch | New device → new class, **remote untouched** |

Because each command already carries its receiver *and* its reversal, the invoker's undo logic is **two lines and never changes**.

Add a second stack and you get **redo** almost free — pop from history, re-execute, push to redo.

---

## 6. ⭐ Macro commands (grouping actions)

A command can hold other commands — "Night Mode" in one button press:

```java
class MacroCommand implements Command {
    private List<Command> commands;
    public MacroCommand(List<Command> commands) { this.commands = commands; }

    public void execute() {
        for (Command c : commands) c.execute();
    }
    public void undo() {
        for (int i = commands.size() - 1; i >= 0; i--) commands.get(i).undo();  // reverse order!
    }
}
```

This is **Composite + Command** — a macro *is* a command, so the remote can't tell the difference and needs no change.

> **Undo runs backwards.** If you did A → B → C, undoing must be C → B → A. Mention this; interviewers like it.

---

## 7. ⭐⭐ Command vs Strategy (the question you WILL get)

Both wrap behaviour in an object behind an interface. Same structure, **different purpose**:

| | **Command** | **Strategy** |
| --- | --- | --- |
| **Models** | A **request** — *do this thing* | An **algorithm** — *how* to do a thing |
| **Carries the receiver?** | **Yes** — built holding its target | **No** — data is passed in as arguments |
| **Interchangeable?** | No — each command is a *different* action | Yes — all strategies do the **same** job, differently |
| **Stored for later?** | **Yes** — queued, logged, stacked for undo | No — used now, maybe swapped later |
| **Has `undo()`?** | Usually | Never |
| **Example** | `LightOnCommand`, `DeleteTextCommand` | `NearestDriverStrategy`, `BCryptPasswordEncoder` |

> **The test:** *Are these objects alternatives to each other, or are they different requests?*
> **Alternatives for one job → Strategy.** **Different actions you want to store and replay → Command.**

## 8. Where you've already used it

| System | Command object | Invoker |
| --- | --- | --- |
| **`ExecutorService.submit(task)`** | `Runnable` / `Callable` | The thread pool |
| **Ctrl+Z in any editor** | Each edit, pushed on an undo stack | The editor |
| **Job queues (Sidekiq, Celery, SQS)** | A serialized task | The worker that picks it up |
| **Swing `Action` / button handlers** | The action object bound to a button or menu item | The UI framework |
| **DB transaction logs** | Each operation recorded, replayed or rolled back | The transaction manager |

> `Runnable` is the cleanest example — `run()` *is* `execute()`. The thread pool runs tasks without knowing what any of them do.

---

## 9. Pros / Cons

| Pros | Cons |
| --- | --- |
| **Decouples invoker from receiver** — the remote never knows a `Light` exists | **Class explosion** — one class per action |
| **Undo / redo almost for free** — just a stack | Overkill when an action has **no undo and no queueing** |
| **Open/Closed** — new action = new class, invoker untouched | **Undo is hard to get right** for complex state (store the old value, don't assume an inverse) |
| **Requests become data** — queue them, log them, schedule them, send them over a network | Extra indirection for a one-line call |
| **Macros** — group commands into one (§6) | Client has to wire receivers to commands |

---

## 10. Interview Quick Recall

- **Type:** Behavioural
- **Core idea:** Turn a method call into an object that carries its receiver, so it can be stored, queued, replayed and undone
- **Roles:** Receiver (does the work) + Command (`execute`/`undo`) + Concrete Commands + Invoker (triggers) + Client (wires)
- **Key line:** `private Command[] buttons;` — the invoker holds **interfaces**, never devices
- **Trigger phrase:** *"undo/redo"*, *"queue the request"*, *"schedule it"*, *"log every operation"*, *"re-assignable buttons"*
- **When NOT to use:** A plain direct call with no undo, no queue and no history — the extra classes buy you nothing
- **Follow-up 1:** *"Command vs Strategy?"* → Strategy = interchangeable **algorithms** for one job; Command = distinct **requests** that carry their receiver and can be stored and undone (§7)
- **Follow-up 2:** *"How do you do multi-level undo?"* → `Stack<Command>`; push on execute, `pop().undo()` on undo. Redo = a second stack (§5)
- **Follow-up 3:** *"How do you run several actions as one?"* → A MacroCommand holding a `List<Command>`; undo iterates in **reverse** (§6)
- **Follow-up 4:** *"Real example?"* → `Runnable` submitted to an `ExecutorService` — the pool is the invoker and has no idea what the task does
