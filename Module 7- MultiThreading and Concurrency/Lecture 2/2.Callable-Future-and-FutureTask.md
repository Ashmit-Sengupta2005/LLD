# Callable, Future & FutureTask — Getting a Result Back

---

## 1. The problem `Callable` solves

`Runnable.run()` is `void`. The ETA task can compute `"25 minutes"`, but it has no way to **return** it to the caller — it can only print it.

> **`Callable` is `Runnable` with a return value.**

| | `Runnable` | `Callable<T>` |
| --- | --- | --- |
| Method | `run()` | `call()` |
| Returns | nothing (`void`) | a value of type `T` |
| Can throw checked exceptions? | ❌ No | ✅ Yes |
| Use it for | fire-and-forget work | work whose **result you need** |

---

## 2. `Callable` + `ExecutorService` + `Future`

```java
class ETACalculationTask implements Callable<String> {     // ⭐ returns a String
    public String call() throws InterruptedException {
        Thread.sleep(5000);
        return "ETA: 25 minutes";                          // ⭐ a real return
    }
}

class SMSTask implements Runnable {                        // no result needed → Runnable
    public void run() {
        try { Thread.sleep(2000); System.out.println("SMS Sent."); }
        catch (InterruptedException e) { e.printStackTrace(); }
    }
}
// EmailTask is the same, with a 3-second delay
```

```java
class Main {
    public static void main(String[] args) {
        // A pool of 3 reusable worker threads
        ExecutorService executorService = Executors.newFixedThreadPool(3);

        Future<String> etaResult = executorService.submit(new ETACalculationTask());  // ⭐ returns a Future
        executorService.submit(new SMSTask());      // no result, so no Future kept
        executorService.submit(new EmailTask());

        try {
            System.out.println(etaResult.get());    // ⭐ blocks until ETA is ready, then prints it
        } catch (InterruptedException | ExecutionException e) {
            e.printStackTrace();
        }

        executorService.shutdown();                 // ⭐ always shut it down
    }
}
```

**What each piece does:**

- **`ExecutorService`** — manages threads for you. You stop creating `new Thread(...)` by hand and just **submit tasks**; the pool reuses its threads
- **`newFixedThreadPool(3)`** — 3 worker threads, so all three tasks can run at once
- **`submit()`** — accepts both `Runnable` and `Callable`, and hands back a `Future`
- **`shutdown()`** — stops accepting new tasks and lets the running ones finish. Without it the program may never exit, because pool threads stay alive

---

## 3. The `Future` interface

> **A `Future` is a receipt.** The task isn't done yet, but this object promises you the result later.

| Method | What it does |
| --- | --- |
| `get()` | Waits for the task to finish and returns the result — **blocking** |
| `isDone()` | `true` if the task has finished |
| `isCancelled()` | `true` if the task was cancelled |
| `cancel()` | Tries to cancel the task before it completes |

**⭐ `get()` blocks — this is the key point.** The moment you call `etaResult.get()`, the main thread stops and waits. So call it **as late as possible**: submit every task first, let them all run together, and only then collect results. Call `get()` too early and you've made your code sequential again.

---

## 4. `FutureTask` — the other way to collect a result

`FutureTask` wraps a `Callable` and implements **both `Runnable` and `Future`**. Because it's a `Runnable`, you can hand it to a plain `Thread`; because it's a `Future`, you can call `get()` on it.

> Use it when you want a return value **without** setting up an `ExecutorService`.

```java
class Main {
    public static void main(String[] args) throws Exception {
        FutureTask<String> etaTask = new FutureTask<>(new ETACalculationTask());  // ⭐ wraps the Callable

        Thread etaThread   = new Thread(etaTask);        // works because FutureTask is Runnable
        Thread smsThread   = new Thread(new SMSTask());
        Thread emailThread = new Thread(new EmailTask());

        etaThread.start();
        smsThread.start();
        emailThread.start();

        System.out.println(etaTask.get());               // works because FutureTask is Future

        smsThread.join();                                // these return nothing, so join() instead
        emailThread.join();

        System.out.println("All tasks completed.");
    }
}
```

> Note the two styles side by side: **`get()`** for tasks that return something, **`join()`** for ones that don't. Both make the main thread wait.

---

## 5. Which one do I use?

| Need | Use |
| --- | --- |
| Fire-and-forget (SMS, email, logging) | `Runnable` |
| A result comes back | `Callable` |
| Collect that result | `Future` (from `submit()`) or `FutureTask` |
| Many tasks, reused threads, real projects | **`ExecutorService` + `Callable` + `Future`** |

> **Why pools win in real code:** creating a thread per task is expensive, and nothing stops you from creating thousands. A fixed pool caps the thread count, reuses threads, and queues the rest.

---

## 6. Quick Recall

- **`Callable<T>`** = `Runnable` that can **return a value** and **throw checked exceptions**; its method is `call()`, not `run()`
- **`Future`** = a receipt for a result that isn't ready yet — `get()`, `isDone()`, `isCancelled()`, `cancel()`
- **`get()` is blocking** — submit all tasks first, call `get()` last
- **`FutureTask`** implements *both* `Runnable` and `Future` → run it on a plain `Thread` and still collect the result
- **`ExecutorService`** manages a pool of reusable threads; `submit()` tasks, then always `shutdown()`
- **Follow-up — "Runnable vs Callable?"** → return value and checked exceptions. That's the whole difference
