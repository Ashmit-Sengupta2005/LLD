# ReentrantLock & tryLock — When `synchronized` Isn't Enough

---

## 1. The problem — BookMyShow

A user starts booking a seat, and that booking runs inside a `synchronized` block. Midway through, the user **goes idle** — switches tabs, walks away.

The thread still **holds the monitor**. Every other user trying to book that seat is stuck waiting, with no way out and no idea how long.

> **The design rule hiding in this:** a lock should protect only the **short check-and-update** of the seat state — never a network call, a payment, or waiting on a human.

**Where `synchronized` falls short:**

| Limitation | Meaning |
| --- | --- |
| **No timeout** | A thread can't say "I'll wait 2 seconds, then give up" |
| **No non-blocking attempt** | There's no monitor version of `tryLock()` |
| **Not interruptible** | A thread blocked on a monitor cannot be interrupted |
| **No fairness** | Some threads may be skipped repeatedly (starvation) |

> `synchronized` is still fine for short, simple critical sections. When you need **timed, interruptible, non-blocking or fair** acquisition, use **`ReentrantLock`**.

---

## 2. Lock vs Mutex

| **Lock** | **Mutex** |
| --- | --- |
| The **general** mechanism for controlling access to a shared resource | A **specific kind** of lock that enforces **mutual exclusion** — one thread at a time |
| May or may not enforce ownership, depending on the implementation | Always ownership-bound — **only the thread that acquired it can release it** |
| Broad family: monitors, reentrant locks, read-write locks, spin locks | Focused on one job: exclusive access |
| Analogy: an access-control system on a room | Analogy: a **key** — only the person who took it can return it |

> **In Java:** both `synchronized` and `ReentrantLock` are ownership-bound, so `ReentrantLock` effectively **is** a mutex. A `Semaphore` is a lock-family tool that is **not** a mutex — it has no owner (§4 of the next file).

## 3. ReentrantLock

From `java.util.concurrent.locks`. A mutual-exclusion lock with **ownership**: only the acquiring thread may unlock it.

**"Reentrant"** = the same thread can acquire it multiple times without deadlocking itself. Every `lock()` needs a matching `unlock()`.

```java
class TicketBooking {
    private int availableSeats = 1;
    private final ReentrantLock lock = new ReentrantLock();

    public void bookTicket(String user) {
        lock.lock();                       // blocks until acquired
        try {
            if (availableSeats > 0) {
                availableSeats--;
                System.out.println(user + " booked the ticket.");
            } else {
                System.out.println(user + " — no seats left.");
            }
        } finally {
            lock.unlock();                 // ⭐ ALWAYS in finally
        }
    }
}
```

> **⭐ The one mistake interviewers look for:** `unlock()` must be in a `finally` block. With `synchronized` the JVM releases the monitor automatically even on an exception — with `ReentrantLock` **you** are responsible, and a missed `unlock()` deadlocks the application permanently.

**What it gives you over `synchronized`:**

| Feature | Method |
| --- | --- |
| Explicit control | `lock()` / `unlock()` — not limited to one block's scope |
| Immediate attempt | `tryLock()` — returns `true`/`false` at once, never waits |
| Timed attempt | `tryLock(2, TimeUnit.SECONDS)` |
| Interruptible wait | `lockInterruptibly()` |
| **Fairness** | `new ReentrantLock(true)` — longest-waiting thread goes first (FIFO), preventing starvation |

## 4. `tryLock()` with timeout

```java
boolean lockAcquired = false;
try {
    lockAcquired = lock.tryLock(2, TimeUnit.SECONDS);   // ⭐ wait at most 2 seconds

    if (!lockAcquired) {
        System.out.println(user + " could not get the lock. Try again later.");
        return;                                          // graceful fallback
    }

    // critical section
    availableSeats--;

} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    if (lockAcquired) lock.unlock();                     // ⭐ only unlock if you got it
}
```

- Returns **`true`** if acquired, **`false`** if the timeout expired
- Throws `InterruptedException` if the waiting thread is interrupted
- Lets the thread **retry, return an error, or take another path** instead of hanging forever

> **⭐ The critical limitation (and the favourite follow-up):** `tryLock(timeout)` controls **how long you wait to get the lock**. It does **not** expire a lock someone else already holds. The idle BookMyShow user keeps the lock either way.

## 5. ⭐ Why a timeout can't kick out the current owner

**Only the owning thread can call `unlock()`.** A scheduler or watchdog thread cannot take the lock away:

- `lock.isHeldByCurrentThread()` is `false` inside the watchdog
- `lock.unlock()` from the watchdog throws **`IllegalMonitorStateException`**
- Flipping some separate `isLocked` boolean changes nothing — the real lock state is untouched

**The correct approach is cooperative cancellation:**

1. A watchdog calls `owner.interrupt()` after the deadline — this is only a **request**
2. The owner notices (its `sleep`/`wait`/blocking call throws `InterruptedException`)
3. The owner stops its work and calls `unlock()` **from its own `finally` block**

```java
scheduler.schedule(() -> owner.interrupt(), 3000, TimeUnit.MILLISECONDS);
// the scheduler NEVER calls unlock()
```

**Takeaways:**
- **No forced expiry** — nobody can rip a lock away from its owner
- **`interrupt()` is a request**, not a kill. It doesn't stop a thread or release its locks
- **If the owner ignores interruption** or is doing non-interruptible work, it keeps the lock

---

## 6. Quick Recall

- **The problem:** `synchronized` has no timeout, no `tryLock`, no interruptibility, no fairness — a slow or idle owner blocks everyone indefinitely
- **Lock** = the general concept; **Mutex** = a lock with **ownership** (only the acquirer releases it)
- **`ReentrantLock`** = explicit, ownership-bound mutex; same thread can re-enter it
- **`unlock()` always goes in `finally`** — unlike `synchronized`, nothing releases it for you
- **`tryLock()`** = instant attempt; **`tryLock(t, unit)`** = timed attempt with a graceful fallback
- **`new ReentrantLock(true)`** = fair, FIFO acquisition — prevents starvation, but slower
- **⭐ Timeouts limit waiting, not holding** — removing an idle owner needs **cooperative cancellation** via `interrupt()`, and the owner must unlock itself
