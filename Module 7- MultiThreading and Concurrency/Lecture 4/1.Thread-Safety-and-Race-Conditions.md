# Thread Safety & Race Conditions

---

## 1. What is thread safety?

**Code is thread-safe if it still gives the correct result when many threads use it at the same time** — no wrong values, no corrupted data.

> **Example:** a TUF+ sale goes live and hundreds of users hit "Buy" at once. A thread-safe purchase counter records **exactly** as many purchases as happened. An unsafe one loses some, or oversells.

Problems only show up **under load**, which is why they're so dangerous — the code passes every test on your laptop and breaks in production.

---

## 2. What is a race condition?

**When two threads touch the same data at the same time and the final result depends on who happens to finish first, not on your logic.**

> **Analogy:** Two cashiers update a sales total on a whiteboard. Both read "₹10,000", both add ₹1,000, both write "₹11,000". **One sale just vanished** — neither saw the other's update.

---

## 3. The classic example: `count++`

```java
class PurchaseCounter {
    private int count = 0;

    public void increment() {
        count++;            // ⭐ looks like 1 step, is actually 3
    }

    public int getCount() { return count; }
}
```

```java
PurchaseCounter counter = new PurchaseCounter();

Runnable task = () -> {
    for (int i = 0; i < 1000; i++) counter.increment();
};

Thread t1 = new Thread(task);
Thread t2 = new Thread(task);
t1.start(); t2.start();
t1.join();  t2.join();

System.out.println("Final Count: " + counter.getCount());   // expect 2000, rarely get it
```

**Why the output is wrong and different every run:**

`count++` is really **three** separate operations:

```
1. READ   count        (say 42)
2. ADD    1            (43)
3. WRITE  it back      (42 → 43)
```

If both threads **read 42** before either writes, both write **43**. Two increments happened, but the count only moved by one — **one update is lost**. Over 2000 increments, you land somewhere under 2000, and the number changes each run.

> **The one-liner:** `count++` is **not atomic**, so a thread can be interrupted halfway through it.

---

## 4. ⭐ The two problems you must name separately

Every fix in the next file solves one or both of these. Interviewers test whether you can tell them apart:

| | **Atomicity** | **Visibility** |
| --- | --- | --- |
| **The problem** | An operation gets interrupted midway, so updates are lost | A thread caches a value and never sees another thread's update |
| **Cause** | `count++` is read-modify-write, not one step | Each CPU core has its own cache; writes may sit there instead of main memory |
| **Symptom** | Wrong count | A thread loops forever on a stale `flag` |
| **Fixed by** | `synchronized`, atomic classes | `synchronized`, `volatile`, atomic classes |

**Critical section** — the piece of code that touches shared data and must be run by **only one thread at a time**. In the example above, that's `count++`.

---

## 5. Quick Recall

- **Thread safety** = correct results even when many threads run the same code together
- **Race condition** = the outcome depends on **timing**, not logic — whoever finishes last wins
- **`count++` is 3 operations** (read, add, write) — the single most asked example in this topic
- **Critical section** = the code touching shared data; only one thread should be inside it
- **Two distinct problems:** **atomicity** (lost updates) and **visibility** (stale cached values)
- **Why it matters:** these bugs appear only under load and are nearly impossible to reproduce
