# Program, Process & Thread — Interview Q&A

---

## Q1. What is a program, a process and a thread?

**The bakery analogy — use this first, it answers all three at once:**

| | Bakery | Computer |
| --- | --- | --- |
| **Program** | The **recipe book** sitting on the shelf. Just instructions, doing nothing | `chrome.exe` on your disk |
| **Process** | **Actually baking** a cake from one recipe — the recipe in action | Chrome running, loaded in memory |
| **Thread** | The **individual bakers** inside that one job — one mixes, one preheats, one ices | Chrome's UI thread, network thread, input thread |

**Program** — a set of instructions written to do some task. It is **static**: a file on disk. Downloading `chrome.exe` gives you a program; it does nothing until you run it.

**Process** — a **running instance** of a program. The moment you double-click Chrome, the OS loads the code into memory and gives it resources (memory, CPU time, I/O). That running copy is the process.
- Has its **own memory space**, separate from every other process
- Runs independently; cannot touch another process's memory unless explicitly allowed (IPC)
- The OS manages it and hands it resources

**Thread** — the **smallest unit of execution inside a process**. One process can have many threads, and they all share the process's memory.
- Called a **"lightweight process"** — cheap to create, cheap to switch
- Threads of the same process share memory, so talking to each other is easy and fast
- Inside Chrome: one thread draws the UI, another fetches data from the network, another listens for your clicks — all at the same time, all inside one process

> **One line for the interview:** A program is the code at rest, a process is that code running with its own memory, and a thread is one lane of execution inside a process.

## Q2. Process vs Thread

| | **Process** | **Thread** |
| --- | --- | --- |
| **What it is** | An independent program in execution, with its own resources | A sub-unit inside a process, doing one specific task |
| **Memory** | Its own dedicated, isolated memory | **Shares** the process's memory with sibling threads |
| **Isolation** | Fully isolated — cannot interfere with another process | Not isolated — threads can directly read/write shared data |
| **Communication** | Hard — needs IPC (sockets, shared files, pipes) | Easy — just share a variable in memory |
| **Weight** | **Heavyweight** — costly to create and switch | **Lightweight** — minimal overhead |
| **Crash impact** | One process crashing doesn't affect others | One bad thread can take down the **whole process** |
| **Example** | Two PostgreSQL instances, each a separate process | A web server where each thread handles one client request |

> **Summary:** Processes are **isolated and safe but expensive**. Threads are **fast and connected but fragile** — a crash or a bad write in one thread hurts the rest.

## Q3. Shared memory vs Isolated memory

| | **Shared Memory** | **Isolated Memory** |
| --- | --- | --- |
| **Meaning** | Memory several threads/processes can all access | Memory owned by exactly one process, locked away from others |
| **Used in** | Multi-threaded apps that need to pass data around fast | Processes that must run independently |
| **Communication** | Fast — data is simply *there*, no copying | Slow — needs IPC, extra code and overhead |
| **Risk** | **Race conditions and data corruption** when two threads write at once | Very low — nobody else can touch your memory |
| **Example** | A video-processing app where many threads edit the same image data | A word processor and a browser — neither can read the other's memory |

> **Trade-off in one line:** Shared memory buys you **speed** and costs you **safety** (you must now synchronise). Isolated memory buys you **safety and stability** and costs you **speed and simplicity of communication**.

## Q4. When should you use a thread, and when a process?

**Use a THREAD when:**
- **Tasks need to share data** — shared memory makes this instant
- **Overhead matters** — threads are cheap to create and switch
- **The tasks are part of the same logic** — e.g. a web server handling requests, or video rendering
- **You need high performance** — threads can spread across CPU cores
- **Tasks are tightly coupled** and talk to each other constantly
- **Responsiveness matters** — push slow work to a background thread so the UI stays alive

**Use a PROCESS when:**
- **Tasks must be isolated** from each other
- **One crash must not kill the others** — failure stays contained
- **You need a security boundary** — no process can peek into another's memory
- **Different tech stacks or runtimes** are involved (a Python service next to a Java one)
- **You need resource limits** per task (cap its CPU or memory)
- **Different users** run the tasks, and their data must stay separate

> **Decide with one question:** Do these tasks need to **cooperate closely** (→ threads) or **not harm each other** (→ processes)?

## Q5. What is fault tolerance?

**Fault tolerance is a system's ability to keep working correctly even when something fails** — a crashed server, a dead disk, a dropped network link. The goal is that one failure should never bring the whole system down.

> **Analogy:** An aeroplane has multiple engines and backup systems. If one engine fails, the others keep the plane flying safely.

**How it is achieved:**
- **Redundancy** — keep spares ready: duplicate servers, backup power, mirrored data. If one dies, the spare takes over
- **Error detection and correction** — spot errors as they happen and fix them (checksums, parity bits, error-correcting codes)
- **Graceful degradation** — run slower or with fewer features instead of dying. If one server fails, route traffic to a backup; users notice a slowdown, not an outage
- **Automatic recovery** — detect the failed part and restart it, or shift its work elsewhere, with no human involved

## Q6. What is isolation?

**Isolation means keeping tasks, processes or environments separated so they cannot interfere with each other.** If one breaks, the rest carry on.

> **Analogy:** Rooms in a hotel. Each has its own lock, and a plumbing leak in room 204 doesn't flood room 205.

**What isolation gives you:**
- **Memory separation** — each process gets its own memory; nobody can read or overwrite another's data
- **Failure containment** — a crash stays inside its own box instead of spreading system-wide
- **Security boundaries** — in a multi-user system, one user cannot reach another user's data
- **Predictable behaviour** — nothing outside can interfere, so a task behaves the same way every time

> **How it links to fault tolerance:** Isolation is what *makes* fault tolerance possible. You can only contain a failure if the failing part was separated in the first place — which is exactly why we choose processes over threads when robustness matters.
