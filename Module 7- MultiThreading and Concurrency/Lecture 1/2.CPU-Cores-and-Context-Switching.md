# CPU Cores & Context Switching — Interview Q&A

---

## Q1. What are cores in a CPU?

**A core is a physical processing unit inside the CPU that can execute instructions on its own.** Modern CPUs ship with several cores, so the chip can genuinely work on multiple things at the same moment.

**Each core can run one thread independently** — so more cores means more threads actually running together, not just taking turns.

> **Analogy:** Cores are workers in an office. One worker (single-core) handles every task one after another. Ten workers (multi-core) take ten different tasks and finish them in parallel.

**Why it matters:**
- **Performance** — more cores, more work done at once. Video editing, gaming and data processing all feel smoother
- **Parallelism** — true simultaneous execution needs multiple cores; without them you only get the *illusion* of parallel work
- **Energy efficiency** — splitting work across cores finishes it sooner and lets the chip draw less power
- **Scaling your app** — knowing the core count lets you size thread pools properly instead of guessing

---

## Q2. What is hyperthreading?

**Hyperthreading (an Intel technology) lets one physical core behave like two logical cores**, so a single core can handle two threads at once. A 4-core CPU with hyperthreading looks like 8 cores to the OS.

> **Analogy:** One worker who can juggle two tasks — whenever one task stalls, they switch to the other instead of sitting idle.

**How it works:**

**Intelligent time slicing**
- The two logical cores take turns using the physical core
- Time slicing = splitting the core's time between the two threads so both make progress
- It is *intelligent* because when one thread is stuck waiting (for data, for disk, for network I/O), the other immediately uses that idle time

**Resource sharing**
- Both threads share the core's cache, execution units and memory bandwidth
- Those resources get divided smartly, so you gain performance without buying more physical cores

**Benefits**
- **Better resource utilisation** — far less idle time on each core
- **Better multitasking** — the core stays busy, wasted cycles drop

> **Careful:** hyperthreading does **not** double real performance. It only fills gaps that would otherwise be wasted — two logical cores are not as good as two physical cores.

## Q3. What is context switching?

**Context switching is saving the state of one thread/process and restoring the state of another, so the CPU can swap between them without losing anyone's progress.** This is what creates the *illusion* of parallelism even on a single core.

> **Analogy:** A chef cooking soup who must check the roast. They stop stirring (save where they were), check the oven, then come back to the soup exactly where they left off (restore the state). Progress on the soup is never lost.

**The steps, in order:**

1. **Interrupt** — the OS pauses the running thread, or a higher-priority thread demands the CPU
2. **Save state** — the current thread's registers, program counter and other vital data are written to memory, so it can resume from the exact same point
3. **Load state** — the next thread's saved state is loaded back from memory
4. **Switch execution** — the CPU starts running that thread from where it had stopped, and the cycle repeats

**Why it matters:**
- **Multitasking** — many threads appear to run "together" on one core
- **Resource management** — no single task can hog the CPU forever
- **Efficiency** — when one thread blocks, the CPU picks up another instead of idling

---

## Q4. What is the thread scheduler?

**The thread scheduler is the part of the OS that decides which thread runs next and when to pause the current one** — it is the thing that actually triggers context switches.

- Balances the workload so CPU time is spread fairly across tasks
- Uses **scheduling algorithms** — round-robin, priority-based scheduling, and others — to pick the next thread
- Every switch it orders is a context switch

---

## Q5. Is context switching free? (the follow-up)

**No — it has a real cost, and this is the usual interview follow-up.**

- **Scheduler overhead** — saving and loading thread state takes CPU cycles, and those cycles do no useful work
- **Performance degradation** — the more threads you create, the more time the CPU spends *switching* instead of *executing*. Past a point, adding threads makes the program **slower**, not faster

> **Say this:** "Threads aren't free. More threads than cores means more context switching, and beyond a point the switching overhead eats the gain — which is why we size thread pools to the core count rather than spawning a thread per task."
