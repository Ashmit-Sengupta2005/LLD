# Producer-Consumer Problem

---

## 1. What is it?

Two kinds of threads share one **fixed-size buffer**:

- **Producer** — makes data and puts it into the buffer
- **Consumer** — takes data out and processes it

**The problem:** the producer must not add when the buffer is **full**, and the consumer must not remove when it's **empty** — without race conditions.

Also called the **Bounded Buffer Problem**.

> **Analogy:** a coffee machine (producer) and a customer (consumer). Don't brew if the cup is full; don't drink if the cup is empty.

**Two things the solution needs:**
1. **Mutual exclusion** — one thread touches the buffer at a time
2. **Coordination** — a full producer and an empty consumer must **wait**, and be **woken up** when things change

---

## 2. The solution — `wait()` and `notify()`

| Method | What it does |
| --- | --- |
| `wait()` | Pauses the thread **and releases the lock**. Thread goes to **WAITING** |
| `notify()` | Wakes **one** waiting thread — it then competes to re-acquire the lock |
| `notifyAll()` | Wakes **all** waiting threads |

> **⭐ The key detail:** `wait()` **releases the lock**. If it didn't, nobody else could ever enter and change the condition — instant deadlock. (`sleep()` does **not** release the lock; that's the classic comparison question.)

Both must be called **inside a `synchronized` block**, or you get `IllegalMonitorStateException`.

---

## 3. The standard code (bounded buffer)

```java
class SubmissionQueue {
    private final Queue<String> queue = new LinkedList<>();
    private final int MAX = 5;

    // PRODUCER
    public synchronized void produce(String item) throws InterruptedException {
        while (queue.size() == MAX) {      // ⭐ while, not if
            wait();                        // buffer full → wait, release lock
        }
        queue.offer(item);
        notifyAll();                       // tell consumers there's data
    }

    // CONSUMER
    public synchronized String consume() throws InterruptedException {
        while (queue.isEmpty()) {          // ⭐ while, not if
            wait();                        // buffer empty → wait, release lock
        }
        String item = queue.poll();
        notifyAll();                       // tell producers there's space
        return item;
    }
}
```

**The flow:**

```
buffer full   → producer waits  → consumer takes one → notifyAll → producer resumes
buffer empty  → consumer waits  → producer adds one  → notifyAll → consumer resumes
```

---

## 4. ⭐ The three things interviewers ask

**1. "Why `while` and not `if`?"**
A woken thread must **re-check** the condition, because:
- **Spurious wakeups** — a thread can wake up without anyone notifying it
- `notifyAll()` wakes everyone, but by the time a thread gets the lock, another thread may have already emptied/filled the buffer

With `if`, it would skip the check and act on a stale condition. **`while` is the correct answer, always.**

**2. "`notify()` or `notifyAll()`?"**
- `notify()` wakes one **random** waiting thread — cheaper, but risky: it may wake another *producer* when you needed a *consumer*, and everyone sleeps forever
- **`notifyAll()` is the safe default** whenever you have multiple producers or consumers

**3. "`wait()` vs `sleep()`?"**

| | `wait()` | `sleep()` |
| --- | --- | --- |
| Releases the lock? | ✅ **Yes** | ❌ **No** |
| Wakes up when | notified | the timer expires |
| Called on | an object, inside `synchronized` | `Thread`, anywhere |

---

## 5. ⭐ The real-world answer: `BlockingQueue`

In production you don't write `wait`/`notify` by hand — `java.util.concurrent` already has it:

```java
BlockingQueue<String> queue = new ArrayBlockingQueue<>(5);

queue.put(item);        // producer — blocks automatically if full
String item = queue.take();   // consumer — blocks automatically if empty
```

**`put()` and `take()` handle all the waiting and signalling internally.** No `synchronized`, no `wait()`, no missed-notify bugs.

> **Say this at the end:** *"That's the classic `wait`/`notify` solution. In real code I'd use a `BlockingQueue`, which implements exactly this pattern and is already thread-safe."* It's the single best line to finish this question on.

---

## 6. Quick Recall

- **Producer-Consumer** = shared bounded buffer; producer waits when **full**, consumer waits when **empty**
- Needs **mutual exclusion** (`synchronized`) + **coordination** (`wait` / `notify`)
- **`wait()` releases the lock, `sleep()` does not** — the most common comparison asked
- **Always `while (condition) wait();`** — never `if` — because of spurious wakeups
- **`notifyAll()`** is the safe choice with multiple producers/consumers
- **Real answer: `BlockingQueue`** (`put()` / `take()`) — same pattern, already built and tested
